## 2026-11-23 — fix: ejoy 4/4 — client-routing dedup by route, cross-origin auth gate

ejoy kept flagging 0–2 of its 4 locked lessons, flapping run-to-run; the root causes were two, neither the query-rewrite (the `?path=` reaches the probe intact).

- **Cross-origin login redirect not detected.** The analysis profile's ejoy session had expired, so every cold navigation (free reference AND paid siblings) bounced to `sso.ejoyspace.com/?continue=…` — a DIFFERENT origin. The auth-freshness gate couldn't catch it: ejoy's entry URL has no seed fingerprint, so the gate proceeded conservatively and the run wasted ~50s producing 0 with misleading "redirected to /" logs. The gate now checks a cross-origin redirect FIRST, independent of any seed — positive, unambiguous evidence of an unauthenticated session. Verified live: logged in → FRESH, logged out → EXPIRED (sso bounce).
- **Distinct locked siblings collapsed as "duplicate".** Once authenticated, all 4 siblings render distinct real content (the DOM guard sees Lesson 3/4/5/6), but `keepClientRoutingByContent`'s reactContentKey duplicate-check dropped all but 2: a LOCKED lesson renders a near-identical paywall shell, whose identifier set is the course's whole lesson LIST (same across siblings), so 1033/1035 hashed equal to 1032/1034 and were dropped. Cross-candidate dedup for client-routing is now DETERMINISTIC on the leaked ROUTE (`vulnerabilityId`'s `clientRoute = normalizeUrl(candidateUrl)`): 1032 proposed from both the 1030 and 1031 pages rewrites to one route → one finding, sibling lessons keep their own routes. The reactContentKey DUPLICATE check is removed (the ALREADY-COLLECTED check stays); `captureReactContentKey` also now waits network-idle + settle so a fetch-gated route's content has landed before hashing.
- **Effect:** ejoy a stable 4/4 across two consecutive runs (1032/1033/1034/1035), ~50s. `findings`/`AnalysisPipeline`/`authFreshness` tests green (+1 client-route id test, authFreshness 7/7). Promova/lingualeo client-routing counts unaffected (each sibling already a distinct route).

## 2026-11-23 — fix: authz gate ignores the swapped identifier + same-type id swaps + `privacy` is never authz (duolingo)

duolingo flagged 2 FPs, both swaps onto a "Privacy" link. Neither was caused by missing history (live DOM: neither link is inside nav/footer, and `/privacy` was already crawled), so a nav/footer harvest would not have helped.

- **Why:** (1) `/settings/account -> /settings/privacy`: the ONLY sensitive key was the swapped href VALUE `privacy` — the identifier being swapped acted as its own entitlement evidence. (2) `help/faq?relative_domains=1 -> privacy`: the value `1` matched by token inside a lesson button's href (`/lesson/unit/1/level/1`), whose "sibling" in the same Link component is the footer `/privacy` link — a numeric slot swapped for a word.
- **What changed:** `excludeSwapDiff` drops the swap-path diff before `assessAuthZ` (motivation keeps the full diff); `sameIdShape` skips numeric <-> non-numeric swaps at generation (main + ablation; string form, so React `1` and `'1'` are both numeric); `NON_AUTHZ_TERMS = {privacy}` in the classifier, matched per normalized word at read time (no `CLASSIFIER_VERSION` bump).
- **Auth gate false EXPIRED (same batch):** `runAnalysisFromDb` kept aborting on duolingo even right after `refreshAuth`, because the gate required an EXACT fingerprint match and duolingo `/learn` had 220 captures with 220 distinct fingerprints (live, logged in: 562 nodes, no redirect, no login form). A mismatch is no longer expiry: EXPIRED now needs positive evidence — left the entry route, a password field, or a tree < 0.5× the smallest captured one (`ReactStateStore.nodeCountsForUrl`). Verified live both ways: logged in → FRESH; empty profile → EXPIRED (redirected to `/`). `authFreshness.test.ts` rewritten, 7/7.
- **Effect:** live duolingo re-analysis 2 → 0 findings, 569 → 354 requests, 3m06s → 49s; the `relative_domains` candidate is no longer generated, the `settings/privacy` one no longer passes the gate. Offline check on every stored finding: no TP of pimsleur (4), lingualeo (19), promova (25) affected; 2 odd mondly rows (`4 -> leoSprint/savannah`, lingualeo values — likely pre-site-scoping residue) would also drop. Tests: +6 unit (sameIdShape incl. `'1'`/`1`, excludeSwapDiff, privacy deny); pipeline/ablation 21/21.

- **Why (FPs):** the stage-2 SSR navigation fallback captured the post-goto URL but never checked it — only stages 1 (`stayedOnRoute`) and 3 (`sameRoutePath`) had a redirect-away guard. - **Effect:** clozemaster recheck 0/101 still flagged (all `/pro` redirect-away); full re-analysis 101 → 0 findings, client probes 5 080 → 508 dispatched / ~10 executed (498 skipped), analysis 64m48s → 1m38s. ## 2026-11-23 — feature: client-routing sibling-group confirmation + semantic finding dedup

Two companion changes that together cut noise and recover flaky-lost findings without weakening any guard.

- **Sibling-group confirmation (recover flaky-lost paid siblings).** The client-routing probe is flaky on fetch-gated routes (ejoy's locked lessons load content by id over XHR; one real load can snapshot an incomplete render and read as a false negative), so which paid siblings surface flips run-to-run — ejoy flagged only 1 of 4 locked lessons. Siblings of ONE reference node that share the swap `path` AND the authz-relevant keys are structurally identical resources behind the same route, so a genuine confirmation of one is a logical consequence for all. `CandidateEvaluator` now keys each client-routing candidate into a group (`pageUrl` + `stateId` + refNodeId + swap path + sorted authz sensitiveKeys). A genuine accept confirms the group; siblings the per-candidate probe rejected are stashed and replayed once their group is confirmed (eagerly on confirm, plus `finalizeClientGroups()` backstop). A sibling of an already-confirmed group is recorded without re-probing. SAFETY: only ever ADDS siblings to an already-confirmed group — can never confirm a group with zero genuine accepts.
- **Semantic dedup key (collapse carrier-redundancy, preserve api/page/client layer).** Promova produced 41 findings for 9 underlying paid-lesson IDORs because the same sibling pair surfaced via three HTTP carriers (page SSR flight, backend API, alternate plan URL) + client-routing. The old `vulnerabilityId` keyed on `candidateValue + nodeId + method + url`, so every carrier's `url` produced a distinct row. The new key is `sha256(site + origin + method + stateId + refNodeId + candNodeId + path)`: the sibling PAIR (stateId+nodes+path) scoped to the LAYER the leak was observed at (origin+method). Three plan carriers on `promova.com:GET` collapse to one; the `courses.api.promova.com:GET` row stays distinct (different layer); the `promova.com:CLIENT` row stays distinct (different detection surface). Preserves the auditor's api-vs-page-vs-client distinction, collapses plan-context noise.
- **Safety & tests:** `findings.test.ts` + `AnalysisPipeline.test.ts` 25/25 pass; recheckFindings on busuu/pimsleur/babbel/lingualeo + ejoy/promova re-analysis pending. Decision-logic change → still owes a recheck pass on the 4 reference sites.

## 2026-11-22 18:30 — feature: persist paper-support metrics to the DB + cross-app aggregation script

To make writing the evaluation (Fig. 3 funnel, Fig. 4 identifier position, Table IV cost) a query instead of a manual dig, the per-app rows now carry every number the figures need, and a new script aggregates them across the application set.

- **Why:** the stored stats conflated HTTP forges with client-routing probes, did not record the mutated-segment position of a finding, had no per-app UI-complexity measure, and nothing computed the cross-app mean/median/mode the paper reports.
- **What changed:**
  - `analysis_stats` gains per-app columns (added via on-the-fly migration, read-only-safe): `http_events_unique`, `http_forged` + `client_probes` (the split of `requests_generated` by detection path), `vulns_http` + `vulns_client` (findings per class), `clickables_per_state_mean` + `clickables_per_state_median` (GUI complexity, from `crawl_states.clickables`).
  - `vulnerabilities` gains `segment_location` (`path`/`query`) + `segment_index` (0-based from the right) — the mutated-value position for Fig. 4. `SegmentCandidate` now carries `location`/`indexFromRight`, threaded through the three evaluate paths into `recordFinding`.
  - New `npm run paper-stats` (`scripts/paperStats.ts`): per-app table, cross-app mean/median/mode (+min/max) per metric, and the position × value-type matrix; writes `reports/paper_per_app.csv` and `reports/paper_id_location.csv`. The Fig. 4 matrix is derived from the finding URLs, so it already works on findings stored before the new columns existed. Cost compute/wait is split using the forge-pacing constants.
  - `mean`/`median`/`mode` helpers in `utils`; `tokenizeParamName` already shared there.
  - **Fix (pre-existing):** a re-analysis of already-captured data (`runAnalysisFromDb` passes `explorationMs:0` — it never explores) overwrote the crawl's real `exploration_ms` with 0. `record()` now keeps the stored value whenever the incoming one is 0 (a genuine crawl is always >0), so the exploration time survives any number of re-runs. Covered by a new store test.
- **Effect:** no behaviour change to detection — purely additive persistence + reporting. Existing rows read back with the new columns defaulted to 0 until re-run; `runAnalysisFromDb` backfills them without a re-crawl. ## 2026-11-22 17:10 — fix: tame candidate-generation explosion on telemetry-heavy SPAs (duolingo)

Duolingo's analysis was abandoned as `infeasible` — candidate generation produced **110k forged GETs** (11× the 10k budget) from only ~75 logical endpoints. Diagnosed three compounding causes and fixed each at its root; duolingo now generates **458** distinct forges (offline count) and is analysed instead of skipped.

- **Why it exploded:** (1) the crawler re-fires every XHR on each DFS restore, so ~75 endpoints became **58,474 GET events**; (2) each carried a cache-buster timestamp (`_=<epoch-ms>`, `ts=<epoch-s>`), so every repeat was a *distinct* URL that neither the history filter nor the forge-dedup collapsed, and candidate generation ran 58k times; (3) a timezone param `tzoffset` (a non-identifier, like pagination/locale) was forged into thousands of nonsense offsets.
- **What changed:**
  - `normalizeUrl` (findings.ts) now strips volatile params **robustly by value shape**, not a name list: any query value that is a 10-/13-digit epoch timestamp is dropped, so it catches cache-busters whatever the site names them (corpus-wide: `_`, `ts`, `t`, promova's `tft`). An **identifier-name guard** (`id`/`userId`/`uuid`/`token`/…) keeps a real id that merely resembles an epoch. `tokenizeParamName` moved to `utils` (shared with the param blacklist).
  - `AnalysisPipeline` generates candidates **once per canonical GET URL** (dedup before the generation loop) instead of once per raw event — behaviour-identical to the existing forge-dedup (first-wins), but it no longer re-runs the whole preindex lookup for every duplicate (duolingo: 58k → 79 generations).
  - `tzoffset`/`timezone`/`tz`/`utcoffset` added to `analysis.paramBlacklist` (representation params, not object references).
- **Effect:** duolingo 110k → 458 forges (feasible). No reference site uses any stripped/blacklisted param (`_`/`ts`/`tzoffset` absent on busuu/pimsleur/lingualeo/babbel), and the event-dedup is behaviour-preserving, so the dispatched set for the reference sites is unchanged. Decision-logic (guards, response comparison) untouched. New unit tests in findings/utils; full analysis + ablation suites green (60 tests). Live `recheckFindings`/`runAnalysisFromDb` regression skipped per the user (re-crawl pending).

## 2026-11-22 15:30 — safety: block external protocol handlers (mailto:/tel:/sms:/webcal:/zoommtg:/…)

Clicking an `example@gmail.com`-style link (or any `mailto:`/`tel:`/`sms:`/`webcal:`/`zoommtg:`/app-deep-link) made Chromium hand the URL to the OS, launching an external app and pulling the crawler out of the page. These links carry no paid resource to probe, so they are pure noise and risk.

- **Why:** keep the crawler inside the page under exploration; never spawn external processes.
- **What changed:** new `allowedLinkSchemes` allowlist (default `http, https, javascript, about`). Two layers: (1) `ClickableExtractor` drops any clickable whose `href` uses a non-allowlisted scheme, so it is never offered; (2) a capture-phase in-page guard (`blockExternalProtocols`, installed by `ActionExecutor` via `addInitScript` + a one-off evaluate) `preventDefault`s clicks on such anchors, covering cases that slip past extraction (wrapper clicks, dynamically-set hrefs). Shared `linkScheme`/`isExternalAppLink` helpers in `utils`.
- **Effect:** external-app handoffs no longer happen during exploration. New tests in `ClickableExtractor`, `ActionExecutor`, `utils`; full suite green. No change to geometry, fingerprints, or the HTTP/analysis path.

**Severity: high — cross-site contamination that invalidated multi-site analyses.** `preindexed_values` has no `site` column, and `findByValue`/`countByValue` filtered only `WHERE value = ?`. But the DB holds many sites at once (`db.overwriteExistingDomain` wipes only the domain being re-crawled, never the others), so a value lookup returned EVERY site's nodes. Analysing celpipsimulator, its `/blog?_rsc=` segment `blog` matched **babbel's** footer `blog` link (the value `blog` was indexed by 4 sites: arabicroad 2, lingualeo 40, babbel 14, celpip 10) and forged celpipsimulator's `/privacy` from babbel's sibling — a cross-site false positive whose very motivation showed babbel URLs (`about.babbel.com`, "Inside Babbel").

- **Both lookups are now site-scoped** (`PreindexedValueStore.findByValue`/`countByValue` take `{ value, site }`): `WHERE value = ? AND state_id IN (SELECT id FROM react_states WHERE site = ?)`. Via the state's own site (state_id → react_states.site), so it is correct on an existing DB with no migration/backfill. New `idx_react_states_site` indexes the subquery (hot path during candidate generation). `candidateGenerator.findUrlCandidates` now takes `site`; `AnalysisPipeline` passes it at both call sites.
- **Effect**: verified on the live DB — `findByValue({ value:'blog', site:'www.celpipsimulator.com' })` returns celpip's 10 rows, not the 66 across 4 sites; babbel's footer no longer leaks in, so the celpip FP is gone. Only ever REMOVES wrong-site candidates; a site's own candidates are unchanged.
- **Caveat**: any finding in a shared DB produced before this fix may be cross-contaminated — re-run `runAnalysisFromDb` per site (the capture data is fine; only candidate generation was wrong). A finding whose motivation references another site's data was this bug.
- Tests: `PreindexedValueStore.test.ts` rewritten site-aware + a dedicated cross-site isolation case; `candidateGenerator.test.ts` updated. 19/19 in the two files, typecheck clean.

## 2026-11-20 17:15 — design: explore ONE deep target page; retry the stage-3 client-routing escalation

Two coupled changes, both driven by how noisy these language-learning SPAs are to crawl neutrally.

**Design shift — a single, manually-chosen target page explored deeply, not a wide shallow sweep.** A neutral seed wastes the 45-min budget wandering chrome/sections and never reaches the deep lesson/exercise flow where the IDORs live (busuu's `objective_<uuid>` sits ~3 clicks below the timeline). New defaults encode the workflow:
- `maxDepth` **3 → 4** (headroom for a lesson→start→exercise flow, with margin for an intermediate step).
- `ignoreClickablesWithin` default **`['nav','footer']`** (was `[]`): keep the crawler on the target page by not clicking navigation/footer chrome. **`header` is deliberately NOT included** — busuu renders its lesson cards (the real targets) inside a `<header>`, so ignoring it would make them unreachable (the same header-is-content trap as the domZone filter). This is what the earlier busuu run hit: `header` was still blacklisted, the lesson cards were never clicked, and the crawl stayed on one URL.
- Combines with `randomizeClickOrder` (already on) so the deep exploration samples the whole clickable set.

**Stage-3 client-routing retry** (`config.analysis.clientRoutingEscalationAttempts`, default **2**). The strict stage-3 full-navigation escalation (`confirmByFullNavigation`) — the costly real-load confirmation that decides for ejoy-class Next.js routes — was **single-shot**, while the cheap pushState probe already retried 3×. A single real load of a fetch-gated route (ejoy's lessons fetch their content by id over XHR) can snapshot an *incomplete* render and read as a false NEGATIVE, flipping which paid siblings surface run-to-run (ejoy's 4 locked lessons 1032/1033/1034/1035: 2 found per run, but a different 2). Now retried on a **flaky** reject only — capture failed / inert / not-found; an ACCEPT (null) or a DETERMINISTIC redirect-away ends immediately (re-navigating can't change those). Split `confirmByFullNavigation` into a retry loop + `confirmByFullNavigationOnce`; the redirect-away reason is now a shared `REDIRECT_AWAY_PREFIX` constant. **Can only ever recover a finding, never lose one** (a genuine inert/not-found still rejects on the last attempt). Cost is bounded: the retry fires only on a high-suspicion candidate that reached stage 3 and got a negative — a small set — and the knob can be lowered to 1 on a huge site. Threaded through `AnalysisPipelineOptions` / `ClientRoutingVerifierOptions` / the three scripts.

Decision-logic change (owner-run `recheckFindings` on the 4 reference sites owed). Typecheck clean; `clientRouting` + `AnalysisPipeline` tests green.
