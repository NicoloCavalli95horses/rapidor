## 2026-11-25 17:30 — fix: authz gate rejects a value-only signal contradicted by an equal entitlement key

Promova's ablation flagged 101 `/ai-tutor/999 -> /ai-tutor/<n>` swaps (plus 2 `my-plan/…/999`). The gate passed on the tag VALUE `free_talk` ("free"), while the explicit `free` key was `false` on all 171 lessons. The forged RSC payload is the same page shell (echoed id + per-render RSC key + deploy ids), so nothing leaked. The main pipeline never proposes these swaps: the catalog is not rendered as sibling components carrying ids.

- Why: an entitlement key equal on both sides is positive evidence of the same privilege; a value that merely contains an authz word is not.
- What: `assessAuthZ` returns `nameKeys` (hits from key/path names). `httpGuards.authzGateVerdict` (shared, main + ablation) rejects when `nameKeys` is empty and the swapped resource has an authz-relevant key with an equal flag/term value. Value-only verdicts without such a key (string enums) are unchanged. Tests in `test/httpGuards.test.ts`. New `scripts/debug/authzGateAudit.ts` (`--trace`, `--value-only`), and `ablationFunnel.ts --trace`.
- Effect: main unchanged, since all 59 stored findings on the 8 sites with findings pass by key name (audit, 0 rejected); `recheckFindings` cannot test this rule. Ablation: promova 110 → 7 (6 SSR `my-plan` + 1 `courses.api`, lessons 76/77/78, the main's TPs), talkpal 2 → 2. Sites with 0 findings cannot change (the guard only removes).

## 2026-11-25 14:40 — fix: ablation aligned with the main pipeline (shared decision code)

The ablation must differ from the main pipeline ONLY in the sibling source (JSON bodies vs React components). It was judging candidates more leniently: no diff scoping, the swapped id counted as its own evidence, no `isIdenticalResponse`, no value-insensitivity.

- Why: with laxer guards the React-vs-JSON comparison was confounded by the oracle, not just by the signal.
- What: new `analysis/httpGuards.ts` (`authzGateVerdict`, `httpContentGuardReason`) used by BOTH `candidateEvaluator` and `AblationPipeline`. The ablation now runs the authz gate before the forge (scoped via the new `JsonCandidate.swapPath`, swap diff excluded, direction gate), drops `isIdenticalResponse` forges (no client-routing fallback), and defers findings to a value-insensitivity + dedup finalization. Generation uses one reference per canonical 200 GET and `isNonSerializableMarker`, like the main pipeline. `authOverride` reaches the ablation forge. `runAblationFromDb` gained the entry-point auth gate.
- Effect (`runAblationFromDb` on all 15 sites, session FRESH everywhere): promova 138 → 110, talkpal 2, every other site 0 (unchanged). Main-pipeline behaviour unchanged (refactor only; `AnalysisPipeline` tests pass). `scripts/debug/ablationFunnel.ts` replays the funnel offline stage by stage. Its findings: busuu's 14 HTTP TPs ARE generated by the ablation but fail the authz gate (the `unlocked` signal exists only in React props); getpronounce's `echo` is in no JSON body; pimsleur/lingualeo/ejoy TPs are client-routing (out of scope by construction).

## 2026-11-25 10:30 — fix: client-routing dedup keys on the swapped sibling identity, not the full route

lingualeo reported 18 client-routing findings that are really 9 premium training types, each counted twice: the same type is reached at two word-set scopes (`/en/training/wordMix` and `/en/training/word_set/8/wordMix`). The `clientRoute` dedup key (`normalizeUrl(candidateUrl)`) kept the `/word_set/8/` prefix, so the two scopes hashed to different routes and did not collapse.

- Why: the leaked *capability* is the training TYPE; the word-set is orthogonal (which words, not which paid feature). Counting type×scope double-counts the same leak and inflates the TP count.
- What: `vulnerabilityId` client-routing branch now keys on `clientSwap` = `candidateValue|location|position` (path index-from-right, or query param name) instead of `clientRoute`. Carrier-independent: identical across a path-prefix or volatile-param difference. `candidateEvaluator.recordFinding` builds the key; `normalizeUrl` is no longer used there.
- Effect: lingualeo 18 → 9. Proven from the stored rows (distinct `candidateValue|location|segment_index` per site): ejoy 4, pimsleur 4, promova 9-CLIENT, rocketlanguages 1, babbel 2 all unchanged — in the reference sites the swapped value is already unique per route, so per-value and per-route keys coincide, and "same sibling from two reference pages" still collapses. Client-routing only; HTTP findings (busuu, getpronounce, promova's 15 http) use the unchanged branch. Validated with `runAnalysisFromDb` on lingualeo/ejoy/promova/pimsleur.

## 2026-11-25 09:00 — fix: never forge our own `[non-serializable:...]` placeholder as a candidate value

A re-analysis of babbel (negative control) produced a spurious client-routing finding whose candidate value was the literal string `[non-serializable:undefined]` — the marker the browser extension stringifies an unserializable React prop into (`[non-serializable:<ctor>]`). It is our own placeholder, never a value the app uses as an identifier, so forging it into a path/route is meaningless.

- Why: the sibling React node's swapped leaf was an `undefined` prop → serialized to `[non-serializable:undefined]`; candidate generation used it as a replacement value, producing a FP (babbel path swap `0ecaf91… -> [non-serializable:undefined]`, which also compared a `placement_test` widget against a lesson).
- What: new `isNonSerializableMarker` in `candidateGenerator.ts`, applied beside `segmentBlacklist`/`sameIdShape` in `expand()` — a candidate whose replacement value matches `^\[non-serializable:.*\]$` is dropped. Main pipeline only (the marker is a React artifact; the ablation reads JSON bodies, where it never appears).
- Effect: babbel 3 → 2 findings (the two `content_release_id` client-routing swaps remain, under manual TP/FP review). Provable no-op elsewhere: across the whole DB only babbel's one finding had a marker as `candidate_value`, so no reference-site TP is affected (no full reference re-run needed).

## 2026-11-24 21:40 — feature: `node.dom` = the element's opening tag (extension build 57); chrome zone reads only the element's own tag

The extension stored each node's full `outerHTML`, repeating every subtree at each ancestor, although the chrome-zone skip only needs the element's own tag/role/class.

- Extension (`bridge.js`, build 57): `dom` is the start tag, serialized from a shallow copy in an inert document (no custom-element constructor, no resource load). Checked in Chromium: equal to `openingTag(outerHTML)` on every element, SVG/void/`>`-in-attribute included.
- `domZone.openingTag` + `domChromeZone` reads only the element's own tag (`\srole=`/`\sclass=`, whole attribute names). Before, a role/class anywhere in the subtree counted: babbel's app wrapper was "navigation" through a nested `role="navigation"`, so its descendants were skipped.
- Stored `react_states` trimmed to the same form (backup first, then `VACUUM`): `storage/crawler.db` 11.5 -> 7.0 GB (graphs 7.6 -> 3.1 GB), `demo/crawler.db` 0.94 -> 0.41 GB. Backup vs trimmed, same code: identical candidates, chrome skips and `reactContentKey` on all 15 sites.
- Effect vs the old rule: identical on every site but babbel (+40 generation candidates, `lesson-player -> root/lesson-root/…`) and rocketlanguages (2 590 nodes no longer chrome, 0 candidate change). Reference sites unchanged.
- babbel `runAnalysisFromDb`: the +40 candidates are all rejected. It now stores 3 CLIENT findings (was 0 on 2026-11-23) from candidates the old rule produced too, so NOT from this change: a `[non-serializable:undefined]` extension sentinel used as a path value, and 2 `content_release_id` lesson swaps passing on `unlocked` only. Open: to investigate.
- Build docs: `yarn build:chrome` (production + ONNX/offscreen assets), not the development build the docs named.
- Extension build 58: same, minus an unused `prop-types` import in `bridge.js` (no longer bundled).

## 2026-11-24 20:30 — fix: analysis heap OOM on large React graphs (rocketlanguages)

rocketlanguages' end-of-crawl analysis died with `JavaScript heap out of memory`: 259 states of ~23 MB of graph JSON each (5.4 GB, 10x any other site), and `CandidateGenerator` kept every parsed graph for the whole run (~31 MB of heap each, ~8 GB against Node's ~4.3 GB limit).

- Why so big: the extension's `node.dom` is the element's FULL `outerHTML`, so every subtree is repeated at each ancestor (13 of the 23 MB per state). Only the chrome-zone skip reads it.
- `slimGraphForGeneration` (`domZone.ts`): on load, each node's `dom` becomes its precomputed `chromeZone` label and is dropped. Same verdict: checked on every stored state (1 472 states, 3.0M nodes, 0 differences).
- The graph cache is now an LRU bounded by stored JSON size (`graphCacheMaxBytes`, default 1 GB). Every other site fits whole, so they never re-parse; `ReactStateStore.getJsonById` added.
- Effect (generation only, rocketlanguages, default heap): peak 2.3 GB, 275 parses (259 states + 16 re-parses), 33 s, 231 candidates. No change to what any site generates.

## 2026-11-24 19:00 — feature: `run_metadata` table — how each site's crawl was produced

The DB recorded no trace of the config, code revision or stop condition behind a crawl, so a truncated
crawl looked like a complete one and the data's provenance (needed for the Zenodo artifact) was unknown.
`analysis_stats.exploration_ms` is also overwritten with 0 by `runAnalysisFromDb` (duolingo, talkpal).

- New `RunMetadataStore` (`run_metadata`, one row per site) written by `RunMetadataHooks` at the end of the exploration, before `AnalysisHooks`: start URL, start/end, `exploration_ms`, `stop_reason`, `git_commit` (`-dirty` aware), effective config JSON (without `userDataDir`/`startUrl(s)`). Wiped by `clearOnStart` and by the per-domain overwrite like the other per-site tables. Not written by `runAnalysisFromDb` (a debug path).
- `DfsExplorer` reports why it stopped: `IExplorationHooks.onEnd` gets an optional `stopReason` (`completed`/`max-states`/`max-duration`/`error`).
- Backfilled the 14 sites crawled 22–24/11 (one-off, outside the repo): exploration code and config unchanged since the first crawl (verified by `git diff`), commit = last before the crawl, `exploration_ms` from `analysis_stats` (state-timestamp span for duolingo/talkpal), `stop_reason` inferred: max-duration celpip/duolingo/pimsleur/lingualeo, max-states clozemaster, completed the rest.
- Tests: `RunMetadataHooks.test.ts` (5), `DfsExplorer.test.ts` +4 stop-reason cases.
