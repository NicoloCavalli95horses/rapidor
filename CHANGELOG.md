## 2026-11-20 13:00 — analysis: scope the authz gate to the swapped resource + lower the threshold (ejoy lesson IDOR vs nav FPs)

The authz gate classified the WHOLE component diff, so a sibling swap of a whole nav/layout component "passed" on a generic key sitting anywhere in it (ejoy's `37 → 45` swaps a menu item's `items.0.id` yet passed on the top-level `user` object) — while a real, focused entitlement diff missed because its sole signal scored just under threshold (ejoy's paid lesson `lock: false → true`, `whether lock` = 0.307 < 0.33). Two coupled changes fix both, verified safe against every reference finding's stored `authz_diff`.

- **Scope the diff to the swapped resource** (`scopeDiffsToResource`, responseEvaluate.ts; always on, in `CandidateEvaluator.authzGate`). Before classifying, keep only diffs under the swapped value's PARENT object (the resource the id names). A generic key elsewhere in a whole-component swap (`user`, `feature`) is dropped; an entitlement that is a sibling of / nested within the swapped id survives. Verified: ejoy nav `user` (top-level, swap `items.0.id`) → dropped; ejoy `lesson.lock` under `lesson.id`, pimsleur `miniLesson.isFree` under `miniLesson.id` → kept; busuu/lingualeo swap a TOP-LEVEL `id` (parent is root) so nothing is scoped out — lingualeo's `user`-VALUE finding survives. (React/main pipeline only; the ablation's JSON candidate path is element-relative and would need separate plumbing.)
- **Lower THRESHOLD 0.33 → 0.30** (authzClassifier.ts), applied at READ time (recomputed from the cached score), so no `CLASSIFIER_VERSION` bump and persisted scores stay valid. This catches ejoy's `lock` (0.307). It is only safe *because* of the scoping above — the generic keys a lower bar would otherwise admit now sit outside the swapped resource and are filtered before classification.
- **Removed the query-strip fallback** (the earlier same-day step): now that a path candidate's duplicated identity is reconciled from the sibling's own state (`rewriteCorrelatedQuery`), an id left un-reconciled is genuinely incoherent and is DROPPED, not probed on a query-stripped clean path (which tested a different url than the user reaches and only produced false positives). `stripUrlQuery` removed; config `clientRoutingQueryStripFallback` renamed `clientRoutingPathCoherence` (it now gates rewrite + drop).
- **Net on ejoy** (expected, pending a live run): the paid-lesson `1030 → 1032` IDOR is now reachable (authz passes on scoped `lock`; the rewrite forges the real `?path=…/lessons/1032/<h2>.json`), and the nav/section-swap FPs (`37 → 45/73/29`, `help → dictation`, …) are dropped at the authz gate (their only relevant key, `user`, is out of scope).
- **Effect/regressions**: new `test/responseEvaluate.test.ts` cases (`scopeDiffsToResource`: nav `user` dropped, `lesson.lock` kept, top-level swap keeps all); `test/AnalysisPipeline.test.ts` + `test/AblationPipeline.test.ts` + `test/correlatedQuery.test.ts` + `test/utils.test.ts` green; typecheck clean. Decision-logic change (authz gate + threshold) → a `recheckFindings` on the 4 reference sites is owed before trusting it there; the stored-`authz_diff` check above is the offline evidence it does not drop any of them.

## 2026-11-20 12:10 — analysis: a candidate swaps a RESOURCE IDENTITY, not one token (finds ejoy's leaked-capability IDOR)

Reframes the client-routing path candidate from "change one URL token" to "swap one sibling resource's identity", which can span more than one token when the url duplicates that identity — and in doing so detects ejoy's real paid-lesson IDOR the previous coherence-strip was (correctly) hiding behind a clean path.

- **The finding**: ejoy's lesson is addressed both by `/app/courses/37/314/<id>` AND by an opaque per-lesson capability `?path=cp/…/lessons/<id>/<hash>.json` (the content is fetched from the latter). The free user's React state carries EVERY lesson's own `path` — hash included — on its sibling node, **including paid ones** (`lock:true`: lesson 1032's `path = …/lessons/1032/be93….json` sits in the state of a user who only owns the free lessons). That leaked capability is the IDOR.
- **Why it was missed**: candidate generation swaps one segment (`1030 → 1032`) but `spliceSegment` keeps the stale `?path=…/1030/…`, an incoherent url that renders the original lesson; the earlier coherence-strip then probed the clean `/courses/37/314/1032`, which can't fetch content without the hash → rejected. So the true positive was invisible.
- **What changed**: new `rewriteCorrelatedQuery` (`correlatedQuery.ts`), run FIRST in `evaluateClientRoutingPathCandidate`: a query value that both embeds the swapped id AND equals a leaf of the reference node is replaced with that SAME leaf from the candidate (sibling) node — so `?path=` is rewritten to lesson 1032's own `lesson.path`, building the real paid-lesson url the probe can reach. It is the client-routing analog of what the HTTP forge already does (forge the sibling's request from leaked sibling state). **No new candidates** — one sibling, one probe; it only reconciles the existing candidate's url (no combinatorial fan-out). It fires only when the identity is genuinely duplicated (query value equals a node leaf); otherwise a no-op. When nothing correlates (ejoy's courseId `37 → 32`: `?path=` carries a lesson path absent from the course node), the existing coherence-strip takes over (clean path → not-found → rejected), so the courseId Frankenstein FP stays fixed.
- **Docs**: the conceptual shift ("one token" → "one resource identity, possibly >1 token") is written into [docs/analysis.md](docs/analysis.md) (step 2 + step 6) and `.claude/rules/analysis.md`.
- **Effect/regressions**: new `test/correlatedQuery.test.ts` (the ejoy lesson rewrite, the courseId no-op, malformed input); `test/AnalysisPipeline.test.ts` + `test/utils.test.ts` green; typecheck clean. Decision-logic change (can ADD a true-positive finding), gated by the same `clientRoutingQueryStripFallback` kill switch; a `recheckFindings` on the 4 reference sites is owed before trusting it there (the rewrite is a no-op unless a query value equals a node leaf, which none of the reference-site candidates hit).

## 2026-11-20 11:20 — analysis: drop incoherent client-routing path candidates (ejoy courseId false positives)

ejoy flagged ~40 client-routing "IDOR" findings of the form `37 → <other courseId>` on the lesson page `/app/courses/37/314/1030?path=cp/course/live/37/lessons/1030/<hash>.json`, the mutated page visibly identical to the original — false positives the content guard did not stop. Root cause: the candidate url is INCOHERENT. `spliceSegment` swaps the courseId in the PATH (`37 → 32`) but re-attaches the reference's query, which still carries the old courseId inside `?path=…/live/37/lessons/…`. The lesson content is driven by `?path=` (still course 37), while the route says course 32, so the SPA renders a Frankenstein page — course-32 chrome (sidebar/breadcrumb/title) around course-37 content. It differs from the reference by the course-level chrome, which the inert guard's value masking can't neutralise (the chrome differs by course NAME, not by the masked number `37`/`32`), so it is kept. `urlCarriesValue` never caught the incoherence either — it matches only whole segments / whole param values, never a value embedded inside a param's own path.

- **What changed**: `evaluateClientRoutingPathCandidate` now checks coherence BEFORE probing (replacing the retry-on-rejection fallback added earlier the same day). New `urlEmbedsValue` (utils): whether the reference value appears as a bounded token ANYWHERE in the url, decoded — including inside `?path=`. When it lingers, the one-segment swap is incoherent, so the candidate is probed on the query-stripped clean path (the SPA infers its params from it) instead of the incoherent url; if the old value STILL lingers after stripping (it sits in another path segment), the candidate can't be made coherent and is dropped. The clean path makes a sibling lesson (`1030 → 1031`) a real test and an incoherent course swap (`/courses/32/314/1030`, unit 314 ∉ course 32) render not-found → rejected. Everything downstream records the stripped `confirmedUrl`. Still behind `config.analysis.clientRoutingQueryStripFallback`.
- **Effect/regressions**: new `test/utils.test.ts` cases (`urlEmbedsValue` boundary-awareness + the ejoy incoherent url); `test/AnalysisPipeline.test.ts` green; typecheck clean. This only ever drops or re-routes candidates whose url was self-contradictory — a coherent path swap (no lingering value) is probed exactly as before.

## 2026-11-20 10:35 — ablation: apply the param/segment blacklists (same analysis rules as the main pipeline)

The ablation applied the `maxSegmentMatches` caps but NOT the param/segment name blacklists, so pagination controls it should never mutate slipped through — ejoy's `curPage` changes were flagged as ablation vulnerabilities (a pagination param is not an object reference; swapping it changes how much of your own data returns, never whose). The ablation is meant to share every analysis rule with the main pipeline, differing ONLY in using JSON siblings instead of React ones.

- **What changed**: `AblationPipeline` candidate generation now applies the same two blacklists as `candidateGenerator` — a query param whose name (or a token of it, via `paramNameBlacklisted`) is in `config.analysis.paramBlacklist` is never mutated (`curPage` → token `page`), and a path segment whose value is in `segmentBlacklist` is never mutated nor used as a replacement value. `AblationPipelineOptions` gained `paramBlacklist`/`segmentBlacklist`, threaded from config in buildExplorer, runAnalysisFromDb and runAblationFromDb.
- **Effect/regressions**: new `test/AblationPipeline.test.ts` case (a `curPage` candidate is flagged with no blacklist, dropped with the exact name AND with the tokenized `page`); the suite's other 8 tests green; typecheck clean. This only ever DROPS ablation candidates (pagination/section params that were always FPs), so it cannot lose a real ablation finding.

## 2026-11-20 10:10 — analysis: client-routing path fallback with the query stripped (SPA infers params)

A client-routing PATH candidate keeps the reference URL's query, because `spliceSegment` re-attaches it. For a route that infers its params from the PATH, swapping only the id makes an INCOHERENT url: ejoy's lesson is `/app/courses/37/314/<id>?path=cp/…/lessons/<id>/<hash>.json`, so the `1030 → 1031` candidate becomes `/app/courses/37/314/1031?path=…/lessons/1030/<hash>.json` — path says 1031, `path=` still points at lesson 1030's content. The probe then tests a page that renders the ORIGINAL lesson (or errors), never the sibling, so a real lesson-id IDOR can't surface.

- **What changed**: `CandidateEvaluator.evaluateClientRoutingPathCandidate` now, when the primary probe REJECTS a high-suspicion path candidate (authz already fired) and the candidate URL carries a query, retries ONCE against the clean path (`stripUrlQuery`, new in utils). The SPA then infers the params from the path (confirmed manually on ejoy: `/app/courses/37/314/1032` renders without the query). If the stripped route confirms, everything downstream — the content-novelty guard, the finding id, the recorded row and the reproduction script — uses the stripped URL (`confirmedUrl`), so a finding reflects the url that actually leaked. One extra navigation per rejected high-suspicion path candidate; behind `config.analysis.clientRoutingQueryStripFallback` (default on, kill switch).
- **Scope**: path candidates only (a query-param candidate mutates a single param — stripping the whole query is meaningless there). The lesson page is a pure client navigation (0 http_events for the page url, 1 crawl_state; the only HTTP event is the `_next/data/.../1030.json` XHR, which returns `{}`), so this is the only path by which a lesson-id swap can be probed.
- **Note on ejoy specifically**: even with this, ejoy's lesson content is addressed by an opaque per-lesson hash in `?path=…/<hash>.json`, not by the numeric id — so swapping `1030 → 1031` on the clean path still won't reach 1031's content without 1031's hash (a capability URL, not a classic numeric IDOR). The fallback is the general fix for path-inferring SPAs; it does not manufacture a finding where the site is not actually vulnerable.
- **Effect/regressions**: new `test/utils.test.ts` (`stripUrlQuery`); `test/AnalysisPipeline.test.ts` green; typecheck clean. This is a decision-logic change that can ADD findings (a rejected candidate may now confirm via the clean path), so a `recheckFindings` on the 4 reference sites is owed before trusting it there — the fallback only runs on ALREADY-rejected high-suspicion candidates and re-imposes the same content/not-found guards, so a confirmed one is a real leak, not a loosened bar.

## 2026-11-20 09:30 — analysis: two false-positive fixes (empty-data forge, tokenized param blacklist)

Two FP classes found while reviewing ejoy-english's findings. Both are candidate-evaluation / generation guards, no crawler change.

- **Empty-data guard (always on, HTTP main + ablation).** A forged request that comes back with no actual data — `{}`, `[]`, or an all-empty wrapper like ejoy's `search-new` → `{"data":{"data":[],"total":0}}`, and the ablation's `api/courses/progress/42` → `{}` — leaked nothing, however much it "differs" from the reference, so it is never a finding. New `isEmptyJsonResponse` (analysis/responseEvaluate.ts): parses the body and treats it as empty when every array is empty and every remaining scalar sits under a narrow metadata key (`total`/`count`/`size`/`status`/…); an id/name/title/slug or any non-empty array is content, so a real record is never called empty. Applied right after the error-status guard in both `candidateEvaluator` (HTTP path) and `AblationPipeline`. Drops only on positive evidence: a non-JSON body (an HTML 404) returns false (kept). Note: ejoy's `search-new?size=…` ablation FPs are a DIFFERENT class (a real-data response that differs only by a pagination param) — the ablation deliberately lacks the main pipeline's param-name blacklist, so those remain, as the studied weakness.
- **Tokenized param blacklist (candidate generation).** `config.analysis.paramBlacklist` now matches a query param by TOKEN as well as by exact name (`paramNameBlacklisted` + `tokenizeParamName`, splitting camelCase / snake / kebab / letter-digit): a compound bound like `maxLevel` / `minScore` / `pageSize` is dropped on its `max` / `min` / `page` token, not only an exact `limit`. Added `max`, `min` to the default list. Caveat baked into the comments: a token that is also a common English word (`order`, `page`, `size`) will drop a real-reference param containing it (`orderId`, `pageId`) — so the list stays made of bound/pagination words. No reference-site TP param is hit (pimsleur's `?id=` tokenizes to `id`, not blacklisted; busuu/lingualeo TPs are path segments, never param-gated).
- **Effect/regressions**: new cases in `test/responseEvaluate.test.ts` (`isEmptyJsonResponse`) and `test/candidateGenerator.test.ts` (`tokenizeParamName`/`paramNameBlacklisted`); `test/AblationPipeline.test.ts`, `test/findings.test.ts` green; typecheck clean. Both are decision-logic changes (a generation filter + a content guard), so a `recheckFindings` on the 4 reference sites is owed before trusting them there — the guards only ever DROP (never add), and no reference TP returns empty data or sits under a tokenized bound param, so no loss is expected.

## 2026-11-20 08:56 — analysis: survive an auth refresh at t2 (entry-point gate + re-auth without re-crawl)

Phase 1 of letting a `runAnalysisFromDb` re-analysis (t2) outlive the captured (t1) session: re-login manually and re-point the forge at the fresh session, instead of re-crawling. Supersedes yesterday's (uncommitted) "re-logging in won't help, re-crawl" conclusion, which was only true while the forge replayed the stale captured auth. The common path (token never expired) is byte-identical to before.

- **Why the old pre-check was wrong as a trigger.** `checkAuthFresh` sampled previously-2xx JSON GETs and aborted on `>=2` now-403. But a `403` on a forged request is *ambiguous*: for a paid-resource IDOR it is the *correct* "no leak" answer (the error-status guard already treats it so). Sampling arbitrary endpoints (some of which may be paid resources the account can't reach) conflates "session dead" with "access correctly denied" — and using a per-forge 403 to re-authenticate risks a re-auth/re-forge loop.
- **Entry-point gate** (`checkEntryPointFresh`, replaces `checkAuthFresh`). The freshness signal now comes from the crawl's own entry point (`START_URL`, an internal *authenticated* page — a resource the user is unambiguously entitled to), decided once up front: re-render it and compare its live React `graph.fingerprint` to the fingerprint(s) captured at that URL at crawl time (`ReactStateStore.fingerprintsForUrl`). Match → alive; mismatch → login redirect → EXPIRED → abort (exit 2) pointing at `refreshAuth`. Structure only (not `reactContentKey`): the page's data legitimately drifts t1→t2, its structure collapses only on the login page. Conservative on missing evidence (no seed fp / no extension / app didn't mount → proceed).
- **Refresh without re-crawl** (`scripts/refreshAuth.ts` → `session_auth` → `applyAuthOverride`). On EXPIRED, `refreshAuth` opens the profile headed for a manual login (reusing the gate to confirm), harvests the fresh header-auth (`harvestSessionAuth`, headers in `config.analysis.volatileAuthHeaders`, default `authorization`), and stores a per-site `AuthOverride = { stripCookie:true, freshHeaders }` in the new `session_auth` table. The forge then overlays it: **stripCookie** drops the captured `Cookie` so `page.request.fetch` rides the context's fresh cookies (cookie-auth: busuu/lingualeo — the stale replayed cookie was the real blocker, confirmed by inspecting captured headers); **freshHeaders** replaces the stale bearer (header-auth: pimsleur). `applyAuthOverride` is pure and a no-op without an override, so a run that never expired is unchanged. `session_auth` is not wiped by `clearOnStart`; `refreshAuth` clears the site's `forged_requests` so no response forged under the dead session is reused. Only the HTTP forge needs it — client-routing probes navigate in the re-authenticated context already.
- **What changed**: new `src/analysis/authSession.ts` (`applyAuthOverride`, `harvestSessionAuth`), `src/db/SessionAuthStore.ts` (`session_auth`), `authFreshness.ts` rewritten to the gate, `ReactStateStore.fingerprintsForUrl`, `config.analysis.volatileAuthHeaders`, `authOverride` threaded `AnalysisPipeline`→`CandidateEvaluator`→forge, `runAnalysisFromDb` (gate + override + new abort message), new `scripts/refreshAuth.ts`.
- **Effect/regressions**: new `test/authSession.test.ts` (pure override + local-server end-to-end: stale→403, refreshed→200 for both bearer and cookie), `test/authFreshness.test.ts` (gate match/mismatch/missing-evidence), `test/SessionAuthStore.test.ts` green; typecheck clean. The fresh path is byte-identical (override undefined → forge unchanged), so no reference-count change is expected; a `recheckFindings` on the 4 sites is still owed to confirm, since the gate replaced the pre-check in `runAnalysisFromDb`. Phase 2 (merging an externally-captured DB + per-site multi-auth) is deliberately out of scope here.

## 2026-11-19 — analysis: client-routing content guards (React), error-status guard, auth-freshness pre-check

Three false-positive / correctness fixes found while re-examining promova's findings. None touches the crawler.

- **Client-routing content guards (the HTTP guards' long-missing twin).** The HTTP path already dropped a forge whose response was already-accessible (in `http_events`) or a duplicate of another finding; the client-routing path had NO content check at all. Added `reactContentKey` (analysis/reactFingerprint.ts): a key over a captured React state's STRUCTURE (`graph.fingerprint`) + its identifier-like DATA (the same `collectPreindexRows` the preindex uses). A micro-test confirmed the structural half alone is too coarse (it keys a page's type, not its instance), so both halves are needed. The verifier gained `captureReactContentKey` (a separate real navigation — a synthetic popstate often does not update a Next.js React tree — run only on already-accepted candidates, leaving the guarded accept/reject ladder untouched); `CandidateEvaluator` now drops a client-routing finding whose rendered state is (a) **already collected** (reactContentKey in any `react_states` row — e.g. promova's `/terms/press-center` renders the already-crawled `/press-center`) or (b) a **duplicate** of an earlier finding this run. React-read uses the extension, now also loaded by `runAnalysisFromDb`; absent it, the guard is simply inactive (key undefined → finding kept), never wrong. promova: 31 → 30, the 10 real sibling-lesson findings untouched (distinct data → distinct keys).
- **Error-status guard (always on, HTTP).** A forged request the server answered with 4xx/5xx (notably 401/403 "access denied") never reached the resource, so it is never a leak — dropped before recording. Catches two similar *error* bodies that would otherwise look like a match, and keeps an expired-token run honest.
- **Auth-freshness pre-check (`runAnalysisFromDb`).** A run on an expired token is meaningless: every forge is denied, or the URL-keyed forge cache serves stale authenticated responses from an earlier session. `checkAuthFresh` re-fetches a few previously-2xx JSON GETs; if ≥2 now return 401/403 it prints a loud warning (re-authenticate in the profile) and aborts (exit 2) instead of producing stale findings. Validated: promova now aborts (4/5 endpoints 401/403, token expired since capture). The end-of-crawl analysis never needs it (it runs in the just-authenticated session).
- **Scope note**: RAPIDOR targets unauthorized access to **paid/higher-privilege** resources in the same session, not other users' data (clarified in CLAUDE.md). promova's `/73 → /71` step swap (free `A1` → paid `A2`, status 200 when authenticated) is a genuine such finding, not a false positive — the manual 403 was only the expired token.
- **Effect/regressions**: `test/AnalysisPipeline.test.ts`, `test/reactFingerprint.test.ts` (new), `test/findings.test.ts`, `test/AblationPipeline.test.ts` green; typecheck clean. normalizeUrl's `_rsc` strip and these guards are decision-logic changes — a `recheckFindings` on the 4 reference sites is still owed before trusting them there.
