## 2026-11-20 09:30 — analysis: two false-positive fixes (empty-data forge, tokenized param blacklist)

Two FP classes found while reviewing ejoy-english's findings. Both are candidate-evaluation / generation guards, no crawler change.

- **Empty-data guard (always on, HTTP main + ablation).** A forged request that comes back with no actual data — `{}`, `[]`, or an all-empty wrapper like ejoy's `search-new` → `{"data":{"data":[],"total":0}}`, and the ablation's `api/courses/progress/42` → `{}` — leaked nothing, however much it "differs" from the reference, so it is never a finding. New `isEmptyJsonResponse` (analysis/responseEvaluate.ts): parses the body and treats it as empty when every array is empty and every remaining scalar sits under a narrow metadata key (`total`/`count`/`size`/`status`/…); an id/name/title/slug or any non-empty array is content, so a real record is never called empty. Applied right after the error-status guard in both `candidateEvaluator` (HTTP path) and `AblationPipeline`. Drops only on positive evidence: a non-JSON body (an HTML 404) returns false (kept). Note: ejoy's `search-new?size=…` ablation FPs are a DIFFERENT class (a real-data response that differs only by a pagination param) — the ablation deliberately lacks the main pipeline's param-name blacklist, so those remain, as the studied weakness.
- **Tokenized param blacklist (candidate generation).** `config.analysis.paramBlacklist` now matches a query param by TOKEN as well as by exact name (`paramNameBlacklisted` + `tokenizeParamName`, splitting camelCase / snake / kebab / letter-digit): a compound bound like `maxLevel` / `minScore` / `pageSize` is dropped on its `max` / `min` / `page` token, not only an exact `limit`. Added `max`, `min` to the default list. Caveat baked into the comments: a token that is also a common English word (`order`, `page`, `size`) will drop a real-reference param containing it (`orderId`, `pageId`) — so the list stays made of bound/pagination words. No reference-site TP param is hit (pimsleur's `?id=` tokenizes to `id`, not blacklisted; busuu/lingualeo TPs are path segments, never param-gated).
- **Effect/regressions**: new cases in `test/responseEvaluate.test.ts` (`isEmptyJsonResponse`) and `test/candidateGenerator.test.ts` (`tokenizeParamName`/`paramNameBlacklisted`); `test/AblationPipeline.test.ts`, `test/findings.test.ts` green; typecheck clean. Both are decision-logic changes (a generation filter + a content guard), so a `recheckFindings` on the 4 reference sites is owed before trusting them there — the guards only ever DROP (never add), and no reference TP returns empty data or sits under a tokenized bound param, so no loss is expected.

## 2026-11-20 08:56 — analysis: survive an auth refresh at t2 (entry-point gate + re-auth without re-crawl)

Phase 1 of letting a `runAnalysisFromDb` re-analysis (t2) outlive the captured (t1) session: re-login manually and re-point the forge at the fresh session, instead of re-crawling. Supersedes yesterday's (uncommitted) "re-logging in won't help, re-crawl" conclusion, which was only true while the forge replayed the stale captured auth. The common path (token never expired) is byte-identical to before.

- **Why the old pre-check was wrong as a trigger.** `checkAuthFresh` sampled previously-2xx JSON GETs and aborted on `>=2` now-403. But a `403` on a forged request is *ambiguous*: for a paid-resource IDOR it is the *correct* "no leak" answer (the error-status guard already treats it so). Sampling arbitrary endpoints (some of which may be paid resources the account can't reach) conflates "session dead" with "access correctly denied" — and using a per-forge 403 to re-authenticate risks a re-auth/re-forge loop.
- **Entry-point gate** (`checkEntryPointFresh`, replaces `checkAuthFresh`). The freshness signal now comes from the crawl's own entry point (`START_URL`, an internal *authenticated* page — a resource the user is unambiguously entitled to), decided once up front: re-render it and compare its live React `graph.fingerprint` to the fingerprint(s) captured at that URL at crawl time (`ReactStateStore.fingerprintsForUrl`). Match → alive; mismatch → login redirect → EXPIRED → abort (exit 2) pointing at `refreshAuth`. Structure only (not `reactContentKey`): the page's data legitimately drifts t1→t2, its structure collapses only on the login page. Conservative on missing evidence (no seed fp / no extension / app didn't mount → proceed).
- **Refresh without re-crawl** (`scripts/refreshAuth.ts` → `session_auth` → `applyAuthOverride`). On EXPIRED, `refreshAuth` opens the profile headed for a manual login (reusing the gate to confirm), harvests the fresh header-auth (`harvestSessionAuth`, headers in `config.analysis.volatileAuthHeaders`, default `authorization`), and stores a per-site `AuthOverride = { stripCookie:true, freshHeaders }` in the new `session_auth` table. The forge then overlays it: **stripCookie** drops the captured `Cookie` so `page.request.fetch` rides the context's fresh cookies (cookie-auth: busuu/lingualeo — the stale replayed cookie was the real blocker, confirmed by inspecting captured headers); **freshHeaders** replaces the stale bearer (header-auth: pimsleur). `applyAuthOverride` is pure and a no-op without an override, so a run that never expired is unchanged. `session_auth` is not wiped by `clearOnStart`; `refreshAuth` clears the site's `forged_requests` so no response forged under the dead session is reused. Only the HTTP forge needs it — client-routing probes navigate in the re-authenticated context already.
- **What changed**: new `src/analysis/authSession.ts` (`applyAuthOverride`, `harvestSessionAuth`), `src/db/SessionAuthStore.ts` (`session_auth`), `authFreshness.ts` rewritten to the gate, `ReactStateStore.fingerprintsForUrl`, `config.analysis.volatileAuthHeaders`, `authOverride` threaded `AnalysisPipeline`→`CandidateEvaluator`→forge, `runAnalysisFromDb` (gate + override + new abort message), new `scripts/refreshAuth.ts`.
- **Effect/regressions**: new `test/authSession.test.ts` (pure override + local-server end-to-end: stale→403, refreshed→200 for both bearer and cookie), `test/authFreshness.test.ts` (gate match/mismatch/missing-evidence), `test/SessionAuthStore.test.ts` green; typecheck clean. The fresh path is byte-identical (override undefined → forge unchanged), so no reference-count change is expected; a `recheckFindings` on the 4 sites is still owed to confirm, since the gate replaced the pre-check in `runAnalysisFromDb`. Phase 2 (merging an externally-captured DB + per-site multi-auth) is deliberately out of scope here.

## 2026-11-19 — analysis: client-routing content guards (React), error-status guard, auth-freshness pre-check

Three false-positive / correctness fixes found while re-examining promova's findings. None touches the crawler.

- **Client-routing content guards (the HTTP guards' long-missing twin).** The HTTP path already dropped a forge whose response was already-accessible (in `http_events`) or a duplicate of another finding; the client-routing path had NO content check at all. Added `reactContentKey` (analysis/reactFingerprint.ts): a key over a captured React state's STRUCTURE (`graph.fingerprint`) + its identifier-like DATA (the same `collectPreindexRows` the preindex uses). A micro-test confirmed the structural half alone is too coarse (it keys a page's type, not its instance), so both halves are needed. The verifier gained `captureReactContentKey` (a separate real navigation — a synthetic popstate often does not update a Next.js React tree — run only on already-accepted candidates, leaving the guarded accept/reject ladder untouched); `CandidateEvaluator` now drops a client-routing finding whose rendered state is (a) **already collected** (reactContentKey in any `react_states` row — e.g. promova's `/terms/press-center` renders the already-crawled `/press-center`) or (b) a **duplicate** of an earlier finding this run. React-read uses the extension, now also loaded by `runAnalysisFromDb`; absent it, the guard is simply inactive (key undefined → finding kept), never wrong. promova: 31 → 30, the 10 real sibling-lesson findings untouched (distinct data → distinct keys).
- **Error-status guard (always on, HTTP).** A forged request the server answered with 4xx/5xx (notably 401/403 "access denied") never reached the resource, so it is never a leak — dropped before recording. Catches two similar *error* bodies that would otherwise look like a match, and keeps an expired-token run honest.
- **Auth-freshness pre-check (`runAnalysisFromDb`).** A run on an expired token is meaningless: every forge is denied, or the URL-keyed forge cache serves stale authenticated responses from an earlier session. `checkAuthFresh` re-fetches a few previously-2xx JSON GETs; if ≥2 now return 401/403 it prints a loud warning (re-authenticate in the profile) and aborts (exit 2) instead of producing stale findings. Validated: promova now aborts (4/5 endpoints 401/403, token expired since capture). The end-of-crawl analysis never needs it (it runs in the just-authenticated session).
- **Scope note**: RAPIDOR targets unauthorized access to **paid/higher-privilege** resources in the same session, not other users' data (clarified in CLAUDE.md). promova's `/73 → /71` step swap (free `A1` → paid `A2`, status 200 when authenticated) is a genuine such finding, not a false positive — the manual 403 was only the expired token.
- **Effect/regressions**: `test/AnalysisPipeline.test.ts`, `test/reactFingerprint.test.ts` (new), `test/findings.test.ts`, `test/AblationPipeline.test.ts` green; typecheck clean. normalizeUrl's `_rsc` strip and these guards are decision-logic changes — a `recheckFindings` on the 4 reference sites is still owed before trusting them there.

## 2026-11-19 — analysis: tame the ablation's combinatorial explosion (carrier-cap, volatile params, per-site forge budget)

Re-running promova end-to-end surfaced that the ablation generates **~4.8M distinct forge GETs** (vs the main pipeline's ~12.5k) and OOM'd / would have DoS'd the site. Measured the drivers and fixed them; the explosion itself is genuine (a result for the paper), but it is now bounded and flagged instead of fatal.

- **Why it explodes**: candidate count ≈ Σ over matched values of (distinct URLs carrying the value as a segment) × (bodies it matches) × (array siblings). The amplifier is **low-entropy values** — tiny integers like `"1"` (a page number / version / flag in 3222 distinct URLs) that coincidentally sit under an id-like key in a few JSON bodies. The main pipeline filters these for free (such a value saturates the rendered DOM, > `maxSegmentMatches` React nodes, and is skipped); the sparser JSON corpus holds it in only ~28 bodies, so the hit-count cap never fires. React state is an implicit saliency prior the HTTP-JSON ablation lacks.
- **What changed**:
  - **Carrier-cap** (the missing `maxSegmentMatches` analog): the ablation now also skips a value carried by more than `maxSegmentMatches` *distinct request URLs*. On promova, dropping 7 such values (`0,1,3,6,8,11,1080`) cut candidates **12×** (4.8M → 392k). Plus the existing **hit-cap** (`hits > maxSegmentMatches`).
  - **Volatile-param canonicalization**: `normalizeUrl` now strips Next.js RSC `_rsc` tokens (a module const in `findings.ts`, like `PREINDEXED_KEYS`), so two captures of one request differing only by the token canonicalize equal. Barely dents the ablation (0.7%) but **de-duplicates the main pipeline's findings** — promova's main http candidates dropped 8184 → 1986 (−76%), collapsing ~20 duplicate `_rsc` findings. The forged request still carries the original's params (an RSC request stays comparable).
  - **Per-site forge budget** (`config.analysis.maxGeneratedRequests`, 10k, main AND ablation): generation early-aborts the moment distinct forges exceed it and the site is recorded **infeasible** (new `infeasible` column on `analysis_stats` / `ablation_stats`) instead of dispatched — a memory bound (never materialises millions), a time bound (~10k × 250ms / 3 ≈ a ~45-min per-site budget) and an ethical one (GET-only, but millions of live requests is a DoS). promova's ablation → infeasible even with the caps (still ~118k); its main (~6.4k after the `_rsc` dedup) stays feasible.
  - Removed the earlier `maxJsonSiblingsPerMatch` idea: siblings are not the driver (arrays are <50), so the budget + caps suffice and the config stays lean.
- **Effect/regressions**: `test/AblationPipeline.test.ts`, `test/findings.test.ts` (new `_rsc` case), `test/jsonMatchFinder.test.ts`, `test/HttpEventStore.test.ts` green; typecheck clean. `normalizeUrl` is a decision-logic change (history filter + finding dedup), so a `recheckFindings` on the 4 reference sites is still owed before this is trusted on them.

## 2026-11-19 11:54 — fix: analysis loads http_events without materialising all response bodies (OOM)

A completed promova crawl (17,426 http_events, ~568 MB of response bodies) then OOM'd in analysis: `httpEventStore.listBySite` did `SELECT *`, pulling every body into one array (~1.2 GB in JS, measured), and `primeResponseHistory` parsed all 568 MB on top of that — past Node's 4,144 MB heap. busuu never hit this (8,618 events, only 4 MB of bodies).

- **Why**: make analysis memory scale with the number of events, not the total body bytes.
- **What changed**: `HttpEventStore` gained `listMetaBySite` (events without `response_body`), `getResponseBody({site,id})` (lazy single body) and `forEachResponse` (streams bodies one row at a time via `.iterate()`). The main pipeline and `recheckRunner` now list metadata only, fetch a reference body lazily per candidate (bounded by the forge concurrency), and build the response-history key set by streaming. `run*FromDb`/`runDemo` count events instead of loading them for a log line. Ablation still uses `listBySite` (it needs every JSON body for its preindex) and stays off by default.
- **Effect/regressions**: promova's data-load + history-prime drops from ~1.2 GB retained (RSS 1.5 GB) to ~90 MB (RSS ~300 MB), measured. No change to what gets flagged — `test/AnalysisPipeline.test.ts`, `test/AblationPipeline.test.ts`, `test/HttpEventStore.test.ts` green; typecheck clean.

## 2026-11-19 — fix: NetworkObserver no longer buffers every captured request in memory (OOM on long crawls)

A long headed Promova crawl died with `JavaScript heap out of memory`. Cause: `NetworkObserver.handle()` pushed every same-site request — each with its response body (up to `maxBodyBytes`, default 200 KB) — into an in-memory `requests[]` that was never cleared and lived for the whole per-site exploration, *in addition to* persisting each one to SQLite. Nothing ever reads that array in production (only `stats` is consumed, for one log line; dedup is the store's job via `UNIQUE(site, fingerprint)` + `ON CONFLICT seen_count+1`, not the array's). On a site that loads ~140 requests per page, across a deep crawl with `tabsPerSite: 10`, it grew to GBs and blew past Node's default heap.

- **Why**: the crash was the Node/V8 heap (the crawler process), not the browser — headed just let the crawl run long enough to hit it.
- **What changed**: `handle()` now records straight to the store when one is present (always, in production) and keeps nothing in memory; the `requests[]` buffer is retained only as the fallback sink when there is no store (store-less unit tests inspect it directly). No behaviour change to what reaches `http_events`.
- **Effect/regressions**: unbounded per-site memory growth removed. `test/NetworkObserver.test.ts` + `test/NetworkObserverHooks.test.ts` 6/6 green; typecheck clean. Orthogonal mitigations still available if needed: `NODE_OPTIONS=--max-old-space-size=…` and a lower `tabsPerSite`.

## 2026-11-19 — analysis: two always-on HTTP content-identity guards + ablation in runAnalysisFromDb

Two false-positive/duplicate vectors on the HTTP detection path were unguarded: findings were deduped only by candidate identity (`candidateValue+nodeId+method+url`), never by response content, and the forged response was only ever compared against the reference event — never against the rest of the crawler's own `http_events`.

- **Why**: cleaner precision for the 17-app evaluation — do not count the same leak twice, and do not flag data the user can already reach.
- **What changed**: new `responseEvaluate.canonicalResponseKey` (status + body, byte-equal or key-order-independent JSON — the equivalence `isIdenticalResponse` already uses). Before recording an HTTP finding, `CandidateEvaluator` (and, identically, `AblationPipeline`) now applies, always on, no config knob: (1) **already-accessible-data** — drop a forge whose response equals one the crawler collected legitimately at a *different* URL (the reference event's own response is excluded: that is the server-ignored-value case handled by `isIdenticalResponse`); (2) **cross-candidate dedup** — two swaps forging a byte/JSON-identical response are one leak, recorded once. A missing body yields no key → finding kept (drop only on positive evidence). Both are HTTP-only (client-routing findings carry no server-response evidence). Also: `scripts/runAnalysisFromDb.ts` now runs the ablation pass too when `ABLATION_MODE=true` (it previously instantiated only `AnalysisPipeline`), and the ablation got the same `overwriteFindingsPerSite` re-run hygiene.
- **Effect/regressions**: no reference finding can be lost — pimsleur (4), lingualeo (17) and babbel (0) are all client-routing, which the guards never touch; busuu is the only site with HTTP findings (69) and both guards drop **0** of them (verified offline two ways: all 69 forged bodies are distinct, none appears in `http_events`), so busuu stays at **73**. `test/AnalysisPipeline.test.ts` + `test/AblationPipeline.test.ts` 16/16 green; typecheck clean.
