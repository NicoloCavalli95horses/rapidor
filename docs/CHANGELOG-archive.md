## 2026-11-22 15:30 — safety: block external protocol handlers (mailto:/tel:/sms:/webcal:/zoommtg:/…)

Clicking an `example@gmail.com`-style link (or any `mailto:`/`tel:`/`sms:`/`webcal:`/`zoommtg:`/app-deep-link) made Chromium hand the URL to the OS, launching an external app and pulling the crawler out of the page. These links carry no paid resource to probe, so they are pure noise and risk.

- **Why:** keep the crawler inside the page under exploration; never spawn external processes.
- **What changed:** new `allowedLinkSchemes` allowlist (default `http, https, javascript, about`). Two layers: (1) `ClickableExtractor` drops any clickable whose `href` uses a non-allowlisted scheme, so it is never offered; (2) a capture-phase in-page guard (`blockExternalProtocols`, installed by `ActionExecutor` via `addInitScript` + a one-off evaluate) `preventDefault`s clicks on such anchors, covering cases that slip past extraction (wrapper clicks, dynamically-set hrefs). Shared `linkScheme`/`isExternalAppLink` helpers in `utils`.
- **Effect:** external-app handoffs no longer happen during exploration. New tests in `ClickableExtractor`, `ActionExecutor`, `utils`; full suite green. No change to geometry, fingerprints, or the HTTP/analysis path.

**Severity: high — cross-site contamination that invalidated multi-site analyses.** `preindexed_values` has no `site` column, and `findByValue`/`countByValue` filtered only `WHERE value = ?`. But the DB holds many sites at once (`db.overwriteExistingDomain` wipes only the domain being re-crawled, never the others), so a value lookup returned EVERY site's nodes. Analysing celpipsimulator, its `/blog?_rsc=` segment `blog` matched **babbel's** footer `blog` link (the value `blog` was indexed by 4 sites: arabicroad 2, lingualeo 40, babbel 14, celpip 10) and forged celpipsimulator's `/privacy` from babbel's sibling — a cross-site false positive whose very motivation showed babbel URLs (`about.babbel.com`, "Inside Babbel").

- **Both lookups are now site-scoped** (`PreindexedValueStore.findByValue`/`countByValue` take `{ value, site }`): `WHERE value = ? AND state_id IN (SELECT id FROM react_states WHERE site = ?)`. Via the state's own site (state_id → react_states.site), so it is correct on an existing DB with no migration/backfill. New `idx_react_states_site` indexes the subquery (hot path during candidate generation). `candidateGenerator.findUrlCandidates` now takes `site`; `AnalysisPipeline` passes it at both call sites.
- **Effect**: verified on the live DB — `findByValue({ value:'blog', site:'www.celpipsimulator.com' })` returns celpip's 10 rows, not the 66 across 4 sites; babbel's footer no longer leaks in, so the celpip FP is gone. Only ever REMOVES wrong-site candidates; a site's own candidates are unchanged.
- **Caveat**: any finding in a shared DB produced before this fix may be cross-contaminated — re-run `runAnalysisFromDb` per site (the capture data is fine; only candidate generation was wrong). A finding whose motivation references another site's data was this bug.
- Tests: `PreindexedValueStore.test.ts` rewritten site-aware + a dedicated cross-site isolation case; `candidateGenerator.test.ts` updated. 19/19 in the two files, typecheck clean.

## 2026-11-20 17:15 — design: explore ONE deep target page; retry the stage-3 client-routing escalation

Two coupled changes, both driven by how noisy these language-learning SPAs are to crawl neutrally.

**Design shift — a single, manually-chosen target page explored deeply, not a wide shallow sweep.** A neutral seed wastes the 45-min budget wandering chrome/sections and never reaches the deep lesson/exercise flow where the IDORs live (busuu's `objective_<uuid>` sits ~3 clicks below the timeline). New defaults encode the workflow:
- `maxDepth` **3 → 4** (headroom for a lesson→start→exercise flow, with margin for an intermediate step).
- `ignoreClickablesWithin` default **`['nav','footer']`** (was `[]`): keep the crawler on the target page by not clicking navigation/footer chrome. **`header` is deliberately NOT included** — busuu renders its lesson cards (the real targets) inside a `<header>`, so ignoring it would make them unreachable (the same header-is-content trap as the domZone filter). This is what the earlier busuu run hit: `header` was still blacklisted, the lesson cards were never clicked, and the crawl stayed on one URL.
- Combines with `randomizeClickOrder` (already on) so the deep exploration samples the whole clickable set.

**Stage-3 client-routing retry** (`config.analysis.clientRoutingEscalationAttempts`, default **2**). The strict stage-3 full-navigation escalation (`confirmByFullNavigation`) — the costly real-load confirmation that decides for ejoy-class Next.js routes — was **single-shot**, while the cheap pushState probe already retried 3×. A single real load of a fetch-gated route (ejoy's lessons fetch their content by id over XHR) can snapshot an *incomplete* render and read as a false NEGATIVE, flipping which paid siblings surface run-to-run (ejoy's 4 locked lessons 1032/1033/1034/1035: 2 found per run, but a different 2). Now retried on a **flaky** reject only — capture failed / inert / not-found; an ACCEPT (null) or a DETERMINISTIC redirect-away ends immediately (re-navigating can't change those). Split `confirmByFullNavigation` into a retry loop + `confirmByFullNavigationOnce`; the redirect-away reason is now a shared `REDIRECT_AWAY_PREFIX` constant. **Can only ever recover a finding, never lose one** (a genuine inert/not-found still rejects on the last attempt). Cost is bounded: the retry fires only on a high-suspicion candidate that reached stage 3 and got a negative — a small set — and the knob can be lowered to 1 on a huge site. Threaded through `AnalysisPipelineOptions` / `ClientRoutingVerifierOptions` / the three scripts.

Decision-logic change (owner-run `recheckFindings` on the 4 reference sites owed). Typecheck clean; `clientRouting` + `AnalysisPipeline` tests green.

## 2026-11-20 15:45 — exploration: try a state's clickables in random order (reach page-centre buttons)

On a large app a budget-bounded DFS never leaves the navigation: clickables are captured in DOM/reading order (nav/header first) and each is explored depth-first to exhaustion, so the 45min/depth-2 budget drains on chrome before the page-centre lesson buttons are ever clicked. That is why a fresh busuu crawl captured only 11 top-level URLs and no `.../objective_<uuid>/...` page — so candidate generation had no reference URL to propose the known objective-sibling IDORs from (the objective ids are in the React props but a client-routing path candidate needs a VISITED url carrying the value).

- **`config.randomizeClickOrder`** (default on): `DfsExplorer.visit` now iterates a per-tab random shuffle (`shuffled`, Fisher-Yates in utils) of the state's clickables instead of their capture order, so central buttons get an equal early chance within the budget.
- **No engine/multitab change needed** — the selection is already decentralized: a tab shuffles a COPY of `state.clickables` locally, and the synchronous `claim()` still guarantees per-`(state,element)` exclusivity between tabs. `claimable()`/restore are order-independent (restore replays the recorded `state.path`, not the try order), and element identity (tag+rect+text) does not depend on order. Threaded through `ExplorationLimits` → `buildExplorer`.
- Trade-off: a crawl is no longer repeatable run-to-run. (The disk config hardcodes it `true`; the comment still mentions a `RANDOMIZE_CLICKS` env override that was removed — harmless.) Complementary, already-present lever: `ignoreClickablesWithin` (default `[]`) can skip nav/footer chrome outright — but keep `<header>` OUT of it (busuu renders lesson content there).
- Tests: `shuffled` (permutation, no-mutate, edge cases) in `test/utils.test.ts`.

## 2026-11-20 15:10 — analysis: skip preindex matches inside navigation/footer DOM chrome (domZone)

The newer browser extension serializes each React node's nearest DOM element (`node.dom`) plus its `parent`, so candidate generation can now tell a value that came from the site's nav/footer furniture (never a user-scoped id) from a real resource id. A match whose React node sits inside a chrome zone is skipped — its candidates were pure noise.

- **New `domZone.ts`** (`domChromeZone`, `nodeChromeZone`, `zoneWalkDepthFor`). A node is chrome iff itself or an ancestor (walked via `node.parent`) is a `<nav>`/`<footer>`, `role="navigation"`/`"contentinfo"`, or carries a nav/footer/sidebar class TOKEN (bounded by separators, so `nav-top`/`navbar`/`sidebar`/`footer` hit but `clipboard` does not). **Deliberately NOT `<header>`/`<section>`/`role=banner`:** verified on a fresh busuu graph that busuu renders its objective-id cards — the real IDOR targets (`objective_<uuid>` siblings) — inside a `<header>`, so a header/section rule would drop true positives. On that graph the shipped rule marks 144/8028 nodes (1.8%), all genuine top-nav, and **0 objective-bearing nodes**.
- **Window scales with graph size** (`zoneWalkDepthFor` = `clamp(ceil(log2(nodeCount)), 3, 24)`). A big app nests a nav's descendants deep (busuu: observed depth 9, budget 13); a small app has shallow chrome, where a long walk would let a distant nav ancestor wrongly "contain" a deep content node. log2(nodeCount) tracks tree depth. Memoized per state (it is O(nodes)).
- **Integration** (`candidateGenerator.findUrlCandidates`, main pipeline only): skip a match when `nodeChromeZone` returns a zone; count it in the new `chromeSkipped` return field, aggregated + logged per site by `AnalysisPipeline` (no DB-schema change). Graceful: old captures without `dom` → `nodeChromeZone` returns null → no skip, so this only ever drops a match on positive evidence of chrome.
- **Not in the ablation**: the JSON-only path has no React node to locate in the DOM, so this is a React-pipeline-only filter (like the saliency the ablation lacks by design).
- Tests: `test/domZone.test.ts` (9 cases — tag/role/class, header-excluded, token-boundary, budget, cycle, size scaling). Candidate generation changed → needs a `runAnalysisFromDb busuu` once the new-extension crawl finishes to measure the end-to-end match/candidate reduction and confirm the busuu TPs survive (`recheckFindings`).

## 2026-11-20 14:05 — analysis: error-envelope guard + locale-param filter (Mondly FP reduction)

A depth-3 Mondly pass surfaced two FP classes. Both fixes are safe (no reference-site TP loss, verified against the stored data) and apply to the main HTTP pipeline AND the ablation (so the ablation keeps differing from the main ONLY in using JSON siblings).

- **Error-envelope guard** (`isErrorEnvelopeResponse`, responseEvaluate.ts; main + ablation, right after the empty-data guard). A forged 200 whose TOP-LEVEL JSON signals an error/denial — truthy `error` (bool `true`, non-zero number, non-empty string/object), `success:false`/`ok:false`, or `status:"error"/"fail"/"failure"` — reached nothing, even when real-looking fields sit beside the flag. The response-similarity check is purely RELATIVE (length/key-count ratios ≥ 0.45), so when both reference and forged are short two unrelated small bodies pass as "similar"; this is the absolute content check that catches an error stub. Why not the proposed blunt `<5 top-level keys` floor: 19 genuine busuu HTTP findings have `candKeys=2` and Mondly's own legit responses have 1–2 keys (`{"languages":[…]}`), so a key-count floor would drop real findings — top-level key count is a bad proxy (APIs wrap rich data under few keys). Measured effect on Mondly: 0 *additional* drops — the 17 `{"error":true}` bodies were already caught by the empty-data guard (`error` is a metadata key); this is hardening for multi-key error envelopes on other sites. 0/69 busuu HTTP findings wrongly flagged.
- **Locale-param filter** (`isLocaleParam`/`LOCALE_PARAM`, candidateGenerator.ts; main + ablation, beside the param blacklist). A locale / UI-language query param selects the response's REPRESENTATION (which language its texts come back in), not WHOSE resource it is — like a pagination param, swapping it returns the same resource rendered differently, a guaranteed non-finding (Mondly's `notification-preferences?mother_language=22` came back in Arabic/Thai/Korean/… → one FP per language). Matched by a REGEX, deliberately NOT a blacklist token: the bare token `language` would also drop `target_language`/`learning_language`, which in a language-learning app name the RESOURCE you study (possibly paid) — a real TP. The optional prefix set is only UI/native/mother-style, so `mother_language`/`ui_language`/`locale`/`lang` match while `target_language`/`language_id` stay mutable. Not a config knob — a semantic param-name fact, like `VOLATILE_PARAMS`. Measured effect on Mondly: removes the 5 `mother_language` findings at candidate generation. (`categories/N` path swaps and `languages?lv=1` are a different class, untouched — `lv` is ambiguous, not treated as locale.)
- Tests: `isErrorEnvelopeResponse` and `isLocaleParam` covered in their module tests (38/38 pass in the two files). Candidate generation changed → a full `runAnalysisFromDb mondly` re-run is needed to see the end-to-end effect (not run here; a Mondly pass may be in flight).

## 2026-11-20 13:00 — analysis: scope the authz gate to the swapped resource + lower the threshold (ejoy lesson IDOR vs nav FPs)

The authz gate classified the WHOLE component diff, so a sibling swap of a whole nav/layout component "passed" on a generic key sitting anywhere in it (ejoy's `37 → 45` swaps a menu item's `items.0.id` yet passed on the top-level `user` object) — while a real, focused entitlement diff missed because its sole signal scored just under threshold (ejoy's paid lesson `lock: false → true`, `whether lock` = 0.307 < 0.33). Two coupled changes fix both, verified safe against every reference finding's stored `authz_diff`.

- **Scope the diff to the swapped resource** (`scopeDiffsToResource`, responseEvaluate.ts; always on, in `CandidateEvaluator.authzGate`). Before classifying, keep only diffs under the swapped value's PARENT object (the resource the id names). A generic key elsewhere in a whole-component swap (`user`, `feature`) is dropped; an entitlement that is a sibling of / nested within the swapped id survives. Verified: ejoy nav `user` (top-level, swap `items.0.id`) → dropped; ejoy `lesson.lock` under `lesson.id`, pimsleur `miniLesson.isFree` under `miniLesson.id` → kept; busuu/lingualeo swap a TOP-LEVEL `id` (parent is root) so nothing is scoped out — lingualeo's `user`-VALUE finding survives. (React/main pipeline only; the ablation's JSON candidate path is element-relative and would need separate plumbing.)
- **Lower THRESHOLD 0.33 → 0.30** (authzClassifier.ts), applied at READ time (recomputed from the cached score), so no `CLASSIFIER_VERSION` bump and persisted scores stay valid. This catches ejoy's `lock` (0.307). It is only safe *because* of the scoping above — the generic keys a lower bar would otherwise admit now sit outside the swapped resource and are filtered before classification.
- **Removed the query-strip fallback** (the earlier same-day step): now that a path candidate's duplicated identity is reconciled from the sibling's own state (`rewriteCorrelatedQuery`), an id left un-reconciled is genuinely incoherent and is DROPPED, not probed on a query-stripped clean path (which tested a different url than the user reaches and only produced false positives). `stripUrlQuery` removed; config `clientRoutingQueryStripFallback` renamed `clientRoutingPathCoherence` (it now gates rewrite + drop).
- **Net on ejoy** (expected, pending a live run): the paid-lesson `1030 → 1032` IDOR is now reachable (authz passes on scoped `lock`; the rewrite forges the real `?path=…/lessons/1032/<h2>.json`), and the nav/section-swap FPs (`37 → 45/73/29`, `help → dictation`, …) are dropped at the authz gate (their only relevant key, `user`, is out of scope).
- **Effect/regressions**: new `test/responseEvaluate.test.ts` cases (`scopeDiffsToResource`: nav `user` dropped, `lesson.lock` kept, top-level swap keeps all); `test/AnalysisPipeline.test.ts` + `test/AblationPipeline.test.ts` + `test/correlatedQuery.test.ts` + `test/utils.test.ts` green; typecheck clean. Decision-logic change (authz gate + threshold) → a `recheckFindings` on the 4 reference sites is owed before trusting it there; the stored-`authz_diff` check above is the offline evidence it does not drop any of them.


## 2026-11-20 12:10 — analysis: a candidate swaps a RESOURCE IDENTITY, not one token (finds ejoy's leaked-capability IDOR)

Reframes the client-routing path candidate from "change one URL token" to "swap one sibling resource's identity", which can span more than one token when the url duplicates that identity — and in doing so detects ejoy's real paid-lesson IDOR the previous coherence-strip was (correctly) hiding behind a clean path.

- **The finding**: ejoy's lesson is addressed both by `/app/courses/37/314/<id>` AND by an opaque per-lesson capability `?path=cp/…/lessons/<id>/<hash>.json` (the content is fetched from the latter). The free user's React state carries EVERY lesson's own `path` — hash included — on its sibling node, **including paid ones** (`lock:true`: lesson 1032's `path = …/lessons/1032/be93….json` sits in the state of a user who only owns the free lessons). That leaked capability is the IDOR.
- **Why it was missed**: candidate generation swaps one segment (`1030 → 1032`) but `spliceSegment` keeps the stale `?path=…/1030/…`, an incoherent url that renders the original lesson; the earlier coherence-strip then probed the clean `/courses/37/314/1032`, which can't fetch content without the hash → rejected. So the true positive was invisible.
- **What changed**: new `rewriteCorrelatedQuery` (`correlatedQuery.ts`), run FIRST in `evaluateClientRoutingPathCandidate`: a query value that both embeds the swapped id AND equals a leaf of the reference node is replaced with that SAME leaf from the candidate (sibling) node — so `?path=` is rewritten to lesson 1032's own `lesson.path`, building the real paid-lesson url the probe can reach. It is the client-routing analog of what the HTTP forge already does (forge the sibling's request from leaked sibling state). **No new candidates** — one sibling, one probe; it only reconciles the existing candidate's url (no combinatorial fan-out). It fires only when the identity is genuinely duplicated (query value equals a node leaf); otherwise a no-op. When nothing correlates (ejoy's courseId `37 → 32`: `?path=` carries a lesson path absent from the course node), the existing coherence-strip takes over (clean path → not-found → rejected), so the courseId Frankenstein FP stays fixed.
- **Docs**: the conceptual shift ("one token" → "one resource identity, possibly >1 token") is written into [docs/analysis.md](docs/analysis.md) (step 2 + step 6) and `.claude/rules/analysis.md`.
- **Effect/regressions**: new `test/correlatedQuery.test.ts` (the ejoy lesson rewrite, the courseId no-op, malformed input); `test/AnalysisPipeline.test.ts` + `test/utils.test.ts` green; typecheck clean. Decision-logic change (can ADD a true-positive finding), gated by the same `clientRoutingQueryStripFallback` kill switch; a `recheckFindings` on the 4 reference sites is owed before trusting it there (the rewrite is a no-op unless a query value equals a node leaf, which none of the reference-site candidates hit).

## 2026-11-20 10:10 — analysis: client-routing path fallback with the query stripped (SPA infers params)

A client-routing PATH candidate keeps the reference URL's query, because `spliceSegment` re-attaches it. For a route that infers its params from the PATH, swapping only the id makes an INCOHERENT url: ejoy's lesson is `/app/courses/37/314/<id>?path=cp/…/lessons/<id>/<hash>.json`, so the `1030 → 1031` candidate becomes `/app/courses/37/314/1031?path=…/lessons/1030/<hash>.json` — path says 1031, `path=` still points at lesson 1030's content. The probe then tests a page that renders the ORIGINAL lesson (or errors), never the sibling, so a real lesson-id IDOR can't surface.

- **What changed**: `CandidateEvaluator.evaluateClientRoutingPathCandidate` now, when the primary probe REJECTS a high-suspicion path candidate (authz already fired) and the candidate URL carries a query, retries ONCE against the clean path (`stripUrlQuery`, new in utils). The SPA then infers the params from the path (confirmed manually on ejoy: `/app/courses/37/314/1032` renders without the query). If the stripped route confirms, everything downstream — the content-novelty guard, the finding id, the recorded row and the reproduction script — uses the stripped URL (`confirmedUrl`), so a finding reflects the url that actually leaked. One extra navigation per rejected high-suspicion path candidate; behind `config.analysis.clientRoutingQueryStripFallback` (default on, kill switch).
- **Scope**: path candidates only (a query-param candidate mutates a single param — stripping the whole query is meaningless there). The lesson page is a pure client navigation (0 http_events for the page url, 1 crawl_state; the only HTTP event is the `_next/data/.../1030.json` XHR, which returns `{}`), so this is the only path by which a lesson-id swap can be probed.

The fallback is the general fix for path-inferring SPAs; it does not manufacture a finding where the site is not actually vulnerable.
- **Effect/regressions**: new `test/utils.test.ts` (`stripUrlQuery`); `test/AnalysisPipeline.test.ts` green; typecheck clean. This is a decision-logic change that can ADD findings (a rejected candidate may now confirm via the clean path), so a `recheckFindings` on the 4 reference sites is owed before trusting it there — the fallback only runs on ALREADY-rejected high-suspicion candidates and re-imposes the same content/not-found guards, so a confirmed one is a real leak, not a loosened bar.

## 2026-11-20 09:30 — analysis: two false-positive fixes (empty-data forge, tokenized param blacklist)

Two FP classes found while reviewing ejoy-english's findings. Both are candidate-evaluation / generation guards, no crawler change.

- **Empty-data guard (always on, HTTP main + ablation).** A forged request that comes back with no actual data — `{}`, `[]`, or an all-empty wrapper like ejoy's `search-new` → `{"data":{"data":[],"total":0}}`, and the ablation's `api/courses/progress/42` → `{}` — leaked nothing, however much it "differs" from the reference, so it is never a finding. New `isEmptyJsonResponse` (analysis/responseEvaluate.ts): parses the body and treats it as empty when every array is empty and every remaining scalar sits under a narrow metadata key (`total`/`count`/`size`/`status`/…); an id/name/title/slug or any non-empty array is content, so a real record is never called empty. Applied right after the error-status guard in both `candidateEvaluator` (HTTP path) and `AblationPipeline`. Drops only on positive evidence: a non-JSON body (an HTML 404) returns false (kept). Note: ejoy's `search-new?size=…` ablation FPs are a DIFFERENT class (a real-data response that differs only by a pagination param) — the ablation deliberately lacks the main pipeline's param-name blacklist, so those remain, as the studied weakness.
- **Tokenized param blacklist (candidate generation).** `config.analysis.paramBlacklist` now matches a query param by TOKEN as well as by exact name (`paramNameBlacklisted` + `tokenizeParamName`, splitting camelCase / snake / kebab / letter-digit): a compound bound like `maxLevel` / `minScore` / `pageSize` is dropped on its `max` / `min` / `page` token, not only an exact `limit`. Added `max`, `min` to the default list. Caveat baked into the comments: a token that is also a common English word (`order`, `page`, `size`) will drop a real-reference param containing it (`orderId`, `pageId`) — so the list stays made of bound/pagination words. ## 2026-11-13 14:09 — Client-routing: client digestion is the primary signal, network is a filter not a veto
A query param (or path segment) can be honoured entirely client-side, with no network traffic at all — the SPA reads the mutated value and renders a different resource. - **Network demoted to a filter.** A backend `2xx` for the candidate's own value, or a provable param read (`appReadParam`, query only), is corroboration strong enough to accept directly (skip the not-found screenshot). ## 2026-11-13 13:31 — Client-routing probe: network-truth confirm + adaptive DOM-settle window
Two changes make the client-side-routing probe miss fewer legitimate findings. Its DOM-mutation signal, whose timing follows a network-gated render, was the main source of flakiness — an earlier pimsleur run flagged 1 of 4 real IDORs for this reason.

- **A network `2xx` is a positive oracle, not just a veto.** A same-session response carrying the candidate value that the backend answers `2xx` while the probe renders the route is timing-robust evidence the app fetched and served the candidate resource — independent of whether the `MutationObserver` happened to catch the render. A candidate is now accepted on EITHER the DOM signal (`isUsingNewParams`) OR a network confirm; when the network confirms, the not-found screenshot guard is skipped (a `2xx` is not a not-found page). The retry loop also stops as soon as either signal is decisive, so a network-confirmed candidate no longer burns its remaining attempts.
- **Adaptive DOM-settle window** (`waitDomIdle`, [src/analysis/clientRouting.ts](src/analysis/clientRouting.ts)). The old window had a single bound acting as both floor and ceiling: it gave up at `minWaitMs` reporting "no reaction", so a render that only starts mutating after that bound (a slow, network-gated one) was missed, and a page that never went quiet could keep the probe waiting forever. It now has three bounds — floor (`minWaitMs`), DOM-quiet settle (`idleMs`), ceiling (`maxWaitMs`): nothing is reported settled until something actually mutates, so a late first render is still caught up to the ceiling, and the ceiling guarantees termination. Defaults retuned `3000/300` → `1000/300/4000` (lower floor so a quick reaction resolves sooner; a route that never reacts rides to the ceiling).
- New config bound `analysis.clientRoutingProbe.maxWaitMs`, threaded through `buildExplorer`, `scripts/runAnalysisFromDb.ts` and generated reproduction scripts. The not-found screenshot baseline settles on the ceiling (a visual baseline wants the fully-rendered route, not the floor).

Useful for diagnosing whether a filter (network truth, not-found screenshot, authz relevance, client-routing flakiness) is responsible for an unexpected count.

## 2026-11-13 11:23 — Client-routing false-positive guards: network truth + not-found screenshot baseline
A client-routing candidate is now flagged only when its route resolves to a real, distinct resource, not to an error page or the app's own not-found page. Two independent guards decide this, both scoped to client-side findings (an HTTP/JSON finding already has the server-response oracle):

- **Network truth.** While the probe renders the candidate route, the status of the request the app itself fires for the candidate value is recorded (`page.on('response')`, scoped by the value so the probe's own rollback fetch and analytics never count). Any `4xx` — the backend denied the swap or the resource does not exist — rejects the candidate; a `2xx` confirms it. Carried on `ClientRoutingResult.probeRequests` from `checkClientSideRouting`/`checkClientSideRoutingForPath`.
- **Not-found screenshot baseline** ([src/analysis/routeScreenshot.ts](src/analysis/routeScreenshot.ts)). When no backend call carries the value (a purely client-routed page), a screenshot of the candidate's render is compared (pngjs + pixelmatch) against the app's not-found page — calibrated once per route template by rendering a garbage id in the same slot. A render within `analysis.notFoundScreenshotMaxDiff` (default 0.02) of that baseline is rejected.
- New config knob `analysis.notFoundScreenshotMaxDiff`; `checkClientSideRoutingForPath` takes an optional `candidateValue` for the network scope.
- Measured on the captured busuu data (non-destructively, on a DB copy): 114 → 113 findings. The guards are correct but had little to remove here — busuu's client-routing findings are dominated by objective siblings whose backend genuinely answers `2xx` (kept) and by swaps between two valid navigation sections (`dashboard` ↔ `review`, which render real, different pages, so neither guard applies). Exactly one candidate, whose component fetch returned `4xx`, was removed. Datasets with client-side `404` renders benefit more; the navigation-word-swap false positives remain a separate, open problem.

## 2026-11-13 10:33 — Client-routing probe no longer crashes the whole analysis run
A client-routing probe (`checkClientSideRouting`/`checkClientSideRoutingForPath`) fires a synthetic `pushState` + `popstate`; for some candidate paths this makes the app's own router perform a REAL navigation, which destroys the page's execution context mid-`page.evaluate` (`Execution context was destroyed, most likely because of a navigation`). That rejection was unhandled: it propagated through `runWithConcurrency` and aborted the entire `runForSite` partway through the client-routing phase, losing `analysis_stats` and every not-yet-dispatched candidate (observed on busuu after all 51 HTTP findings had been persisted but before the client-routing ones).

- Both probes now run their script through a small `evaluateProbe` wrapper that catches any `page.evaluate` failure and returns a benign "the app did not react" result (`isUsingNewParams: false`). A destroyed context is never evidence of an authorization issue (the candidate was never confirmed to render), so dropping it is both safe and correct; the caller's queue already re-navigates to the page URL before the next probe.
- Defense in depth: `AnalysisPipeline` now wraps each dispatched candidate task so a single task throwing is logged and skipped instead of rejecting the whole bounded-concurrency pool — one bad candidate can no longer abort the run and discard the stats + remaining findings.

## 2026-11-13 10:27 — Candidate generation: drop generic-keyword segments + cache parsed React graphs
The analysis pipeline's pre-dispatch phase (turning captured URLs into IDOR candidates) took ~20 minutes of pure CPU on busuu before a single request was forged. Two compounding causes, both fixed; on the same data the phase now runs in ~2s instead of >115s (measured offline over 10,752 URLs).

- **Generic-keyword segments skipped.** `extractSegments` proposes every URL path segment as a "swap this value" candidate, filtered only by "does the value appear in the preindex". Generic segments that happen to also be React values — DOM tags / aria roles / category words like `svg` (21k nodes), `grammar` (3.7k), `vocabulary` (6.8k) — matched thousands of preindexed nodes each, and the fan-out (every match × its component siblings, across every URL sharing the word) exploded combinatorially and produced thousands of junk candidates. `AnalysisPipeline.findUrlCandidates` now skips a segment whose value appears in more than `config.analysis.maxSegmentMatches` preindexed nodes (default 300), via the new `PreindexedValueStore.countByValue` (an indexed `COUNT`, never materializing the rows). Real identifiers are far below the cap (busuu objective/exercise/activity ids appear 20–110 times), so the surviving candidates are unchanged — e.g. `objective_e43c5b7a` still yields exactly its 19 sibling candidates.
- **Parsed React graphs cached per run.** `findUrlCandidates` looked a state's graph up once per preindex match (tens of thousands of times) but there are only a couple hundred distinct graphs; it was re-running `JSON.parse` on the same ~150 KB strings repeatedly. `AnalysisPipeline` now memoizes `getById` for the duration of a `runForSite` (cleared at its start, so it never grows across sites or goes stale).
- New config knob `analysis.maxSegmentMatches` (threaded through `buildExplorer` and `scripts/runAnalysisFromDb.ts`). Note: this only addresses the pre-dispatch phase; the serialized client-routing probes remain a separate cost.

## 2026-11-13 09:06 — Tolerant restore: attempt budget for (state, element)
Restoring a state no longer abandons an element (or the branch below it) on the first failure. In SPA environments, an intermittent interstitial at page load (cookie banner, “welcome back” bottom sheet) may cover the target on one page load and disappear on the next: previously, this was enough to prune entire exploration branches, because the `(state, element)` pair was marked as explored *before* the attempt, and a single miss was final.

- `StateStore` transitions from destructive marking (`isExplored`/`markExplored`) to a `untried → inprogress → done` lifecycle using `claim()`/`release()`. `claim()` remains the synchronous and exclusive gate that prevents two tabs from clicking the same element; a `release(‘miss’)` puts the pair back in the queue for a new attempt on a future landing, as long as there is budget, then closes it (guaranteed termination). An exception during the click immediately closes the pair (actual error, not volatility): it is not retried.
- `DfsExplorer.step` now distinguishes between “element found and clicked” and “missed this time”; `claimable()` scans the frontier and retrieves a state only when *all* of its elements are `done`, skipping (without removing) states with only `inprogress` elements.
- New configuration parameter `restoreAttempts` (default 4): the number of times a pair is retried across multiple landings before being deemed unreachable.
- The set of clickable elements remains that of the original snapshot for each state: *new* clickable elements that appear only in variants (e.g., buttons in the intermittent modal) are treated as volatile and ignored; those already captured are simply re-located with tolerance.
