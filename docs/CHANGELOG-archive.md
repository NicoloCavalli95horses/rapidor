## 2026-11-19 — analysis: a re-run overwrites a site's findings instead of accumulating them

Re-running the analysis on already-captured DB data (`scripts/runAnalysisFromDb.ts`) is the cheap half of the loop — no re-crawl — and is how we'll iterate on false-positive reduction across the 17-app dataset without re-exploring each time. But the results were not actually overwritten: `VulnerabilityStore.record` is `INSERT OR IGNORE` on a deterministic finding id and nothing cleared the site's old rows, so `vulnerabilities` accumulated the **union** of every past run. A false positive the improved engine now correctly rejects stayed in the table forever (its row is never revisited) — the exact opposite of iterating toward fewer FPs.

- **Why**: make a re-analysis authoritative, so the final per-site findings always reflect the current engine.
- **What changed**: `AnalysisPipeline.runForSite` now calls `vulnerabilityStore.clearSite({ site })` before recording, gated by the new `config.analysis.overwriteFindingsPerSite` (default `true`; set it to `false` to restore the old additive behavior for diffing two engine versions). Wired through `buildExplorer.ts` (end-of-crawl) and `scripts/runAnalysisFromDb.ts`. Clears **only** `vulnerabilities`: the crawler/extension capture tables (`http_events`/`react_states`/`preindexed_values`/`crawl_states`) and the `forged_requests` forge cache (shared with the ablation) are untouched; `analysis_stats` already self-overwrites per site (`ON CONFLICT(site)`).
- **Effect/regressions**: no decision-logic change, so finding *counts* are unaffected (the reference recheck set is untouched). `test/AnalysisPipeline.test.ts` 9/9 green, typecheck clean. Each test uses a fresh DB, so `clearSite` on an empty site is a no-op there.

## 2026-11-18 15:05 — analysis: authz gate ties a key's relevance to its value's shape (kills busuu course-pack FPs)

The authz classifier flattened every diffed key/path/value and flagged a candidate if ANY token read like an entitlement. busuu's course-pack siblings exploited this: the sole sensitive key on **all 96** of them was `course_pack_paywall_1000` — not an access flag but the KEY of a cover-image URL (`courses.N.image_urls.course_pack_paywall_1000`, shown on the paywall screen), scored 0.342 purely on the word "paywall". Swapping a course-pack id rerenders the whole course *catalog*, so that image key is always in the diff and the gate always passed.

- **`assessAuthZ` now decides PER DIFF** ([authzClassifier.ts](src/analysis/authzClassifier.ts)), tying a key's relevance to the shape of its own value (`valueLooksLikeAsset`: contains `/`/`\`/`://`, a known file extension, or length > 60). A value that is itself an authz term (`tier: "free" → "premium"`) always counts — string enums are preserved — but a key that only *reads* like an entitlement is honoured only when its differing value is not a URL/asset.
- **No CLASSIFIER_VERSION bump**: embedding and normalization are unchanged (scores identical, `authz_classifications` cache stays valid); only the aggregation downstream of the cached scores changed.
- **Measured on the stored findings (DB simulation over `authz_diff`, the same set `recheckFindings` re-examines): busuu 196 → 100 (−96, exactly the course-pack cluster), ejoy 18 → 18, pimsleur 4 → 4, lingualeo 17 → 17, babbel 0 → 0 — zero regressions.** The 50 objective TPs survive (driven by real booleans `unlocked`/`isLessonUnlocked`). A live `recheckFindings` on the four reference sites is still the ratification step (authenticated profile, one site at a time).
- Tests: new `assessAuthZ` case (asset-URL-named key rejected, `tier` enum kept); authzClassifier 6/6, AnalysisPipeline 9/9, `tsc` green.

## 2026-11-18 14:20 — analysis: blacklist `depth` (busuu grammar_review FPs) + course-pack FP root cause

- **Added `depth` to `config.analysis.paramBlacklist`** ([config.ts](src/config.ts)). busuu's `grammar_review_*` endpoints take `?depth=2`; the preindex matched the bare value `2` and forged `depth=67, 68, 12538, …`, producing 6 client-routing FPs. `depth` is a traversal/recursion depth — a quantity control like `limit`/`offset`, not an object reference — so a differing response is expected and no guard can reject it. Same class as the `limit` fix. **Takes effect on the next candidate-generation pass** (`runAnalysisFromDb`); the 6 already-stored findings are unaffected until then. No reference-site TP swaps `depth`.
- **Root-caused the course-pack FP cluster (investigation only, no fix yet).** 96 of busuu's 168 HTTP findings are `course-pack/course_pack_*` sibling swaps, and **all 96** pass the authz gate on a single sensitive key: `course_pack_paywall_1000`. That is not an entitlement flag — it is the KEY of a cover-image URL (`courses.N.image_urls.course_pack_paywall_1000`, the image shown on the paywall screen), whose value is an `https://…jpg` string. The embedding classifier scores "course pack paywall 1000" at **0.342 ≥ 0.33** purely on the word "paywall" (sibling key `course_pack_thumbnail_500` scores 0.133 and is correctly rejected). The matched React node is the whole course *catalog* list, so swapping one pack id rerenders every course → every field differs → the paywall-image key is always in the diff → gate always passes. The real objective TPs are driven instead by genuine boolean flags (`unlocked`, `isLessonUnlocked`), so a "the differing value must be a boolean/enum, not a URL/asset string" rule in `assessAuthZ` would drop all 96 FPs without touching the 50 objective TPs — but that changes the justified classifier logic (bump `CLASSIFIER_VERSION`, full `recheckFindings` on all 4 reference sites), so it is left for a separate, measured change.

## 2026-11-18 12:05 — Candidate generation: keep the rest of the request, and stop mutating pagination params (busuu)
A depth-2 busuu re-run flagged 27 findings, **26 of which a recheck still kept** — and 23 came from the single query param `limit`. Two causes, both fixed here; the remaining 4 (`review` → `courses`/`dashboard` nav-word swaps) are a shallow-depth artifact the history filter removes once the crawler actually visits those sections.

- **Fix: an HTTP candidate URL no longer drops the request's other query params** ([segments.ts](src/analysis/segments.ts) `candidateUrlFor`, used by AnalysisPipeline and AblationPipeline). A query candidate's `parts` is only `"<path>?<key>="`, so splicing it rebuilt the URL from scratch: `notifications?include_voice=1&limit=5` was forged as `notifications?limit=12538` — not "the same request with one value swapped" but a *different request*. Every response difference caused by the missing param was then attributed to the swapped value, which also robbed `isIdenticalResponse` of its meaning. `candidateUrlFor` sets the one param on the real URL (what the client-routing path always did); path candidates still use `spliceSegment`, already correct for them. Pimsleur's 4 TPs are unaffected (they come from the client-routing path, which was never buggy).
- **New guard: `config.analysis.paramBlacklist`** (query params by NAME: `limit`, `offset`, `page`, `per_page`, `size`, `count`, `skip`, `take`, `sort`, `order`, …). A pagination/sorting control is not an object reference — swapping it changes how MUCH of your own data returns, never WHOSE — so the response differs legitimately and **no response or DOM guard can ever reject it**. Measured root cause: `?limit=5` looks the bare value `5` up in the preindex, which matches **77 unrelated nodes** (`props.$paddingCorrection`, `props.itemsCount`, `props.elements[4].id`, `props.tags[4].id`, …), each contributing its component siblings' ids — hence the forged `12538`, `12338`, `68`, `41`… `maxSegmentMatches` (300) never fires at 77, and lowering it would drop real identifiers. Path segments are not gated by this.
- **Why no reference regression**: no reference-site TP swaps a blacklisted param (pimsleur's is `?id=`, busuu's are `objective_*` path segments, lingualeo's are path/`wordTranslate`), and the URL fix only *adds* the params a forge was previously dropping. AnalysisPipeline 9/9, AblationPipeline + matchFinder + preindex green, 27/27 across the fast suites (new cases: `paramBlacklist` gating by name only, and `candidateUrlFor` preserving `include_voice`).
- **Noted, not changed**: `preindex.isInteresting` requires a **string** value to be longer than 1 char but accepts **any finite number**, so single-digit numeric props (paddings, counts, indices) are indexed and collide with any single-digit URL value. Making the numeric rule symmetric with the string one would kill this collision class at the source, but it changes the preindex (needs a re-preindex to take effect) — left for a separate, measured change.

## 2026-11-18 10:35 — Client-routing: authz-first ordering + strict full-navigation stage + segment blacklist (ejoy)
ejoy flagged only false positives on course 37, and missed a real client-side lesson IDOR (`/app/courses/37/314/1030 -> 1032`, lock false→true) because its Next.js router ignores a synthetic `popstate` for a sibling route, so the cheap pushState probe reports `hasMutatedDom:false`. Three changes, structured as an explicit cheap→expensive ladder; the probe gate is now stage 1 of that ladder rather than a hard veto.

- **Authz gate first (cheap, behavior-preserving)** ([AnalysisPipeline.ts](src/analysis/AnalysisPipeline.ts) `authzGate`). The authorization check is pure (`compareObj` of the two React nodes' props + the cached `assessAuthZ`), so every evaluator now runs it BEFORE any forged request or live client-routing probe. A candidate with no entitlement-relevant props diff is rejected for free, skipping the whole expensive half of the pipeline. Every detection path already required `isAuthzRelevant` to record (the two gates are an AND), so this only reorders — same findings, far fewer forges/probes and less traffic to the target.
- **Explicit 3-stage client-routing ladder with a strict full-navigation escalation** (`clientSideConfirmed`). Stage 1 pushState (cheap, busuu/pimsleur decide here). Stage 2 lenient `page.goto` fallback when stage 1 passed the gate but rendered inert (SSR routes, lingualeo). Stage 3 **strict** `page.goto`, run ONLY for a high-suspicion candidate (its props diff crossed an authz boundary — the authz gate above) when stage 1 saw no digestion at all; it re-imposes the gate's safety on the real load — a redirect-away (`sameRoutePath` on the post-goto url) or a failed capture is a REJECT, not a keep. This is what lets ejoy's lesson IDOR be caught without reopening the busuu redirect / flaky-load FPs the gate guards against. Extracted the shared content guard (`judgeRenderedContent`) so every stage's accept bar is identical. Kill switch: `config.analysis.clientRoutingFullNavigationEscalation`. Replaces the earlier (uncommitted) stale-query fallback, which the pushState gate made inert for ejoy.
- **Segment blacklist, both directions** (`findUrlCandidates`, `config.analysis.segmentBlacklist`, default `['app']`). A blacklisted value is skipped as the segment being mutated AND as a candidate replacement value, removing the ejoy `/app` ↔ `/speak`,`/go`,`/website-directory` section-swap FPs (HTTP and client-routing). Query params are never gated.
- **Regression (reference recheck, in progress)**: pimsleur **4/4**, busuu **20/23** (the same 3 `price_*` byte-identical drops — stage 3 did NOT resurrect them), babbel **0**. lingualeo was interrupted (the stage-3 real-navigation escalation adds ~35–45 s per high-suspicion no-reaction candidate — a real latency cost on a worst-case recheck where every stored finding is already authz-relevant; a fresh analysis pays it only for the few authz-relevant candidates that miss pushState); **re-run lingualeo before relying on its count**. ## 2026-11-17 11:30 — Client-routing & HTTP IDOR: DOM-diff guards kill the inert false positives
Lingualeo flagged `buy/...?refclmark=2 -> 1` as an IDOR: the forged request got a 2xx (Next.js re-fetches `_next/data/...json?refclmark=1`), but the two pages are pixel- and content-identical — a tracking param the app reads and ignores. The screenshot not-found guard never fired (a 2xx skipped it) and nothing compared the actual *content*. Same class over HTTP: busuu `checkout.json?price_id=A -> B` returned a byte-identical 65 KB payload yet was flagged because the sibling React props differ. The fix compares rendered content, not just the network verdict.

- **HTTP: identical response is not a finding** ([responseEvaluate.ts](src/analysis/responseEvaluate.ts)). `isIdenticalResponse` (byte-equal or deep-equal JSON) — a forged response identical to the original means the server ignored the swapped value, so it is not an HTTP finding; it falls through to the client-routing fallback instead of being accepted on "similarity". Drops the 3 busuu `price_*` FPs.
- **Client routing: DOM content guards replace the screenshot** ([domSnapshot.ts](src/analysis/domSnapshot.ts) new, `routeScreenshot.ts` removed). Normalized DOM snapshot = text nodes + `<img>` src + element count, keyed by structural path; classes/styles/ids/meta and `<script>`/`<style>` dropped. Screenshots were viewport-bound, blinded by `lightweightMode`'s placeholder assets, and could not tell "nothing changed" from "one string changed". Two guards: **inert value** (candidate DOM == reference, ALWAYS checked — even a 2xx-corroborated candidate, which is what caught `refclmark`) and **not-found** (vs a garbage-id baseline, only when uncorroborated).
- **Both values masked, remount noise calibrated** (`maskValue`, `domNoise`). Each side masks both the reference and candidate value (so an echoed id, or a stale pushState render still showing the reference value, compares equal). The reference is rendered twice bracketing the candidate to subtract per-render churn (lingualeo training pages draw random quiz words every load), keeping a path only if the second reference render does not show the candidate's own text (a stale render, not noise).
- **Two capture mechanisms, cheap first, keep both** ([AnalysisPipeline.ts](src/analysis/AnalysisPipeline.ts) `clientSideConfirmed`). pushState first (no reload — client-routed apps like pimsleur/busuu decide here with no extra load); a real `page.goto` only as a fallback when pushState is inert, because an SSR route (Next.js `/en/training/<type>`) renders content only on a server load (0 vs ~96 differing nodes). goto cannot replace pushState (a purely client-trusting route is visible only via pushState) and is costly, so it runs last.
- **Reliability (keeps pimsleur 4/4)**: both captures now wait for `networkidle` (bounded, best-effort) before snapshotting — a fetch-gated route (pimsleur loads each lesson by id via XHR) otherwise gets caught showing a shell/cookie wall. The not-found baseline is used only when it differs from the known-good reference (soft-404 / failed-capture backoff), so a flaky shell render no longer drops a real finding.
- **New `scripts/recheckFindings.ts`** + `VulnerabilityStore.listBySite` + `AnalysisPipeline.recheckFindings`: re-examines only the stored findings with the current engine, writing nothing — a minutes-long regression check for the decision logic (it cannot find new findings; use `runAnalysisFromDb` for that).
- **Measured (`recheckFindings`, authenticated profile)**: pimsleur **4/4**, busuu **20/23** (3 `price_*` identical-response FPs dropped, objective siblings kept), babbel **0**, lingualeo stable TPs are the `wordTranslate` siblings (**≥5**, modulo pre-existing probe `hasMutatedDom` flakiness); `refclmark` and the `savannah -> *` dashboard-fallback candidates now correctly rejected. Reproduction scripts print a DOM diff as the verdict (screenshots kept as evidence only). Typecheck green; `AnalysisPipeline`/`domSnapshot`/`responseEvaluate` suites green. Guards and justification locked in `.claude/rules/analysis.md`.

## 2026-11-16 08:40 — Analysis logs now match the real finding count (WARN was gated on DB novelty)
A re-run of `runAnalysisFromDb` printed fewer `potential access control issue` WARN lines than `vulnerabilitiesFlagged` in the stats object (e.g. pimsleur logged 2 while the DB held 4). Not a detection miss and not a log race: each finding's WARN was emitted only `if (inserted)`, and `VulnerabilityStore.record` dedups with `INSERT OR IGNORE` (returns `false` for an id already stored). Since `runAnalysisFromDb` opens the store with `clearOnStart:false` and never clears the site, a finding already recorded by an earlier run was silently not re-logged, even though this run re-confirmed it.

- **Log on confirmation, not on DB insertion** ([src/analysis/AnalysisPipeline.ts](src/analysis/AnalysisPipeline.ts)). A new `logConfirmedFinding` emits the WARN for every finding this run confirms, deduped per run by a `loggedFindingIds` set (so the same finding reached from two reference events is not logged twice) and independent of whether the DB row was new. A finding already stored by a previous run is logged with an explicit ` [already recorded in a previous run]` suffix. `writeReproduction` stays gated on `inserted` (no point regenerating a repro script for a known finding). Applied to all three finding paths (HTTP, client-routing query, client-routing path).
- **Authoritative count in the logs.** The end-of-site INFO line now reads `N vulnerabilit(y/ies) flagged (M confirmed this run)`, so the real `vulnerabilitiesFlagged` figure is in the log stream without inspecting the stats object.
- No change to detection, dedup, or the stored rows: the DB count was always correct; only the logs under-reported it.

## 2026-11-16 08:27 — Client-routing probe: self-cleaning rollback removes the order-dependent flakiness
The client-routing probe flagged an inconsistent number of IDORs across runs (pimsleur oscillated between 2/4 and 4/4). Root cause: the probe restored the original URL (`pushState` + `popstate`) in a `finally` block **without awaiting** the resulting re-render. The Node promise resolved while the browser was still rendering, so the next candidate's probe — running on the same pooled page — could start mid-render and have its `popstate` coalesced/dropped by a router still busy with the rollback, reported as a false "no reaction". The miss was position-dependent: the last candidate in a page's sequence was the most exposed (pimsleur's `294`).

- **Self-cleaning rollback** ([src/analysis/clientRouting.ts](src/analysis/clientRouting.ts)). A new inlined `waitDomSettle(idleTime, maxWait)` is awaited after the rollback `popstate`, in both the query-param and path-segment probes, before the probe resolves. Unlike `waitDomIdle` it does not require a mutation (a no-op rollback resolves after one `idleTime` of quiet instead of riding to the ceiling) and it respects the same `__probeInflight` counter, so a network-gated rollback render is awaited too; the in-flight tracker is now uninstalled only after the settle. Each probe therefore leaves the page quiet, and the result no longer depends on candidate order.
- **Retry demoted to a backstop.** `MAX_CLIENT_ROUTING_ATTEMPTS` (3) is kept, but its comment in [AnalysisPipeline.ts](src/analysis/AnalysisPipeline.ts) now reflects that it only covers a genuinely slow *first* render, not the cross-candidate pollution the rollback settle removed.
- **Verified.** `scripts/debugClientRoutingFlakiness.ts` (5 rounds × the 4 pimsleur candidates, no fresh nav between probes): every candidate now 5/5, including the previously-flaky `294` (was intermittent). End-to-end from a cleared DB, `runAnalysisFromDb.ts` flags all 4 pimsleur IDORs deterministically. `clientRouting` and `AnalysisPipeline` suites green (7/7 each). Cost: a bounded settle (~`idleMs`, default 300 ms, up to the ceiling) added per probe.

## 2026-11-13 15:57 — GET-only forging; network-aware probe window; authz classifier reads keys as words

## 2026-11-13 14:54 — Parallelize the client-routing analysis phase over a page pool
The end-of-crawl analysis was dominated by the client-routing phase (pushState probe + not-found screenshot per candidate), which serialized on one shared page because each candidate mutates that page's live DOM. On a real busuu crawl this phase ran the analysis to ~6–7 min while the exploration itself took ~1–2.

## 2026-11-13 14:40 — Analysis gets its own time budget; faster client-routing probe
Two fixes after a busuu crawl whose analysis ran ~30 min and was then killed by the request-handler timeout.

- **Per-phase time budget.** `requestHandlerTimeoutSecs` was `maxDurationSecs + margin`, but the single request handler runs BOTH exploration and the end-of-crawl analysis, and analysis can be as slow as (here, far slower than) exploration. A crawl whose exploration finished well within budget but whose analysis then ran long was marked *failed* even though the analysis effectively completed. The handler is now sized for both phases (`2 * maxDurationSecs + margin`): `maxDurationSecs` is documented as a per-phase budget — the exploration gets it, then the analysis gets it again. Default raised `1800 → 2700` (45 min per phase).
- **Faster client-routing probe.** `analysis.clientRoutingProbe.maxWaitMs` lowered `4000 → 2500`. The ceiling is only ever paid by a candidate that does NOT react (one that does settles at the floor + idle, ~1.3 s); on a crawl with hundreds of non-reacting client-routing candidates, each probed up to 3×, the 4000 ms ceiling dominated the analysis wall-clock. ## 2026-11-13 14:09 — Client-routing: client digestion is the primary signal, network is a filter not a veto
A query param (or path segment) can be honoured entirely client-side, with no network traffic at all — the SPA reads the mutated value and renders a different resource. The previous logic over-weighted the network: a `4xx` on any request carrying the candidate value vetoed the finding, and a query candidate was additionally required to have been read through the hooked `URLSearchParams.get`. Pimsleur (lessons routed purely client-side by `?id`) hit exactly this: 3 of 4 real IDORs were dropped. The decision is rebalanced around what this fallback is actually for — confirming the app consumed the mutated value.

- **Primary signal = client digestion.** A candidate is accepted when the SPA rendered the candidate's OWN route and stayed on it (`hasMutatedDom && stayedOnRoute`), unless that render is the app's generic not-found page (the visual baseline guard). `AnalysisPipeline.clientSideConfirmed` now makes this decision for all three client-routing sites.
- **Network demoted to a filter.** A backend `2xx` for the candidate's own value, or a provable param read (`appReadParam`, query only), is corroboration strong enough to accept directly (skip the not-found screenshot). Their absence no longer rejects, and a `4xx` no longer vetoes on its own: a route that renders a real, distinct page is a client-side finding regardless of what some request returned. The hard `URLSearchParams.get` requirement is gone — an app that parses the query string another way is no longer penalised.
- **Boundary-aware network scoping** (`urlCarriesValue`, [src/analysis/clientRouting.ts](src/analysis/clientRouting.ts)). A probe response counts for a candidate only when the value is a WHOLE path segment or WHOLE query-param value, not an arbitrary substring. Fixes a spurious "confirm" where candidate `298` matched the customer id `6140298` that rides along in every authenticated API call.
- `ClientRoutingResult` exposes the raw signals (`appReadParam`, `stayedOnRoute`) the pipeline now weighs; `isUsingNewParams` is kept for reproduction scripts and the flakiness diagnostic. The retry loop ends on client digestion or a 2xx. New unit tests for `urlCarriesValue`.

## 2026-11-13 13:31 — Client-routing probe: network-truth confirm + adaptive DOM-settle window
Two changes make the client-side-routing probe miss fewer legitimate findings. Its DOM-mutation signal, whose timing follows a network-gated render, was the main source of flakiness — an earlier pimsleur run flagged 1 of 4 real IDORs for this reason.

- **A network `2xx` is a positive oracle, not just a veto.** A same-session response carrying the candidate value that the backend answers `2xx` while the probe renders the route is timing-robust evidence the app fetched and served the candidate resource — independent of whether the `MutationObserver` happened to catch the render. A candidate is now accepted on EITHER the DOM signal (`isUsingNewParams`) OR a network confirm; when the network confirms, the not-found screenshot guard is skipped (a `2xx` is not a not-found page). The retry loop also stops as soon as either signal is decisive, so a network-confirmed candidate no longer burns its remaining attempts.
- **Adaptive DOM-settle window** (`waitDomIdle`, [src/analysis/clientRouting.ts](src/analysis/clientRouting.ts)). The old window had a single bound acting as both floor and ceiling: it gave up at `minWaitMs` reporting "no reaction", so a render that only starts mutating after that bound (a slow, network-gated one) was missed, and a page that never went quiet could keep the probe waiting forever. It now has three bounds — floor (`minWaitMs`), DOM-quiet settle (`idleMs`), ceiling (`maxWaitMs`): nothing is reported settled until something actually mutates, so a late first render is still caught up to the ceiling, and the ceiling guarantees termination. Defaults retuned `3000/300` → `1000/300/4000` (lower floor so a quick reaction resolves sooner; a route that never reacts rides to the ceiling).
- New config bound `analysis.clientRoutingProbe.maxWaitMs`, threaded through `buildExplorer`, `scripts/runAnalysisFromDb.ts` and generated reproduction scripts. The not-found screenshot baseline settles on the ceiling (a visual baseline wants the fully-rendered route, not the floor).
- Verified on the captured pimsleur data (non-destructively, on a DB copy with its findings pre-cleared): the new code flags all 4 of 4 known IDORs (`294/295/297/298`), none rejected.

## 2026-11-13 11:23 — Client-routing false-positive guards: network truth + not-found screenshot baseline

## 2026-11-13 10:33 — Client-routing probe no longer crashes the whole analysis run
A client-routing probe (`checkClientSideRouting`/`checkClientSideRoutingForPath`) fires a synthetic `pushState` + `popstate`; for some candidate paths this makes the app's own router perform a REAL navigation, which destroys the page's execution context mid-`page.evaluate` (`Execution context was destroyed, most likely because of a navigation`). That rejection was unhandled: it propagated through `runWithConcurrency` and aborted the entire `runForSite` partway through the client-routing phase, losing `analysis_stats` and every not-yet-dispatched candidate (observed on busuu after all 51 HTTP findings had been persisted but before the client-routing ones).

- Both probes now run their script through a small `evaluateProbe` wrapper that catches any `page.evaluate` failure and returns a benign "the app did not react" result (`isUsingNewParams: false`). - Defense in depth: `AnalysisPipeline` now wraps each dispatched candidate task so a single task throwing is logged and skipped instead of rejecting the whole bounded-concurrency pool — one bad candidate can no longer abort the run and discard the stats + remaining findings.

## 2026-11-13 10:27 — Candidate generation: drop generic-keyword segments + cache parsed React graphs
The analysis pipeline's pre-dispatch phase (turning captured URLs into IDOR candidates) took ~20 minutes of pure CPU on busuu before a single request was forged. Two compounding causes, both fixed; on the same data the phase now runs in ~2s instead of >115s (measured offline over 10,752 URLs).

- **Generic-keyword segments skipped.** `extractSegments` proposes every URL path segment as a "swap this value" candidate, filtered only by "does the value appear in the preindex". Real identifiers are far below the cap (busuu objective/exercise/activity ids appear 20–110 times), so the surviving candidates are unchanged — e.g. `objective_e43c5b7a` still yields exactly its 19 sibling candidates.
- **Parsed React graphs cached per run.** `findUrlCandidates` looked a state's graph up once per preindex match (tens of thousands of times) but there are only a couple hundred distinct graphs; it was re-running `JSON.parse` on the same ~150 KB strings repeatedly. `AnalysisPipeline` now memoizes `getById` for the duration of a `runForSite` (cleared at its start, so it never grows across sites or goes stale).

## 2026-11-13 09:06 — Tolerant restore: attempt budget for (state, element)
Restoring a state no longer abandons an element (or the branch below it) on the first failure. In SPA environments, an intermittent interstitial at page load (cookie banner, “welcome back” bottom sheet) may cover the target on one page load and disappear on the next: previously, this was enough to prune entire exploration branches, because the `(state, element)` pair was marked as explored *before* the attempt, and a single miss was final.

- `StateStore` transitions from destructive marking (`isExplored`/`markExplored`) to a `untried → inprogress → done` lifecycle using `claim()`/`release()`. `claim()` remains the synchronous and exclusive gate that prevents two tabs from clicking the same element; a `release(‘miss’)` puts the pair back in the queue for a new attempt on a future landing, as long as there is budget, then closes it (guaranteed termination). An exception during the click immediately closes the pair (actual error, not volatility): it is not retried.
- `DfsExplorer.step` now distinguishes between “element found and clicked” and “missed this time”; `claimable()` scans the frontier and retrieves a state only when *all* of its elements are `done`, skipping (without removing) states with only `inprogress` elements.
- New configuration parameter `restoreAttempts` (default 4): the number of times a pair is retried across multiple landings before being deemed unreachable.
- The set of clickable elements remains that of the original snapshot for each state: *new* clickable elements that appear only in variants (e.g., buttons in the intermittent modal) are treated as volatile and ignored; those already captured are simply re-located with tolerance.
