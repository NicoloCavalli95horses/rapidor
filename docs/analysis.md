# IDOR analysis (authz/IDOR detection)

Part of the [SPA crawler](../README.md). Settings referenced below (`analysis.*`, `db.*`) are documented in the README's [Configuration](../README.md#configuration).

1. **Preindex** ([src/analysis/preindex.ts](../src/analysis/preindex.ts)) — every captured React node's props are walked for "interesting" values (short strings/numbers under keys like `id`, `user`, `role`, `owner`, ...) and tokenized into `preindexed_values`.
2. **Segment extraction** ([src/analysis/segments.ts](../src/analysis/segments.ts)) — for each captured HTTP event and each visited page URL, proposes every path segment and each query parameter as a candidate "swap this value" target. A segment whose value appears in more than `analysis.maxSegmentMatches` preindexed nodes is skipped as a generic keyword (a tag/role/category word that also happens to be a URL segment), not an identifier — real identifiers appear only a handful of times, so this drops the combinatorial fan-out of common words without losing any real candidate. A path segment whose value is in `analysis.segmentBlacklist` (default `['app']`) is also never mutated, in **either direction** — not as the segment being swapped, and not as a candidate's replacement value: these are app-shell/section route roots (`/app`, `/speak`, …), not user-scoped ids, so swapping one only navigates to a different app *section* — which renders a different DOM and so looks like a client-routing finding (the ejoy `/app` ↔ `/speak`,`/go`,`/website-directory` false positives, HTTP and client-routing alike). Query-param values are never gated by that blacklist — query params have their own, by **name**: a param in `analysis.paramBlacklist` (`limit`, `offset`, `page`, `sort`, …) is never mutated, because a pagination/sorting control is not an object reference. Swapping it changes how *much* of your own data comes back, never *whose*, so the response differs legitimately and no downstream guard can reject it — busuu's `?limit=5` alone accounted for 22 of its 27 false positives (the bare value `5` matched 77 unrelated preindexed nodes — paddings, counts, array indices — each contributing its component siblings' ids; the `maxSegmentMatches` cap never fires at 77). The candidate URL itself is built by `segments.candidateUrlFor`, which sets the one swapped param on the real URL so **every other param survives**; building it from the candidate's `parts` alone used to drop them, forging a different request and making any response difference meaningless.
3. **Match finding** ([src/analysis/matchFinder.ts](../src/analysis/matchFinder.ts)) — if a candidate's value matches a pre-indexed one, looks up sibling instances of the *same React component* with a different value at the same prop path.
4. **Request forging** ([src/analysis/requestForge.ts](../src/analysis/requestForge.ts)) — **GET only**: the detector reads, never writes, so it skips any captured non-GET event and `forgeRequest` refuses a non-GET method outright (replaying a POST/PUT/DELETE with a swapped id would change state on the live target). It splices the sibling's value into the GET and replays it via Playwright's `page.request.fetch()` (reuses the browsing context's cookies, but — unlike the page's own `fetch`/XHR — never fires `page.on('request')`, so forged probes never pollute `http_events`).
5. **Response evaluation** ([src/analysis/responseEvaluate.ts](../src/analysis/responseEvaluate.ts)) — the forged response is compared against the original (status/headers/body-shape similarity); if it still looks "authorized" — and is **not identical** to the original response (`isIdenticalResponse`: byte-identical, or deep-equal JSON; identical means the server ignored the swapped value, so the forge leaked nothing and the candidate falls through to the client-routing fallback instead) — the differing props are classified for authorization-relevance by a sentence-embedding model (`src/analysis/authzClassifier.ts`, `@huggingface/transformers`, cosine similarity against a few fixed "entitlement" concept sentences, cached in `authz_classifications` — see `db.clearClassifierCache` above). Each key/value is normalized before embedding — camelCase/snake/kebab split into words and framed as a yes/no condition (`isLessonUnlocked` → `"whether is lesson unlocked"`) — so compound and boolean authorization flags read in the words the model knows instead of as one opaque token. The verdict is taken **per diff**, tying a key's relevance to the shape of its own value (`assessAuthZ` / `valueLooksLikeAsset`): a value that is itself an authz term (`tier: "free" → "premium"`) always counts, so string enums are kept, but a key that merely *reads* like an entitlement is honoured only when its differing value is not a URL/asset. busuu's `course_pack_paywall_1000` is a cover-image field (value an `https://…jpg`) whose name alone scored 0.342 on "paywall"; swapping a course-pack id rerenders the whole catalog, so that key was always in the diff and flagged all 96 course-pack false positives — none of them an access flag.
6. **Client-side routing fallback** ([src/analysis/clientRouting.ts](../src/analysis/clientRouting.ts)) — for a candidate whose forged request did not look like it leaked anything (e.g. the server correctly rejects it), also checks whether the page's own client-side routing honors the swapped value anyway: it navigates back to the page the original event happened on, mutates `window.location` (`pushState` + a synthetic `popstate`) and watches for a real DOM mutation, independent of any server response — this is how a purely client-routed authorization bug (the UI trusts a URL it never re-validates) gets caught even though no "wrong" request ever reaches the network. It works for both **query parameters** (`checkClientSideRouting`) and **path segments** (`checkClientSideRoutingForPath`). The **primary signal is client digestion**: the SPA rendered the candidate's own route and stayed on it (`hasMutatedDom && stayedOnRoute`) — a value honoured purely client-side, with no network traffic at all, is a real finding. What can then still reject it are two **DOM content guards** ([src/analysis/domSnapshot.ts](../src/analysis/domSnapshot.ts), described below): the swapped value changing nothing on the page (inert value), or the app rendering its generic not-found page for every id. The **network is a filter, not a veto**: a `2xx` the backend returns for the candidate's own value, or a provable param read (`URLSearchParams.get`, hooked for query params only), is corroboration strong enough to skip the not-found guard (never the inert-value guard) — but their absence does not reject, and a `4xx` on an incidental request does not veto a route that renders a real, distinct page. A network response is attributed to the candidate only when its value is a **whole path segment or whole query-param value** (`urlCarriesValue`), never a substring, so a short id never matches a longer one it happens to sit inside. Each probe **awaits its own rollback re-render to settle** before resolving, so it leaves the shared pool page quiet for the next candidate instead of leaving a render in flight that the next probe could land in mid-way (the former source of order-dependent flakiness). A negative result is still retried up to 3 times as a secondary backstop for a genuinely slow first render.

   **DOM content guards.** A client-routing finding is kept only when the candidate route shows real, distinct content. Both guards compare **normalized DOM snapshots** ([src/analysis/domSnapshot.ts](../src/analysis/domSnapshot.ts)), not screenshots: a screenshot only sees the viewport, depends on fonts/images loading (lightweightMode turns every image into the same placeholder, so another user's avatar is invisible) and cannot tell "nothing changed" from "one short string changed". A snapshot keeps only:
   - every **text node** (whitespace-collapsed, hidden content included), keyed by an XPath-like structural path with a per-tag index (`body/div[1]/span[0]/#0`), so an inserted sibling does not shift the rest;
   - the **`src` of every `<img>`** — the one attribute that carries user data on its own;
   - the **element count** — a structural change with no text.

   Classes, styles, ids, `data-*`, meta and hrefs are dropped (framework noise, or the value merely reflected into links); `<script>`/`<style>`/`<noscript>`/`<template>` are skipped (Next.js's `__NEXT_DATA__` embeds the current query). Before comparing, every side is **masked with both values** (the reference's and the candidate's, whole-token occurrences, values of 3+ characters), so a page that only echoes the id it was given ("Order 1042 not found") — or a stale render still showing the reference's id — compares equal. The route's **remount noise** is calibrated out: for each candidate the reference is rendered twice (bracketing the candidate's own render), and the paths that differ between those two renders (a countdown, a carousel, lingualeo's random quiz words) plus their element-count drift are ignored — except a path where the second reference render shows the *candidate's* text, which is a stale render, not noise, and is kept.

   **Three stages, cheapest first** (`clientSideConfirmed`, an explicit ladder — the first stage to reach a verdict wins, inconclusive falls through, the real page load is always last). **Stage 1 — pushState+popstate** (no reload, the mechanism a genuinely client-routed SPA honours, so busuu/pimsleur decide here with no extra network); it applies only when the probe gate passed (`hasMutatedDom && stayedOnRoute`). **Stage 2 — SSR navigation fallback (lenient):** when stage 1 passed the gate but rendered *identical* to the reference, a real `page.goto` — because a server-rendered route (Next.js) produces its content only on a server fetch that pushState never triggers, so lingualeo's `/en/training/<type>` siblings look identical under pushState (0 nodes) but differ by ~96 text nodes on a real load; the app already proved it digests the route, so a failed capture here *keeps*. **Stage 3 — strict full-navigation escalation:** when stage 1 saw *no* digestion at all (no DOM reaction, or the router redirected away), a real `page.goto` run **only for a high-suspicion candidate** (one whose props diff already crossed an authorization boundary). This catches an app whose router ignores a synthetic `popstate` for a sibling route (ejoy/Next.js: stage 1 is blind, yet a real load renders the sibling), while re-imposing the gate's safety on the real load — a redirect-away (`sameRoutePath` on the post-goto URL) or a failed capture is a *reject*, not a keep. Stages 2 and 3 run the **same content guard** (`judgeRenderedContent`) as stage 1, so the accept bar is identical regardless of how the render was captured. Stage 3's kill switch: `analysis.clientRoutingFullNavigationEscalation`.

   **Cheapest gate first.** The authorization check is pure — a diff of the two React nodes' props (`compareObj`) classified against the cached entitlement model (`assessAuthZ`) — with no network and no live browser. So every evaluator runs it (`authzGate`) **before** forging a request or launching a client-routing probe: a candidate whose props carry no entitlement signal (two public resources differing only by id/name/href) is rejected for free, skipping the whole expensive half of the pipeline. This is a behavior-preserving reorder — every detection path already required an authz-relevant diff to record a finding, and the two gates are an AND — that simply moves the cheap one earlier. The relevance verdict is also the **high-suspicion** signal that licenses the stage-3 full-navigation escalation above: the costly real load runs only for a candidate whose props already point at an authorization boundary, never for the long tail of section-swap / navigation-word noise.

   - **Inert value** (always applied, even when the network or a param read corroborates the probe): candidate vs reference. No changed text node and no element-count change beyond the noise, under *both* capture mechanisms, means the swapped value changed nothing on the page, so the candidate is rejected. A DOM mutation alone is not new content: lingualeo's `buy/...?refclmark=2 -> 1` re-fetches `_next/data/...json?refclmark=1` (a 2xx carrying the value) and re-renders exactly the same page.
   - **Not found** (only when nothing corroborates): the candidate vs the app's not-found page, calibrated once per route template **and capture mechanism** by rendering a garbage id in the same slot. Rejected when both the changed-text-node fraction and the element-count fraction are within `analysis.notFoundDomMaxDiff`.

   Candidates are also **seeded from the crawler's own visited page URLs**, not only from `http_events`: a value an SPA only ever reads client-side never shows up in any request, yet is still tested via the client-routing probe.
7. **History filter** — before any request or probe, a candidate URL that the crawler already reached on its own (checked against the union of `http_events`, `react_states` and `crawl_states`) is skipped: swapping in a value the user can already reach by clicking around is not evidence of unauthorized access.

A flagged finding (`vulnerabilities` table) records which detection path caught it (`detectionMethod: 'http' | 'client-routing'`), the reference/candidate URLs, and a human-readable `motivation` (which props differ and how). Everything above — including every stat that used to only exist transiently (segments extracted, matches found, candidates found, HTTP events, React states, requests generated, vulnerabilities flagged) and the wall-clock time of the exploration and analysis phases (`exploration_ms`/`analysis_ms`, logged as `hh:mm:ss.mmm`) — is persisted per site in `analysis_stats`; inspect it with `npm run stats` (see [Statistics](../README.md#statistics)).

## Reproduction scripts

Right after a genuinely new finding is recorded (by any of the three paths: forged HTTP request, client-routing on a query param, client-routing on a path segment), [src/analysis/reproductionScript.ts](../src/analysis/reproductionScript.ts) writes a standalone `reports/<site>/<site>_<vulnType>_<timestamp>.repro.ts` (`vulnType` is `http`, `client-query`, or `client-path`; `timestamp` includes milliseconds, so concurrently-evaluated candidates never collide). It is self-contained — the original request/response and both nodes' React props are embedded in the file itself, so it never depends on `storage/crawler.db` (which a later crawl, `db.clearOnStart` being the default, wipes):

```bash
npx tsx reports/<site>/<site>_<vulnType>_<timestamp>.repro.ts
```

All three finding kinds go through the **same flow**: a real (non-headless) browser opens, navigates to the original URL/request and the mutated one, and a DOM snapshot and a screenshot are taken of each — for an HTTP finding this means opening the reference and candidate URLs directly (skipped, with a message, for a non-`GET` method, which can't be replayed by opening a URL); for a client-routing finding the probe runs via `pushState`+`popstate` (informational), then the candidate page is opened by a real navigation — the content guard's own mechanism — for the DOM diff and screenshots. The script then prints, in order:

1. the **original** request/response (http) or page (client-routing);
2. the **mutated** request/response (a live, fresh request) or page;
3. the **DOM diff** of the two pages — the same normalized comparison the pipeline's guards use (`domSnapshot.ts`, each side masked with its own value), listing every changed text node (`- before` / `+ after`, first 20) and the element counts. This is the verdict signal; with a single capture per side there is no self-noise calibration, so read the listed lines before trusting a "changed" verdict;
4. the two **screenshots** (`<baseName>.original.png`, `<baseName>.mutated.png`) and their pixel diff (`<baseName>.diff.png`, `pixelmatch`/`pngjs`) — **visual evidence only**, never a criterion;
5. the **verdict**: response similarity (http) or the probe result (client-routing), followed by the DOM diff's verdict ("content changed" vs "content IDENTICAL — most likely a false positive");
6. the **React props** of the original node and of the node whose value was spliced into the mutated request/URL, plus the authorization-relevant differences and the keys the classifier flagged.

A failure while generating a script never prevents the finding itself from being recorded.

## Ablation study (HTTP-JSON-only)

`analysis.ablationMode` (default `false`, `ABLATION_MODE=true` to turn it on) runs a second, independent analysis pass — [src/analysis/AblationPipeline.ts](../src/analysis/AblationPipeline.ts) — alongside the main one, to measure how much of what the React-informed pipeline finds actually required React state at all, versus how much was sitting in plain sight in the JSON the site's own API already returned. No new network monitoring and no new exploration: it reuses the exact same `http_events`/`crawl_states` the main pipeline already captured.

* **Preindex** ([src/analysis/jsonMatchFinder.ts](../src/analysis/jsonMatchFinder.ts), `buildJsonPreindex`) — every already-captured JSON response body for the site is walked once (same depth cap and "interesting key" rules as the React preindex — `isInteresting`/`tokenize` are reused verbatim), building a `value -> {body, path}[]` index. A URL segment is then looked up against the *whole* corpus, not just "its own" response: the id a request's own URL carries is often only ever *returned*, alongside its siblings, by a completely different endpoint (a list/listing call), not by the per-item endpoint whose own URL happens to contain it.
* **Sibling finding** (`findJsonCandidates`) — once a match lands inside some body, siblings are looked for at *every* enclosing array level along that match's path (not just the nearest one), each level varied independently while every other index stays fixed at its reference value — the JSON analog of `matchFinder.ts`'s `componentIndex` walk. Sibling-finding itself never crosses bodies: two different HTTP responses are never assumed to describe related data just because a value happens to appear in both.
* **Oracle** — identical to the main pipeline's HTTP path: forge the candidate request (`requestForge.ts`), compare the response (`responseEvaluate.ts`), diff the two sibling objects' properties (`compareObj`), classify the diff for authorization relevance (the same shared `authzClassifier.ts`, same cache). `compareObj` recurses index-wise into arrays (not just plain objects) for both pipelines, deliberately: the fairest ablation gives the HTTP-only analysis every tool the React-informed one has, so any remaining gap in what each pipeline flags reflects a real difference in signal (React state vs. JSON alone), not an avoidable blind spot shared by both.
* **Shared forged-request cache** ([src/db/ForgedRequestStore.ts](../src/db/ForgedRequestStore.ts)) — keyed by `(site, method, url, body)`: if the main pipeline already forged the exact same candidate (the two often propose the same id swap from two different sources), the ablation reuses that response instead of hitting the live site again, and vice versa.
* **Structurally narrower by construction, not by omission** — there is no equivalent of the client-routing probes: those resolve their oracle from a DOM-mutation signal (did the app's own rendering react?), which has no network counterpart at all. A query param or path segment an SPA only ever reads client-side is invisible to a network-only analysis, full stop.

Findings land in their own tables — `ablation_vulnerabilities`/`ablation_stats` — never mixed with `vulnerabilities`/`analysis_stats`, so the two are always comparable:

```bash
ABLATION_MODE=true START_URL=https://example.com npm start
npm run compare-ablation                               # side-by-side stats + which findings the main pipeline caught that the ablation missed, by detectionMethod
npm run compare-ablation -- --db storage/other-run.db
```
