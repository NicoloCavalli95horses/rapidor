# IDOR analysis (authz/IDOR detection)

Part of the [SPA crawler](../README.md). Settings referenced below (`analysis.*`, `db.*`) are documented in the README's [Configuration](../README.md#configuration).

1. **Preindex** ([src/analysis/preindex.ts](../src/analysis/preindex.ts)) — every captured React node's props are walked for "interesting" values (short strings/numbers under keys like `id`, `user`, `role`, `owner`, ...) and tokenized into `preindexed_values`.
2. **Segment extraction** ([src/analysis/segments.ts](../src/analysis/segments.ts)) — for each captured HTTP event and each visited page URL, proposes every path segment and each query parameter as a candidate "swap this value" target. A segment whose value appears in more than `analysis.maxSegmentMatches` preindexed nodes is skipped as a generic keyword (a tag/role/category word that also happens to be a URL segment), not an identifier — real identifiers appear only a handful of times, so this drops the combinatorial fan-out of common words without losing any real candidate. A match is also skipped when its React node sits inside the site's **navigation/footer DOM chrome** (`domZone.ts`): the newer browser extension serializes each node's nearest DOM element (`node.dom`) and its `parent`, so a value that came from a `<nav>`/`<footer>` (or a `role="navigation"`/`"contentinfo"` / nav-class element, found by walking ancestors) is recognised as navigation furniture — never a user-scoped id — and produces no candidates. The rule deliberately treats ONLY nav/footer/sidebar as chrome and NOT `<header>`/`<section>`: busuu renders its objective-id cards (its real IDOR targets) inside a `<header>`, so a header rule would drop true positives. The ancestor-walk window scales with graph size (`log2(nodeCount)`, ~13 for a busuu-sized app) and the filter no-ops on older captures that lack the `dom` field. A path segment whose value is in `analysis.segmentBlacklist` (default `['app']`) is also never mutated, in **either direction** — not as the segment being swapped, and not as a candidate's replacement value: these are app-shell/section route roots (`/app`, `/speak`, …), not user-scoped ids, so swapping one only navigates to a different app *section* — which renders a different DOM and so looks like a client-routing finding (the ejoy `/app` ↔ `/speak`,`/go`,`/website-directory` false positives, HTTP and client-routing alike). Query-param values are never gated by that blacklist — query params have their own, by **name**: a param in `analysis.paramBlacklist` (`limit`, `offset`, `page`, `sort`, … and timezone params `tzoffset`/`timezone`/`tz`) is never mutated, because a pagination/sorting/representation control is not an object reference. Swapping it changes how *much* of your own data comes back, never *whose*, so the response differs legitimately and no downstream guard can reject it — busuu's `?limit=5` alone accounted for 22 of its 27 false positives (the bare value `5` matched 77 unrelated preindexed nodes — paddings, counts, array indices — each contributing its component siblings' ids; the `maxSegmentMatches` cap never fires at 77). A **locale / UI-language** param (`isLocaleParam`/`LOCALE_PARAM`: `locale`, `lang`, `language`, `mother_language`, `ui_language`, …) is likewise never mutated — it selects the response's *language*, not *whose* resource it is (Mondly's `notification-preferences?mother_language=22` just returns the same preferences in another language). It is matched by a regex rather than a blacklist token on purpose: a bare `language` token would also drop `target_language`/`learning_language`, which in a language-learning app name the studied resource (possibly paid) — a real target; the regex's prefix set is UI/native/mother-style only, so those stay mutable. A **marketing / attribution** param (`isTrackingParam`/`TRACKING_PARAM`: `utm_*`, `refclmark`, `campaignId`, click-ids like `gclid`/`fbclid`/`msclkid`) is never mutated either — it names *where the visit came from*, never *which* resource, so the server ignores it and a swap only surfaces response noise. lingualeo's CRM buy blob `/_next/data/…/en/buy/…json?…&refclmark=2&campaignId=…` is the motivating case: the inert `refclmark` value `2` collided with a wordset id in the page's React state, so sibling ids got forged; the server returned the same blob, but its dynamic `elements`/`tags` list reordered between capture and forge and the positional diff (`elements.1.type: "user" -> "global"`) tripped the authz gate → 10 HTTP false positives on one request. Like the locale filter it is a regex, not a token, so a resource param that merely contains a tracking word (`refId`, `price_id`, `campaign_name`) stays mutable. The candidate URL itself is built by `segments.candidateUrlFor`, which sets the one swapped param on the real URL so **every other param survives**; building it from the candidate's `parts` alone used to drop them, forging a different request and making any response difference meaningless. A candidate represents swapping **one sibling resource's identity**, which is usually a single URL token but need not be: when that identity is duplicated in the url (ejoy encodes a lesson both as a path segment and as a capability in `?path=`), the client-routing path reconciles the other occurrence from the sibling's own state (step 6, *resource identity*) rather than mutating tokens independently — still one candidate, one probe.
3. **Match finding** ([src/analysis/matchFinder.ts](../src/analysis/matchFinder.ts)) — if a candidate's value matches a pre-indexed one, looks up sibling instances of the *same React component* with a different value at the same prop path.
4. **Request forging** ([src/analysis/requestForge.ts](../src/analysis/requestForge.ts)) — **GET only**: the detector reads, never writes, so it skips any captured non-GET event and `forgeRequest` refuses a non-GET method outright (replaying a POST/PUT/DELETE with a swapped id would change state on the live target). It splices the sibling's value into the GET and replays it via Playwright's `page.request.fetch()` (reuses the browsing context's cookies, but — unlike the page's own `fetch`/XHR — never fires `page.on('request')`, so forged probes never pollute `http_events`). Only a **`200` GET** is used as a forge reference (main and ablation): a `204`/`3xx` has no body to compare and a `4xx` means the user can't reach even the original. Non-200 events still feed the history filter. Motivating case: talkpal's ~31k first-party Google Analytics beacons (`/bqpw/g/collect`, `204`, unique `_p`/`sst.rnd`/`rcb` per hit) that drove ~3.6M preindex matches and never finished generating.
5. **Response evaluation** ([src/analysis/responseEvaluate.ts](../src/analysis/responseEvaluate.ts)) — the forged response is compared against the original (status/content-type equal, top-level body-shape close, and body length within bounds — **asymmetric**: a LARGER forged body is fine, since a paid/higher-privilege resource legitimately carries more content; only a much SMALLER one, a stub/denial, is rejected, via `isLengthNotTruncated`); if it still looks "authorized" — and is **not identical** to the original response (`isIdenticalResponse`: byte-identical, or deep-equal JSON; identical means the server ignored the swapped value, so the forge leaked nothing and the candidate falls through to the client-routing fallback instead) — the differing props are classified for authorization-relevance by a sentence-embedding model (`src/analysis/authzClassifier.ts`, `@huggingface/transformers`, cosine similarity against a few fixed "entitlement" concept sentences, cached in `authz_classifications` — see `db.clearClassifierCache` above). Each key/value is normalized before embedding — camelCase/snake/kebab split into words and framed as a yes/no condition (`isLessonUnlocked` → `"whether is lesson unlocked"`) — so compound and boolean authorization flags read in the words the model knows instead of as one opaque token. The verdict is taken **per diff**, tying a key's relevance to the shape of its own value (`assessAuthZ` / `valueLooksLikeAsset`): a value that is itself an authz term (`tier: "free" → "premium"`) always counts, so string enums are kept, but a key that merely *reads* like an entitlement is honoured only when its differing value is not a URL/asset. busuu's `course_pack_paywall_1000` is a cover-image field (value an `https://…jpg`) whose name alone scored 0.342 on "paywall"; swapping a course-pack id rerenders the whole catalog, so that key was always in the diff and flagged all 96 course-pack false positives — none of them an access flag.
   **HTTP content-identity guards (always on, no config knob).** Before an HTTP forge is recorded as a finding, two checks on the forged response's *content* — keyed by `responseEvaluate.canonicalResponseKey` (status + body, byte-equal or key-order-independent JSON: the same equivalence `isIdenticalResponse` uses): (1) **already-accessible data** — if the forged body equals a response the crawler already collected legitimately at a *different* URL (anywhere in this site's `http_events`), the user can already reach that data by normal browsing, so it is not an access-control leak and the candidate is dropped. The reference event's *own* response is excluded from this comparison: a forge that returns the original's body is the "server ignored the swapped value" case handled by `isIdenticalResponse` above, not data accessible at another URL. (2) **cross-candidate dedup** — two different sibling swaps that forge a byte/JSON-identical response describe the *same* leak (the server's answer does not depend on which sibling proposed the value), so only the first is recorded. A forged response with no body yields no key and is never dropped (drop only on positive evidence). A forged response with an **error status (`>= 400`)** is also dropped outright — a 401/403 "access denied" or any 4xx/5xx means the server never served the resource, so there is nothing to leak (this also keeps an expired-token run honest: every forge comes back denied and nothing is flagged, instead of a stale 200 in the forge cache being trusted). An **empty-data** forge (`isEmptyJsonResponse`: `{}`, `[]`, or an all-empty wrapper like `{"data":{"data":[],"total":0}}`) is likewise dropped — it carries no data, so it is not a leak however much it differs from the reference (a body with a real record, a non-empty array, or a non-metadata scalar is never "empty"; a non-JSON body is kept). An **error-envelope** forge (`isErrorEnvelopeResponse`) is dropped too: a 200 whose top-level JSON signals an error/denial — truthy `error`, `success:false`/`ok:false`, or `status:"error"` — reached nothing, even when real-looking fields sit beside the flag (apps that answer 200 instead of a 4xx, e.g. Mondly's `{"error":true}`). This is the absolute content check the purely *relative* similarity ratios cannot provide (two short bodies pass as "similar"); a blunt "too-few-keys" floor is deliberately avoided — real findings have as few as 2 top-level keys (busuu) and APIs wrap rich data under few keys. These guards are HTTP-only — a client-routing finding carries no server-response evidence — and the content-identity pair is applied identically in the [ablation pipeline](#ablation-study-http-json-only), so the two pipelines stay comparable.

   **Client-routing already-accessible guard.** A client-routing finding has no server response, but it DOES render a React state. `reactContentKey` ([src/analysis/reactFingerprint.ts](../src/analysis/reactFingerprint.ts)) hashes a captured state's STRUCTURE (`graph.fingerprint`) together with its identifier-like DATA (the same `collectPreindexRows` the preindex uses). Before recording, `CandidateEvaluator` drops a finding whose candidate route's live-rendered state is **already-collected** — its key matches some `react_states` row, a page the user already reaches by normal browsing (promova's `/terms/press-center` renders the already-crawled `/press-center`). The live state is read via the extension by `ClientRoutingVerifier.captureReactContentKey` — a *separate real navigation* run only on already-accepted candidates (a synthetic popstate often does not update a Next.js tree; it waits for network-idle and a settle so a fetch-gated route's content has landed before hashing); extension absent → key undefined → finding kept. The corpus is built offline from `react_states` (`primeReactHistory`). Cross-candidate **dedup** is *not* done here: it is deterministic on the leaked route (see the finding-id note below) — a content-hash duplicate check used to live here but collapsed distinct *locked* siblings, which all render a near-identical paywall shell (ejoy's lessons 1033 and 1035 hashed equal), so one was lost; the route key tells them apart exactly.

6. **Client-side routing fallback** ([src/analysis/clientRouting.ts](../src/analysis/clientRouting.ts)) — for a candidate whose forged request did not look like it leaked anything (e.g. the server correctly rejects it), also checks whether the page's own client-side routing honors the swapped value anyway: it navigates back to the page the original event happened on, mutates `window.location` (`pushState` + a synthetic `popstate`) and watches for a real DOM mutation, independent of any server response — this is how a purely client-routed authorization bug (the UI trusts a URL it never re-validates) gets caught even though no "wrong" request ever reaches the network. It works for both **query parameters** (`checkClientSideRouting`) and **path segments** (`checkClientSideRoutingForPath`). The **primary signal is client digestion**: the SPA rendered the candidate's own route and stayed on it (`hasMutatedDom && stayedOnRoute`) — a value honoured purely client-side, with no network traffic at all, is a real finding. What can then still reject it are two **DOM content guards** ([src/analysis/domSnapshot.ts](../src/analysis/domSnapshot.ts), described below): the swapped value changing nothing on the page (inert value), or the app rendering its generic not-found page for every id. The **network is a filter, not a veto**: a `2xx` the backend returns for the candidate's own value, or a provable param read (`URLSearchParams.get`, hooked for query params only), is corroboration strong enough to skip the not-found guard (never the inert-value guard) — but their absence does not reject, and a `4xx` on an incidental request does not veto a route that renders a real, distinct page. A network response is attributed to the candidate only when its value is a **whole path segment or whole query-param value** (`urlCarriesValue`), never a substring, so a short id never matches a longer one it happens to sit inside. Each probe **awaits its own rollback re-render to settle** before resolving, so it leaves the shared pool page quiet for the next candidate instead of leaving a render in flight that the next probe could land in mid-way (the former source of order-dependent flakiness). A negative result is still retried up to 3 times as a secondary backstop for a genuinely slow first render.

   **DOM content guards.** A client-routing finding is kept only when the candidate route shows real, distinct content. Both guards compare **normalized DOM snapshots** ([src/analysis/domSnapshot.ts](../src/analysis/domSnapshot.ts)), not screenshots: a screenshot only sees the viewport, depends on fonts/images loading (lightweightMode turns every image into the same placeholder, so another user's avatar is invisible) and cannot tell "nothing changed" from "one short string changed". A snapshot keeps only:
   - every **text node** (whitespace-collapsed, hidden content included), keyed by an XPath-like structural path with a per-tag index (`body/div[1]/span[0]/#0`), so an inserted sibling does not shift the rest;
   - the **`src` of every `<img>`** — the one attribute that carries user data on its own;
   - the **element count** — a structural change with no text.

   Classes, styles, ids, `data-*`, meta and hrefs are dropped (framework noise, or the value merely reflected into links); `<script>`/`<style>`/`<noscript>`/`<template>` are skipped (Next.js's `__NEXT_DATA__` embeds the current query). Before comparing, every side is **masked with both values** (the reference's and the candidate's, whole-token occurrences, values of 3+ characters), so a page that only echoes the id it was given ("Order 1042 not found") — or a stale render still showing the reference's id — compares equal. The route's **remount noise** is calibrated out: for each candidate the reference is rendered twice (bracketing the candidate's own render), and the paths that differ between those two renders (a countdown, a carousel, lingualeo's random quiz words) plus their element-count drift are ignored — except a path where the second reference render shows the *candidate's* text, which is a stale render, not noise, and is kept.

   **Three stages, cheapest first** (`clientSideConfirmed`, an explicit ladder — the first stage to reach a verdict wins, inconclusive falls through, the real page load is always last). **Stage 1 — pushState+popstate** (no reload, the mechanism a genuinely client-routed SPA honours, so busuu/pimsleur decide here with no extra network); it applies only when the probe gate passed (`hasMutatedDom && stayedOnRoute`). **Stage 2 — SSR navigation fallback (lenient):** when stage 1 passed the gate but rendered *identical* to the reference, a real `page.goto` — because a server-rendered route (Next.js) produces its content only on a server fetch that pushState never triggers, so lingualeo's `/en/training/<type>` siblings look identical under pushState (0 nodes) but differ by ~96 text nodes on a real load; the app already proved it digests the route, so a failed capture here *keeps* — but a real load the app **redirected away** from the candidate route is a *reject* (clozemaster bounces paid stories to `/pro`, whose upsell page would otherwise read as "new content"). **Stage 3 — strict full-navigation escalation:** when stage 1 saw *no* digestion at all (no DOM reaction, or the router redirected away), a real `page.goto` run **only for a high-suspicion candidate** (one whose props diff already crossed an authorization boundary). This catches an app whose router ignores a synthetic `popstate` for a sibling route (ejoy/Next.js: stage 1 is blind, yet a real load renders the sibling), while re-imposing the gate's safety on the real load — a redirect-away (`sameRoutePath` on the post-goto URL) or a failed capture is a *reject*, not a keep. Stages 2 and 3 run the **same content guard** (`judgeRenderedContent`) as stage 1, so the accept bar is identical regardless of how the render was captured. Stage 3's kill switch: `analysis.clientRoutingFullNavigationEscalation`.

   **Sibling-group confirmation (flakiness recovery).** The stage-3 probe is flaky on fetch-gated routes — ejoy's locked lessons fetch their content by id over XHR, so one real load can snapshot an incomplete render and read as a false *negative*, flipping which paid siblings surface run-to-run (ejoy flagged only 1 of its 4 locked lessons in one run). But the siblings of one reference node that share the swapped `path` AND the authorization-relevant keys are structurally identical resources behind the *same* route, so a genuine confirmation of one is a logical consequence for all. `CandidateEvaluator` keys each client-routing candidate into a **group** (`pageUrl` + `stateId` + reference node id + swap `path` + the sorted authz `sensitiveKeys` — a different authz signature is a different group, so unrelated entitlements never cross-confirm). The moment one sibling earns a genuine accept (a real, distinct, not-found-passing render that also clears the content-novelty gate), the group is confirmed; siblings the per-candidate probe *rejected* are replayed as findings (eagerly on confirmation, with an end-of-run backstop for the race where a sibling's probe finishes after the flush), and a sibling of an already-confirmed group is recorded without re-probing at all. Recovered siblings deliberately **skip the content guards** — a flaky/incomplete render is exactly the signal being distrusted, and re-checking it could only re-lose them; the *confirming* sibling still passed every guard. The safety invariant that keeps this from being a weakened guard: it only ever *adds* siblings to an already-confirmed group, so it can never confirm a group with zero genuine accepts — it recovers the flaky-lost siblings of a real finding, never manufactures one. Promova's `73 → 76..84` plan siblings and ejoy's `1030 → 1032/1033/1034/1035` locked lessons are the motivating groups.

   **Negative group inference and route dedup (cost).** The mirror holds too: once `analysis.clientRoutingGroupRejectAfter` (default 3) siblings of a group were rejected by a redirect-away to the *same* target, the remaining siblings are skipped (stashed, so a later genuine confirmation still recovers them). Only redirect-aways count — they are deterministic, unlike the inert/capture false negatives of a flaky probe. Client-routing probes are also deduped by canonical candidate route rather than per reference page, so a route proposed from several sibling pages of one template is probed once. On clozemaster — 10 visited stories, each matching a catalog card with ~508 paid siblings, all bounced to `/pro` — the two together replace 5 080 live probes with a handful.

   **A candidate swaps a resource identity, not a single token.** The detector's unit is *one sibling resource*, and that identity can be encoded in more than one place in the same url. ejoy's lesson is addressed both by `/app/courses/37/314/<id>` AND by an opaque per-lesson capability in `?path=cp/…/lessons/<id>/<hash>.json`; the content is fetched from the latter. Swapping only the path segment (`1030 → 1032`) leaves `?path=` on the original lesson — an *incoherent* url that renders the original (a false negative) or a Frankenstein page (a false positive). So `evaluateClientRoutingPathCandidate` makes the swap coherent across the url before probing, in two steps, **without generating any new candidate** (one sibling, one probe — no combinatorial fan-out):
      1. **Correlated-field rewrite** ([src/analysis/correlatedQuery.ts](../src/analysis/correlatedQuery.ts), `rewriteCorrelatedQuery`). A query param whose value both embeds the swapped id AND equals a leaf of the reference React node is replaced with that same leaf from the *candidate* (sibling) node. ejoy's `?path=…/lessons/1030/<h0>.json` equals the reference lesson node's `lesson.path`; the sibling node carries lesson 1032's own `lesson.path = …/lessons/1032/<h2>.json` — **including for paid lessons** (`lock:true`), leaked into the free user's state. So the rewrite builds the real paid-lesson url `/app/courses/37/314/1032?path=…/lessons/1032/<h2>.json`, and the probe reaches the paid content. This is the leaked-capability IDOR the detector exists to forge — the same "forge the sibling's request from leaked sibling state" it already does for HTTP, extended to the client-routing url. It fires only when the identity is genuinely duplicated (value equals a node leaf); otherwise it is a no-op.
      2. **Drop if still incoherent** (`urlEmbedsValue`). If the old value still lingers after the rewrite — no correlated leaf matched, e.g. ejoy's courseId `37 → 32`, where `?path=` carries a *lesson* path not found on the *course* node — the one-segment swap can't be reconciled from state and is **dropped**. It is NOT probed on a query-stripped clean path: that tested a different url than the user actually reaches and only produced false positives.

      Downstream records the reconciled `confirmedUrl`; a swap with no duplicated identity (no query to reconcile) is probed exactly as before. Kill switch `analysis.clientRoutingPathCoherence` (gates the rewrite + the incoherent-drop).

   **Cheapest gate first, scoped to the swapped resource.** The authorization check is pure — a diff of the two React nodes' props (`compareObj`) classified against the cached entitlement model (`assessAuthZ`) — with no network and no live browser. So every evaluator runs it (`authzGate`) **before** forging a request or launching a client-routing probe: a candidate whose props carry no entitlement signal is rejected for free, skipping the whole expensive half of the pipeline. Before classifying, the diff is **scoped to the swapped resource** (`scopeDiffsToResource`): only diffs under the swapped value's parent object are considered. This stops a whole-component swap (a nav/sidebar/layout sibling) from passing on a generic key that sits elsewhere in it — ejoy's `37 → 45` swaps a menu item's `items.0.id` yet "passed" on the top-level `user` object; scoping to `items.0` drops `user`, so the section-swap false positives vanish. A real entitlement is a sibling of / nested within the swapped id and survives (ejoy's `lesson.lock` under `lesson.id`, pimsleur's `miniLesson.isFree` under `miniLesson.id`); a swap whose id is itself top-level (busuu/lingualeo `id`) keeps every diff, losing nothing. This scoping is what makes the classifier's `THRESHOLD` safe to lower to **0.30** (from RAPIDOR's 0.33) — enough to catch a bare single-word flag that frames just under, ejoy's `lock` (`whether lock` = 0.307, the sole signal of `lock: false → true` on a paid lesson) — without readmitting the generic nav keys the lower bar would otherwise flag, because they now sit outside the scoped subtree. The threshold is applied at read time (recomputed from the cached score), so changing it needs no `CLASSIFIER_VERSION` bump. This is otherwise a behavior-preserving reorder (the two gates are an AND); the relevance verdict is also the **high-suspicion** signal that licenses the stage-3 full-navigation escalation above.

   **Three more gate rules (duolingo).** (1) The diff AT the swap path — the identifier being swapped — is excluded before classification (`excludeSwapDiff`): it differs by construction, so it can never be its own entitlement evidence (duolingo's `/settings/account -> /settings/privacy` passed only because the swapped href value read like an authz term). (2) An identifier slot keeps its type (`sameIdShape`, at generation, main and ablation): a numeric URL value is only swapped for a numeric one and a non-numeric for a non-numeric one, compared on the string form so a React `1` and a `'1'` are both numeric — a cross-type swap means the component groups different kinds of links (duolingo `relative_domains=1 -> privacy`). (3) `NON_AUTHZ_TERMS` (currently `privacy`) are never authz-relevant, whatever their embedding score: privacy pages are the user's own, never a paid resource. Verified offline on every stored finding: no reference TP is affected.

   - **Inert value** (always applied, even when the network or a param read corroborates the probe): candidate vs reference. No changed text node and no element-count change beyond the noise, under *both* capture mechanisms, means the swapped value changed nothing on the page, so the candidate is rejected. A DOM mutation alone is not new content: lingualeo's `buy/...?refclmark=2 -> 1` re-fetches `_next/data/...json?refclmark=1` (a 2xx carrying the value) and re-renders exactly the same page.
   - **Not found** (only when nothing corroborates): the candidate vs the app's not-found page, calibrated once per route template **and capture mechanism** by rendering a garbage id in the same slot. Rejected when both the changed-text-node fraction and the element-count fraction are within `analysis.notFoundDomMaxDiff`.

   Candidates are also **seeded from the crawler's own visited page URLs**, not only from `http_events`: a value an SPA only ever reads client-side never shows up in any request, yet is still tested via the client-routing probe.
7. **History filter** — before any request or probe, a candidate URL that the crawler already reached on its own (checked against the union of `http_events`, `react_states` and `crawl_states`) is skipped: swapping in a value the user can already reach by clicking around is not evidence of unauthorized access.

A finding's id (`vulnerabilityId`) is a **semantic** key: the swapped sibling pair (`stateId` + reference node + candidate node + swap `path`) scoped to the layer it was observed at (`origin` of the candidate URL + `method`). The same sibling swap surfaced through several carrier URLs on one layer (promova's page SSR flight under two plan ids) collapses to one row, while an API-backend leak, a page-SSR leak and a client-routing leak of the same pair stay distinct findings (promova: 41 → 25 rows, no TP lost). A **client-routing** finding keys on the leaked route instead (the reconciled `candidateUrl`): the same lesson reached from two reference pages collapses to one, while sibling lessons keep their own routes — deterministic, where the live content key cannot tell locked siblings apart (ejoy a stable 4/4).

A flagged finding (`vulnerabilities` table) records which detection path caught it (`detectionMethod: 'http' | 'client-routing'`), the reference/candidate URLs, a human-readable `motivation` (which props differ and how), and the **position of the mutated value** in the URI (`segment_location` `'path'`/`'query'` + `segment_index`, the 0-based index from the right for a path segment) for the paper's identifier-position figure. Everything above — including every stat that used to only exist transiently (segments extracted, matches found, candidates found, HTTP events, React states, requests generated, vulnerabilities flagged) and the wall-clock time of the exploration and analysis phases (`exploration_ms`/`analysis_ms`, logged as `hh:mm:ss.mmm`) — is persisted per site in `analysis_stats`; inspect it with `npm run stats` (see [Statistics](../README.md#statistics)). `analysis_stats` also carries paper-support splits per app: `http_events_unique` (distinct canonical events), `http_forged`/`client_probes` (the split of `requests_generated` by detection path), `vulns_http`/`vulns_client` (findings per class), and `clickables_per_state_mean`/`clickables_per_state_median` (UI complexity). `npm run paper-stats` aggregates these across all applications (mean/median/mode) and emits the figure CSVs.

## Reproduction scripts

Right after a genuinely new finding is recorded (by any of the three paths: forged HTTP request, client-routing on a query param, client-routing on a path segment), [src/analysis/reproductionScript.ts](../src/analysis/reproductionScript.ts) writes a standalone `reports/<site>/<site>_<vulnType>_<timestamp>.repro.ts` (`vulnType` is `http`, `client-query`, or `client-path`; `timestamp` includes milliseconds, so concurrently-evaluated candidates never collide). It is self-contained — the original request/response and both nodes' React props are embedded in the file itself, so it never depends on `storage/crawler.db` (which a later crawl, `db.clearOnStart` being the default, wipes):

```bash
npx tsx reports/<site>/<site>_<vulnType>_<timestamp>.repro.ts
```

All three finding kinds go through the **same flow**: a real (non-headless) browser opens, navigates to the original URL/request and the mutated one, and a DOM snapshot and a screenshot are taken of each — for an HTTP finding this means opening the reference and candidate URLs directly (skipped, with a message, for a non-`GET` method, which can't be replayed by opening a URL); for a client-routing finding the probe runs via `pushState`+`popstate` (informational), then the candidate page is opened by a real navigation — the content guard's own mechanism — for the DOM diff and screenshots. The script then prints, in order:

1. the **original** request/response (http) or page (client-routing);
2. the **mutated** request/response (a live, fresh request) or page;
3. the **DOM diff** of the two pages — the same normalized comparison the pipeline's guards use (`domSnapshot.ts`, each side masked with its own value), listing every changed text node (`- before` / `+ after`, first 20) and the element counts. This is the verdict signal; with a single capture per side there is no self-noise calibration, so read the listed lines before trusting a "changed" verdict;
4. the two **screenshots** (`<baseName>.original.png`, `<baseName>.mutated.png`) and their pixel diff (`<baseName>.diff.png`, `pixelmatch`/`pngjs`) — **visual evidence only**, never a criterion;
5. the **verdict**: response similarity (http) or the probe result (client-routing), followed by the DOM diff's verdict ("content changed" vs "content IDENTICAL — most likely a false positive");
6. the **React props** of the original node and of the node whose value was spliced into the mutated request/URL, plus the authorization-relevant differences and the keys the classifier flagged.

A failure while generating a script never prevents the finding itself from being recorded.

## Re-analysing later: entry-point auth gate + refresh

Exploration (t1) and a `runAnalysisFromDb` re-analysis (t2) can be far apart, but the forge needs a live authenticated session. Two pieces keep a t2 run honest when the t1 session has expired, without re-crawling:

- **Entry-point gate** ([src/analysis/authFreshness.ts](../src/analysis/authFreshness.ts), `checkEntryPointFresh`). Before analysing, the `START_URL` — an internal *authenticated* page — is re-rendered and its live React `graph.fingerprint` is compared to the fingerprint(s) captured at that URL during the crawl (`ReactStateStore.fingerprintsForUrl`). An exact match means the session is alive. A mismatch alone is *not* expiry — a dynamic entry page renders a new structure on almost every load (duolingo `/learn`: 220 captures, 220 distinct fingerprints while logged in). The gate reports expired only on positive evidence of a login page: the load ended on a different origin (a cross-origin bounce to an SSO/login host — checked first, independent of any seed, since the entry URL often has none: ejoy `/app/courses/37/314` → `sso.ejoyspace.com/?continue=…`), the load left the entry route same-origin (the usual login redirect), a password field is rendered, or the live tree has fewer than half the nodes of the smallest captured state. Expired → abort (exit 2) with instructions. The gate deliberately sits on a resource the user is *entitled* to, decided once up front: a per-forge `403` is **ambiguous** (for a paid-resource IDOR a `403` is the *correct* "no leak" answer), so it never drives re-authentication and can never cause a re-auth loop. It uses structure (`graph.fingerprint`), not the content key — the page's data legitimately changes between t1 and t2, its structure collapses only on the login page. Conservative on missing evidence (no seed fingerprint, no extension, app didn't mount → proceed).
- **Refresh without re-crawl** ([scripts/refreshAuth.ts](../scripts/refreshAuth.ts) → `session_auth` → `applyAuthOverride`). On EXPIRED, re-login by hand through `refreshAuth`, which stores a per-site `AuthOverride = { stripCookie, freshHeaders }`: **stripCookie** drops the captured `Cookie` header so the forge's `page.request.fetch` uses the re-authenticated context's fresh cookies (cookie-auth sites); **freshHeaders** overlays the harvested header-auth (bearer token etc., `config.analysis.volatileAuthHeaders`, default `authorization`) onto every forged request (header-auth sites). `applyAuthOverride` is pure and a no-op when no override is stored, so the common path (token never expired) forges the captured headers verbatim. `session_auth` survives `clearOnStart` (it mirrors the live profile session), and `refreshAuth` clears the site's `forged_requests` so no response forged under the dead session is reused. Only the HTTP forge needs the override — client-routing probes navigate in the re-authenticated context and pick up the fresh session automatically. Two fresh profiles are assumed to carry the same privileges.

## Ablation study (HTTP-JSON-only)

`analysis.ablationMode` (default `false`, `ABLATION_MODE=true` to turn it on) runs a second, independent analysis pass — [src/analysis/AblationPipeline.ts](../src/analysis/AblationPipeline.ts) — alongside the main one, to measure how much of what the React-informed pipeline finds actually required React state at all, versus how much was sitting in plain sight in the JSON the site's own API already returned. No new network monitoring and no new exploration: it reuses the exact same `http_events`/`crawl_states` the main pipeline already captured.

* **Preindex** ([src/analysis/jsonMatchFinder.ts](../src/analysis/jsonMatchFinder.ts), `buildJsonPreindex`) — every already-captured JSON response body for the site is walked once (same depth cap and "interesting key" rules as the React preindex — `isInteresting`/`tokenize` are reused verbatim), building a `value -> {body, path}[]` index. A URL segment is then looked up against the *whole* corpus, not just "its own" response: the id a request's own URL carries is often only ever *returned*, alongside its siblings, by a completely different endpoint (a list/listing call), not by the per-item endpoint whose own URL happens to contain it.
* **Sibling finding** (`findJsonCandidates`) — once a match lands inside some body, siblings are looked for at *every* enclosing array level along that match's path (not just the nearest one), each level varied independently while every other index stays fixed at its reference value — the JSON analog of `matchFinder.ts`'s `componentIndex` walk. Sibling-finding itself never crosses bodies: two different HTTP responses are never assumed to describe related data just because a value happens to appear in both.
* **Combinatorial explosion, and why it is the ablation's defining property** — candidate count ≈ Σ over matched values of (distinct URLs carrying the value as a segment) × (bodies it matches) × (array siblings). On a large corpus this blows up: promova's ablation generates **~4.8M distinct forge GETs** vs the main pipeline's ~12.5k. The amplifier is **low-entropy values** — a tiny integer like `"1"` is a page number / version / flag in thousands of URLs yet coincidentally sits under an `id`-like key in a few JSON bodies. The main pipeline filters these for free: such a value saturates the rendered DOM (> `maxSegmentMatches` React nodes) and is skipped. The sparser JSON corpus holds `"1"` in only ~28 bodies, so the hit-count cap never fires — React state is an implicit **saliency prior** the HTTP-JSON analysis lacks, and its absence *is* the explosion. Two mitigations keep it runnable without hiding the result: (a) **carrier-cap** — the ablation also skips a value carried by more than `maxSegmentMatches` *distinct request URLs* (the piece the main gets free from the DOM's redundancy); on promova, dropping 7 such values (`0,1,3,6,8,11,1080`) cut candidates 12×. (b) **per-site forge budget** (`analysis.maxGeneratedRequests`, 10k, shared with the main pipeline): if generation still exceeds it, the site is **abandoned and recorded `infeasible`** (a column on `ablation_stats`/`analysis_stats`) rather than firing millions of live GETs (both pipelines early-abort generation once the budget is exceeded, so an infeasible site never materialises its full task list) — a memory, time (~45-min budget) and ethics bound. promova's ablation → `infeasible`; its main (~6.4k after volatile-param dedup) stays feasible. `infeasible` means "not evaluated", distinct from "0 findings".
* **Volatile params** — `normalizeUrl` drops cache-busting noise before dedup/history comparison, so duplicates of one request (RSC navigations, or an endpoint re-fired on every restore) count once. Next.js RSC `_rsc` is matched by **name**; cache-buster **timestamps** are matched by **value shape** — any query param whose value is a 10-digit (epoch seconds) or 13-digit (epoch ms) integer in the ~2001–2033 window — which is robust to however a site spells the param (`_`, `ts`, `t`, promova's `tft`, …) where a name list would miss it. The **key disambiguates** the value: a param whose name is identifier-like (`id`, `userId`, `uuid`, `token`, …) is never stripped, so a real id that happens to resemble an epoch survives. The forged request still carries the original's params, so its response stays comparable.
* **Same candidate blacklists** — the ablation applies the same `analysis.paramBlacklist` (by name AND token, via `paramNameBlacklisted`), the locale filter (`isLocaleParam`) and the tracking filter (`isTrackingParam`), and `analysis.segmentBlacklist` as the main pipeline: a pagination/sorting query param (`curPage`, `limit`, …), a locale/tracking param, or an app-shell/section path root is never mutated, nor used as a replacement value. The ablation shares every analysis rule and differs ONLY in using JSON siblings instead of React ones; the caps above (hit/carrier) are additional to these blacklists, not a substitute for them.
* **Oracle** — identical to the main pipeline's HTTP path: forge the candidate request (`requestForge.ts`), compare the response (`responseEvaluate.ts`), diff the two sibling objects' properties (`compareObj`), classify the diff for authorization relevance (the same shared `authzClassifier.ts`, same cache), and apply the same always-on **HTTP content-identity guards** (already-accessible-data + cross-candidate dedup + the empty-data guard, see step 5 above). `compareObj` recurses index-wise into arrays (not just plain objects) for both pipelines, deliberately: the fairest ablation gives the HTTP-only analysis every tool the React-informed one has, so any remaining gap in what each pipeline flags reflects a real difference in signal (React state vs. JSON alone), not an avoidable blind spot shared by both. (The one oracle difference kept on purpose: the ablation has no `isIdenticalResponse` gate, its documented weakness.)
* **Shared forged-request cache** ([src/db/ForgedRequestStore.ts](../src/db/ForgedRequestStore.ts)) — keyed by `(site, method, url, body)`: if the main pipeline already forged the exact same candidate (the two often propose the same id swap from two different sources), the ablation reuses that response instead of hitting the live site again, and vice versa.
* **Structurally narrower by construction, not by omission** — there is no equivalent of the client-routing probes: those resolve their oracle from a DOM-mutation signal (did the app's own rendering react?), which has no network counterpart at all. A query param or path segment an SPA only ever reads client-side is invisible to a network-only analysis, full stop.

Findings land in their own tables — `ablation_vulnerabilities`/`ablation_stats` — never mixed with `vulnerabilities`/`analysis_stats`, so the two are always comparable:

```bash
ABLATION_MODE=true START_URL=https://example.com npm start
ABLATION_MODE=true npx tsx scripts/runAnalysisFromDb.ts https://example.com   # re-run BOTH passes on already-captured data (no new crawl); the ablation runs after the main analysis, same as the end-of-crawl ordering
npm run compare-ablation                               # side-by-side stats + which findings the main pipeline caught that the ablation missed, by detectionMethod
npm run compare-ablation -- --db storage/other-run.db
```
