# IDOR analysis: invariants (do not break)

- **Scope.** RAPIDOR detects unauthorized access to **paid / higher-privilege** resources within the SAME session (e.g. a free user reading a paid lesson via an id swap) — NOT access to another user's data. The entitlement signal is the authz-relevant props diff (e.g. `free: true -> false`). A finding whose forge returned 200 with paid content while authenticated is a true positive even if it can't be reproduced later (see the auth-freshness note).
- **GET only.** `requestForge.forgeRequest` refuses non-GET methods, and candidate generation skips non-GET events. Never relax this: replaying POST/PUT/DELETE changes state on real sites.
- Forged requests go through `page.request.fetch()` so they never pollute `http_events`. Go through `forgeRequestCached` (`forged_requests` table, shared with the ablation).
- **Semantic finding dedup key** (`vulnerabilityId` in `findings.ts`, consumed by `VulnerabilityStore.record`'s `INSERT OR IGNORE`): the id keys on the SIBLING PAIR being swapped (`stateId` + `referenceNodeId` + `candidateNodeId` + `path`) scoped to the LAYER the leak was observed at (`candidateUrl`'s `origin` + `method`). Two findings with the same key describe the same IDOR on the same surface — same pair of React component instances, confirmed via the same layer — so they collapse to one row. The key deliberately EXCLUDES the full `url`: multiple carrier URLs can embed the same reference value (promova's step id 73 appears on page SSR flight, on a backend API endpoint, and on a second plan's page URL — three carriers, one sibling pair), and keying on url produced one row per carrier (promova: 37 rows for 9 real leaks). It INCLUDES `origin+method` to preserve the auditor-visible distinction between layers: an API-backend leak (`courses.api.promova.com:GET`), a page-SSR leak (`promova.com:GET`), and a client-routing leak (`promova.com:CLIENT`) are DIFFERENT findings, even for the same sibling pair — different surfaces, different mitigation. It INCLUDES `path` so the same sibling pair matched from two different preindex values at two different fields (`lesson.id` vs `aliasId`, rare but possible) stays distinct. Within one layer, carrier variation (plan segment, `_rsc` cache-buster, …) collapses because the key doesn't mention the url. First arrival wins (the stored `candidate_url` is from whichever carrier reached `recordFinding` first). Change here → re-run `recheckFindings` on the 4 reference sites (the key is deterministic, so the stored id of an existing run won't match after the change, but recheck replays stored rows verbatim, not by id).
- **Authz classifier**: if you change normalization or embedding in `authzClassifier.ts`, bump `CLASSIFIER_VERSION`, otherwise stale rows in `authz_classifications` (never wiped by default) get reused. The `THRESHOLD` (0.30) is NOT part of that: it is applied at READ time (recomputed from the cached `score`), so changing it needs no version bump and reuses the persisted scores. It is 0.30 (down from RAPIDOR's 0.33) to catch a bare entitlement flag that frames just under — ejoy's `lock` (`whether lock` = 0.307, the sole signal of `lock: false -> true`) — and is only safe because the gate scopes the diff first (next bullet).
- **Non-authz terms** (`NON_AUTHZ_TERMS` in `authzClassifier.ts`, currently `privacy`): a term with ANY normalized word in the set is never authz-relevant. Applied at read time in `classify`, before cache/model — like `THRESHOLD`, live policy, so NO `CLASSIFIER_VERSION` bump. For words the embedding model reads as access control that never mark a PAID resource (privacy policy/settings are the user's own pages). Keep it short and justified per word: a word added here is invisible to the gate on every site.
- **HTTP forge**: an HTTP forge whose response is identical to the original (`isIdenticalResponse`: byte-equal or deep-equal JSON) is NOT an HTTP finding — the server ignored the swapped value (busuu `checkout.json?price_id=A->B` returned the same 65 KB payload). It falls through to the client-routing fallback, it is not accepted on response "similarity".
- **Error-status guard** (always on, HTTP): a forged response with status `>= 400` is never an HTTP finding — the server denied/errored (401/403 = access denied), so nothing was reached. Dropped before recording. Also keeps an expired-token run honest (every forge 401/403 → nothing flagged, never a stale 200 trusted).
- **Error-envelope guard** (`isErrorEnvelopeResponse`, always on, HTTP main + ablation): a forged 200 whose TOP-LEVEL JSON is an error/denial envelope — truthy `error` (bool `true`, non-zero number, non-empty string/object), `success:false`/`ok:false`, or `status:"error"/"fail"/"failure"` — reached nothing, so it is never a finding, however "similar" the ratios call it (the similarity check is purely relative, so two short bodies pass). Applied right after the empty-data guard in `candidateEvaluator` and `AblationPipeline`. TOP-LEVEL only (a nested `error` inside a genuine resource is content, not an envelope); drops only on positive evidence (a non-object / non-JSON body returns false → kept). It generalizes the empty-data guard to error stubs that carry real-looking fields beside the flag (`{"error":true,"errorCode":…}`); a bare `{"error":true}` is already caught by empty-data (`error` is a metadata key). Do NOT replace it with a blunt "too-few-keys" floor: 19 genuine busuu HTTP findings have 2 top-level keys and real APIs wrap rich data under few keys, so a key-count floor drops true positives.
- **Empty-data guard** (`isEmptyJsonResponse`, always on, HTTP main + ablation): a forge that returns no actual data — `{}`, `[]`, or an all-empty wrapper (`{"data":{"data":[],"total":0}}`) — leaked nothing, so it is never a finding, however much it differs from the reference. Applied right after the error-status guard in `candidateEvaluator` and `AblationPipeline`. A body is empty when every array is empty and every remaining scalar sits under a narrow metadata key (`total`/`count`/`size`/`status`/…); an id/name/title/slug or any non-empty array is content. Drops only on positive evidence: a non-JSON body (HTML 404) returns false → kept. NOTE the ablation's `search-new?size=…`-style FPs are a different class (real data differing only by a pagination param); the ablation lacks the param-name blacklist by design, so those stay (the studied weakness).
- **Client-routing ALREADY-ACCESSIBLE guard** (`reactContentKey`, analysis/reactFingerprint.ts): a client-routing finding is dropped when its candidate route's live-rendered React state is **already-collected** — its key is in some `react_states` row, a page the user already reaches at a different url (e.g. `/terms/press-center` rendering the crawled `/press-center`). The key = structural `graph.fingerprint` + the identifier-like leaf values (`collectPreindexRows`). `CandidateEvaluator.primeReactHistory` builds the corpus offline from `react_states`; `ClientRoutingVerifier.captureReactContentKey` reads the candidate's state via the extension (a real navigation — a synthetic popstate often does NOT update a Next.js tree, and it waits `networkidle + settle` so a fetch-gated route's own content has LANDED before hashing) AFTER the verifier accepted, so the guarded ladder is untouched. No extension → key `undefined` → finding KEPT (never a wrongful drop). **The cross-candidate DUPLICATE check that also lived here was REMOVED**: it keyed on the same live reactContentKey, which renders a near-identical PAYWALL SHELL for every locked sibling (ejoy's 1033 vs 1035 hash equal), so distinct paid lessons collapsed and ejoy flipped between 2/4 and 1/4 run-to-run. Cross-candidate dedup for client-routing is now DETERMINISTIC on the leaked ROUTE, in `vulnerabilityId` (`clientRoute` = `normalizeUrl(candidateUrl)`): the same lesson reached from two reference pages (1032 proposed from both the 1030 and 1031 pages, each rewritten to `…/1032?path=…/1032/…`) collapses to one finding, sibling lessons keep their own routes → ejoy a stable 4/4. Do NOT reintroduce a content-hash duplicate check for client-routing: the route key is exact and the paywall shell is not.
- **Entry-point auth-freshness gate** (`checkEntryPointFresh`, `runAnalysisFromDb` only): before analysing, re-render the `START_URL` (an internal authenticated page) and compare its live React `graph.fingerprint` to the one(s) captured at that URL at crawl time (`ReactStateStore.fingerprintsForUrl`). An exact match → session alive. A MISMATCH IS NOT EXPIRY: a dynamic entry page renders a new structure on almost every load (duolingo `/learn`: 220 captures, 220 distinct fingerprints, logged in — the old exact-match gate reported EXPIRED forever and `refreshAuth` could never fix it). EXPIRED needs POSITIVE evidence of a login page: (a0) the load ended on a DIFFERENT ORIGIN — checked FIRST and independent of any seed fingerprint, because the entry URL often has none and a cross-origin bounce to an SSO host is unambiguous (ejoy `/app/courses/37/314` → `sso.ejoyspace.com/?continue=…`), (a) the load left the entry route same-origin (`sameRoutePath` — the usual login redirect; duolingo logged-out → `/`), (b) a password field is rendered, or (c) the live tree has < 0.5× the nodes of the smallest captured state (`ReactStateStore.nodeCountsForUrl`). Otherwise → fresh ("new structural variant"). EXPIRED → warn (`scripts/refreshAuth.ts`) and abort (exit 2). The signal MUST be the entry point (a resource the user is entitled to), never a per-forge 403: for a paid-resource IDOR a forge 403 is the CORRECT "no leak" answer, so using it to trigger re-auth would loop. The gate is the ONLY auth trigger; nothing in the forge path re-authenticates. Conservative on missing evidence (no seed fingerprint / no extension / app didn't mount → `fresh:true`, proceed). Use `graph.fingerprint` (STRUCTURE), not `reactContentKey` (structure+data): the entry page's DATA legitimately changes between t1 and t2, its STRUCTURE collapses only on the login page. The end-of-crawl analysis runs in the just-authenticated session, so it needs no gate.
- **Auth refresh without re-crawl** (`scripts/refreshAuth.ts` → `session_auth` → `applyAuthOverride`): when the gate is EXPIRED, re-login manually and re-point the forge at the fresh session instead of re-crawling. `refreshAuth` stores a per-site `AuthOverride` = `{ stripCookie: true, freshHeaders }`: **stripCookie** drops the captured `Cookie` so the forge's `page.request.fetch` uses the re-authenticated context's fresh cookies (cookie-auth: busuu/lingualeo); **freshHeaders** overlays the harvested header-auth (bearer etc., `config.analysis.volatileAuthHeaders`, default `authorization`) onto every forged request (header-auth: pimsleur). `applyAuthOverride` is pure and a NO-OP when the override is absent, so the common path (token never expired) forges the captured headers verbatim — zero behaviour change. `session_auth` is NOT wiped by `clearOnStart` (it mirrors the live profile session). `refreshAuth` also clears the site's `forged_requests` so no response forged under the dead session is reused. Only the HTTP forge needs the override; client-routing probes navigate in the re-authenticated context and get fresh auth automatically. Assumes two fresh profiles carry the same privileges.

## Client-routing IDOR verification (`clientSideConfirmed`) — justified, do not regress

This logic was rebuilt to kill real false positives (lingualeo `refclmark`, the busuu redirect-away) WITHOUT losing real findings (pimsleur 4/4, busuu objective siblings, lingualeo `wordTranslate` siblings). Every rule below exists because a specific site broke without it — change it only with a `recheckFindings` run on all four reference sites (see Regression checks) proving no loss.

- **Cheapest gate first — the authz gate precedes every live probe/forge.** Each evaluator calls `authzGate` (pure: `compareObj` of the two React nodes' props + `assessAuthZ`, cached) BEFORE forging a request or running a client-routing probe; a candidate with no entitlement-relevant props diff is rejected for free. This is a behavior-preserving reorder (every path already required `isAuthzRelevant` to record — AND is commutative), it only moves the cheap check earlier. Its verdict is also the **high-suspicion** signal that licenses the stage-3 escalation below — do not record a finding that skipped it.
- **Authz gate is SCOPED to the swapped resource** (`scopeDiffsToResource`, always on in `authzGate`): classify only diffs under the swapped value's PARENT object, not the whole component. A whole-component swap (a nav/sidebar/layout sibling) must NOT pass on a generic key that sits elsewhere in it — ejoy's `37 → 45` swaps a menu item's `items.0.id` yet passed on the top-level `user` object; scoping to `items.0` drops `user`. A real entitlement is a sibling of / nested within the swapped id and survives (`lesson.lock` under `lesson.id`; pimsleur `miniLesson.isFree` under `miniLesson.id`). A swap whose id is itself TOP-LEVEL (parent is root — busuu/lingualeo `id`) keeps every diff, so nothing is lost (lingualeo's `user`-VALUE finding survives). Verified against every reference finding's stored `authz_diff` before enabling; it is what makes the 0.30 threshold safe. React/main pipeline only — the ablation's JSON candidate path is element-relative (`relPath` folded into `candidatePath`) and would need separate plumbing to scope.
- **The swapped identifier is never its own entitlement evidence** (`excludeSwapDiff`, in `authzGate` after `scopeDiffsToResource`): the diff AT the swap path differs by construction, so it is dropped before `assessAuthZ` (the recorded `differences`/motivation still keep it). The signal must come from ANOTHER property (`lesson.lock` beside `lesson.id`). Motivating FP: duolingo `/settings/account -> /settings/privacy`, whose ONLY sensitive key was the swapped href VALUE `privacy` (the value-as-authz-term rule). Verified offline on every stored finding before enabling: only that FP lost its keys (pimsleur 4, lingualeo 19, promova 25, mondly 20 all keep theirs). Main pipeline only.
- **Probe gate = STAGE 1, no longer a hard veto.** The cheap pushState probe's `hasMutatedDom && stayedOnRoute` (the SPA rendered the candidate's own route and stayed on it) decides stage 1. A redirect-away or no reaction is now INCONCLUSIVE, not an automatic rejection: it falls through to the stage-3 escalation, but ONLY for a high-suspicion candidate, and that stage re-imposes the same safety (a redirect-away is still rejected there, via `sameRoutePath` on the post-goto URL — the busuu `dashboard/review -> dashboard/timeline` guard). A non-high-suspicion inconclusive candidate is still rejected outright.
- **Network is a filter, not a veto**: a `2xx` carrying the candidate value (or a hooked `URLSearchParams.get`) *corroborates*; a `4xx` on an incidental request does NOT reject. Attribution is boundary-aware (`urlCarriesValue`: whole segment or whole param value, never a substring — `298` must not match `6140298`).
- **Content guard runs even when corroborated.** A `2xx` cannot tell a real leak from an ignored tracking param (lingualeo `refclmark=1` returns a 2xx for a byte-identical `_next/data` JSON), so the **inert-value** check (candidate DOM == reference DOM) ALWAYS runs. Only the **not-found** check is skipped when corroborated.
- **DOM, never screenshots.** Compare normalized DOM snapshots (`domSnapshot.ts`: text nodes + `<img>` src + element count). Screenshots are viewport-bound, hidden by `lightweightMode`'s placeholder assets, and blind to a one-string change. Do not reintroduce a pixel diff as a *criterion* (it may stay in reproduction scripts as evidence only).
- **Mask BOTH values** out of every side before comparing. A stale pushState render shows the *reference* value in the candidate's content; masking each side with only its own value makes a stale render look falsely different (and match the stale not-found baseline). Masking both makes a stale render read inert → fall through; a real leak still differs by its own data.
- **Remount-noise calibration**: render the reference twice, bracketing the candidate's own render, and ignore the paths that differ between those two (lingualeo training pages draw random quiz words every load) — EXCEPT a path where the second reference render shows the candidate's text (a stale render, not noise). Do not cache the reference render per page: the bracket must be per candidate.
- **Stage-3 escalation is RETRIED on a flaky reject** (`confirmByFullNavigation` loops `config.analysis.clientRoutingEscalationAttempts` times, default 2; split into `confirmByFullNavigationOnce`). Unlike the pushState probe (retried 3×), the strict real-load stage used to be single-shot, so one incomplete render of a fetch-gated route (ejoy's lessons load content by id over XHR) read as a false NEGATIVE — flipping which paid siblings surfaced run-to-run (ejoy's locked 1032/1033/1034/1035: a different 2 of 4 per run). Retry ONLY on a flaky reject — capture failed / inert / not-found; an ACCEPT (null) returns immediately, and so does a DETERMINISTIC redirect-away (`REDIRECT_AWAY_PREFIX`, re-navigating can't change it). It can ONLY recover a finding, never lose one (a genuine inert/not-found still rejects on the last attempt). Cost is bounded (fires only on a high-suspicion candidate that reached stage 3 AND got a negative); lower the knob to 1 on a huge site if the budget is tight. A change here is decision-logic → `recheckFindings` on the 4 sites.
- **Client-routing sibling-group confirmation** (`CandidateEvaluator.clientGroup*`, the two pure client-routing evaluators): the probe is flaky on fetch-gated routes (ejoy's locked lessons fetch content by id over XHR, so one real load can snapshot an incomplete render and read as a false negative), flipping which paid siblings surface run-to-run. Siblings of ONE reference node that share the swap `path` AND the authz-relevant keys are structurally identical resources behind the same route, so a genuine confirmation of one is a logical consequence for all. The group key = `pageUrl` + `stateId` + reference `nodeId` + swap `path` + sorted authz `sensitiveKeys` (a different authz signature forms a different group — no cross-confirmation of unrelated entitlements). A genuine accept (a real, distinct, not-found-passing render that ALSO passes the content-novelty gate) confirms the group; a sibling the per-candidate probe REJECTED is stashed and replayed once the group is confirmed (eagerly on confirm, plus `finalizeClientGroups()` as an end-of-run backstop for the stash-after-flush race); a sibling of an already-confirmed group is recorded WITHOUT re-probing. Recovered siblings SKIP the content guards by design — the flaky/incomplete render is exactly the signal we distrust, and re-running a flaky capture could only re-lose them (the CONFIRMING sibling still passes every guard). **SAFETY (the invariant that keeps this from being a weakened guard):** it only ever ADDS siblings to an ALREADY-confirmed group — it can NEVER confirm a group with zero genuine accepts, so it recovers the flaky-lost siblings of a real finding and never manufactures a finding where the detector found nothing. Promova's `73 -> 76..84` plan siblings and ejoy's `1030 -> 1032/1033/1034/1035` locked lessons are the motivating groups. Decision-logic change → `recheckFindings` on the 4 reference sites (a confirmed-but-FP group will now surface ALL its siblings, so re-check promova's mix before trusting the count).
- **Three stages, cheapest first — keep ALL.** `clientSideConfirmed` is an explicit ladder; the first stage to reach a verdict wins, inconclusive falls through, the real load is always last. (1) **pushState** (no reload; the mechanism a genuinely client-routed SPA honours — pimsleur/busuu decide here with no extra network). (2) **SSR navigation fallback (lenient)**: a real `page.goto` reached when stage 1 passed the probe gate but rendered INERT, because an SSR route (Next.js) renders content only on a server load (lingualeo `/en/training/<type>`: 0 nodes under pushState, ~96 on a real load); a failed capture here KEEPS (the app already proved client digestion), but a real load the app REDIRECTED AWAY from (`sameRoutePath` on the post-goto URL) is a REJECT, same as stages 1 and 3 — lenient means "keep on missing evidence", never "accept a redirect": clozemaster bounces every paid story to `/pro`, whose upsell DOM differs from both the reference and the not-found baseline, and stage 2 without this guard flagged 101 FPs (recheck: 0/101 after the fix). (3) **Strict full-navigation escalation**: a real `page.goto` reached when stage 1 saw NO digestion (no reaction / redirect-away), run ONLY for a high-suspicion candidate (ejoy: Next.js ignores a synthetic popstate for a sibling lesson, so stage 1 is blind, yet a real load renders the sibling). Stricter than stage 2 because no prior client-routing signal backs it: a redirect-away (`sameRoutePath`) or a failed capture is a REJECT, not a keep. Never drop pushState for goto-only: a purely client-trusting route (server would reject a direct load, SPA renders from loaded state) is visible ONLY via pushState. Never drop stage 2: SSR routes are invisible to pushState. The stage-2 and stage-3 content verdict runs the SAME `judgeRenderedContent` as pushState, so the accept bar is identical across stages. Kill switch for the stage-3 escalation: `config.analysis.clientRoutingFullNavigationEscalation`.
- **Wait for network idle before snapshotting** (`waitForLoadState('networkidle')`, bounded, best-effort, in both capture fns). A fetch-gated route (pimsleur loads each lesson by id via XHR) has `load`/popstate fire on the shell while content is still coming; a fixed settle alone catches the shell (or a cookie wall) and silently drops real findings. This is the reliability fix that keeps pimsleur at 4/4 — do not remove it.
- **Not-found baseline must be usable.** The garbage-id baseline rejects a candidate only when it is itself meaningfully different from the known-good reference page. If garbage ≈ reference (a soft-404 app, or a failed/cookie-walled render where everything is the same shell), "looks like garbage" proves nothing, so back off and keep. Baselines are cached per (template, mechanism).
- The client-routing phase runs on a pool of pages (`withPooledPage`). One probe per page at a time, because it mutates the live DOM. The probe is retried up to 3×, on the same page.
- **Client-routing probes are deduped by CANONICAL CANDIDATE ROUTE** (`client|path|<normalizeUrl>` / `client|query|<normalizeUrl>` in `AnalysisPipeline`), not per reference page — the same as HTTP's `method|url`. The same route proposed from N sibling pages of one template is ONE probe (clozemaster: 10 visited stories × 508 catalog siblings = 5 080 probes → 508). The reference page only supplies the known-good DOM for the inert/not-found comparison; any page of the template does.
- **Negative sibling-group inference** (`config.analysis.clientRoutingGroupRejectAfter`, default 3, 0 = off; `CandidateEvaluator.clientGroupRejected`): the mirror of the group confirmation. After K siblings of one group were rejected by a redirect-away to the SAME target, the rest of the group is skipped. ONLY a redirect-away counts — it is deterministic (the stage-3 retry already short-circuits on it), whereas probe flakiness produces false negatives on inert/capture, never a redirect. Skipped siblings are STASHED like rejected ones, so a later genuine confirmation still recovers them (confirmation wins). Cuts clozemaster's 508 paid stories (all → `/pro`) to ~K probes. Never count other reject reasons towards it.
- History filter: a candidate URL that is already in `http_events`/`react_states`/`crawl_states` is skipped.
- **Volatile params** (`findings.ts` `VOLATILE_PARAMS`, `['_rsc']`): `normalizeUrl` strips Next.js RSC `_rsc` tokens so two captures of one request differing only by the token canonicalize equal — this is the history filter AND the finding/candidate dedup key. Not a config knob (a framework fact, like `PREINDEXED_KEYS`). Canonicalization ONLY: `candidateUrlFor`/`forgeRequest` still send the original's params, so an RSC request stays an RSC request and its response comparable (don't strip them from the forged request or the baseline won't match). On promova it collapsed ~20 duplicate `_rsc` findings and cut main http candidates 8184 → 1986. Changing this touches every site's history/dedup → re-run `recheckFindings` on the 4 reference sites.
- **Per-site forge budget** (`config.analysis.maxGeneratedRequests`, 10k, main AND ablation): if candidate generation exceeds it, the site is ABANDONED (nothing dispatched) and recorded with `infeasible=1` on `analysis_stats`/`ablation_stats`, not analysed. It is a memory bound (generation early-aborts, never materialising millions), a time bound (≈ `budget × timeBetweenRequestsMs / maxConcurrentRequests`, kept near a ~45-min per-site budget — adjust the three together), and an ethics bound (GET-only, but millions of live requests is a DoS). The main is React-bounded and rarely trips it; the ablation on a large corpus does (promova: ~4.8M → infeasible). `infeasible` is NOT a finding count of 0 — it means "not evaluated"; keep them distinct in any stats/averaging.
- **Ablation candidate caps** (`AblationPipeline`, both reuse `maxSegmentMatches`): the JSON path has no React saliency prior, so a low-entropy value (a tiny integer `"1"` = page number/version/flag) that sits under an id-like key in a few bodies would fan out across every URL carrying it. Skip a value matching more than `maxSegmentMatches` bodies (hit-cap) OR carried by more than `maxSegmentMatches` distinct request URLs (**carrier-cap** — the piece the main gets free from the DOM's redundancy). On promova the carrier-cap alone cut candidates 12× (7 values: `0,1,3,6,8,11,1080`). This is the ablation's own filter; it does not touch the main pipeline.
- **Ablation shares the name blacklists** (`AblationPipeline` applies `paramBlacklist` via `paramNameBlacklisted` AND `segmentBlacklist`, same as `candidateGenerator`): the ablation differs from the main pipeline ONLY in using JSON siblings instead of React ones — every other analysis rule applies, blacklists included. A pagination/sorting query param (ejoy's `curPage`, `limit`, …) and an app-shell/section path root are never mutated (nor used as a replacement value), in the ablation too. Do NOT confuse this with "the ablation lacks the param blacklist" (an earlier, now-fixed weakness): it applies it. The ablation caps above (hit/carrier) are ADDITIONAL to the blacklists, not a substitute.
- **Candidate URLs must preserve the rest of the request.** Build an HTTP candidate's URL with `segments.candidateUrlFor` (sets the one query param on the real URL), never with `spliceSegment` alone: a query candidate's `parts` is only `"<path>?<key>="`, so splicing it DROPS every other param (busuu's `notifications?include_voice=1&limit=5` → `notifications?limit=12538`). That forges a *different* request, attributes the resulting response difference to the swapped value, and robs `isIdenticalResponse` of its meaning. Path candidates still go through `spliceSegment`, which re-attaches the original query. ("Preserve the rest" means do not DROP unrelated params; it is not in tension with the resource-identity reconciliation below, which deliberately rewrites the ONE query copy of the swapped identity.)
- **A candidate swaps a RESOURCE IDENTITY, not a single URL token.** The detector's unit is one sibling resource; that identity is usually one token but can be duplicated in the url (ejoy addresses a lesson both by `/courses/37/314/<id>` AND by a capability in `?path=cp/…/lessons/<id>/<hash>.json`, and the content is fetched from the latter). A one-segment swap that leaves the other copy stale is INCOHERENT (renders the original — FN — or a Frankenstein page — FP). `evaluateClientRoutingPathCandidate` reconciles the whole url to the chosen sibling BEFORE probing, in two steps, **generating NO new candidate** (one sibling, one probe — never mutate tokens independently, that would explode):
  1. **Correlated-field rewrite** (`rewriteCorrelatedQuery`, `correlatedQuery.ts`): a query value that both embeds the swapped id AND equals a leaf of the reference React node is replaced with that SAME leaf from the candidate (sibling) node. ejoy's `?path=…/lessons/1030/<h0>.json` equals the reference `lesson.path`; the sibling node carries lesson 1032's own `lesson.path` (`…/1032/<h2>.json`), leaked into the free user's state even for PAID lessons (`lock:true`) — so the rewrite builds the real paid-lesson url and the probe reaches the paid content. This IS the leaked-capability IDOR (the client-routing analog of forging the sibling's HTTP request from leaked state). No-op unless the identity is genuinely duplicated.
  2. **Drop if still incoherent** (`config.analysis.clientRoutingPathCoherence`, default on, gates both steps): if the old value STILL lingers after the rewrite (`urlEmbedsValue`, boundary-aware, decoded, finds it even inside `?path=` — unlike `urlCarriesValue`'s whole-segment match), the swap can't be reconciled from state (ejoy's courseId `37 → 32`: `?path=` carries a LESSON path, absent from the COURSE node) → DROP. We do NOT probe a query-stripped clean path: that tested a different url than the user reaches and only produced FPs (removed along with `stripUrlQuery`).

  Downstream records the reconciled `confirmedUrl`. Path candidates only; a swap with no duplicated identity (nothing to reconcile) is probed exactly as before. Decision-logic change → `recheckFindings` on the 4 reference sites before trusting it there.
- **Param blacklist** (`config.analysis.paramBlacklist`, matched by exact name AND by TOKEN via `paramNameBlacklisted`/`tokenizeParamName`): a query param whose NAME is listed, OR any of whose camelCase/snake/kebab tokens is listed, is never mutated — so `max`/`min` also drop `maxLevel`/`minScore`, `page`/`size` also drop `pageSize`. Keep the list made of bound/pagination words: a token that is also a common English word (`order`, `page`, `size`) will also drop a real-ref param containing it (`orderId`, `pageId`). A query param whose NAME is listed is never mutated — pagination/sorting controls (`limit`, `offset`, `page`, `sort`, …) are not object references, so swapping one changes how MUCH of your own data returns, never WHOSE. The response therefore differs legitimately and NO response/DOM guard can ever reject it: busuu's `?limit=5` alone produced 22 of its 27 false positives (the bare value `5` matched 77 unrelated preindexed nodes — `$paddingCorrection`, `itemsCount`, `elements[4].id` — each contributing its component siblings' ids). `maxSegmentMatches` is the wrong tool (77 is far under the cap; lowering it would drop real identifiers). Path segments are never gated by this. Keep the default clear of any reference-site TP param (pimsleur's TP swaps `?id=`).
- **Locale-param filter** (`isLocaleParam`/`LOCALE_PARAM`, candidateGenerator.ts; main AND ablation, beside the param blacklist, NOT a config knob): a locale / UI-language query param selects the response's REPRESENTATION (which language its texts come back in), not WHOSE resource it is — swapping it returns the same resource in another language, so the response differs legitimately and no content guard can reject it (Mondly's `notification-preferences?mother_language=22` in Arabic/Thai/… → one FP per language, the same class as the `?limit` pagination FP). Matched by a REGEX, deliberately NOT a blacklist token: the bare token `language` would also drop `target_language`/`learning_language`, which in a language-learning app name the studied RESOURCE (possibly paid) — a real TP. The optional prefix set is UI/native/mother-style only, so `mother_language`/`ui_language`/`locale`/`lang`/`lng`/`langcode`/`mother_tongue` match while `target_language`/`learning_language`/`language_id` stay mutable. A semantic param-name fact like `VOLATILE_PARAMS`/`PREINDEXED_KEYS`; query params only (a path segment is never gated by it). Shared with the ablation so it keeps differing from the main pipeline ONLY in using JSON siblings.
- **DOM chrome-zone skip** (`domZone.ts`: `nodeChromeZone`/`domChromeZone`/`zoneWalkDepthFor`; main pipeline only, in `candidateGenerator.findUrlCandidates`): skip a preindex match whose React node sits inside the site's navigation/footer chrome — a URL value from nav/footer furniture is never a user-scoped resource id. Uses the newer extension's per-node serialized DOM (`node.dom`) + `parent`: a node is chrome iff itself or an ancestor is `<nav>`/`<footer>`, `role="navigation"`/`"contentinfo"`, or carries a nav/footer/sidebar class TOKEN. **NEVER `<header>`/`<section>`/`role=banner`** — busuu renders its `objective_<uuid>` cards (the real TPs) inside a `<header>`, so a header/section rule drops true positives (verified: the shipped nav/footer rule marks 0 objective-bearing nodes on a fresh busuu graph, 1.8% of nodes, all top-nav). The ancestor walk is bounded by `zoneWalkDepthFor` = `clamp(ceil(log2(nodeCount)), 3, 24)`, which SCALES with graph size (busuu ~8k nodes → 13, covers its observed depth 9; a small graph gets a short window so a distant nav ancestor can't wrongly contain a deep content node). Graceful: an old capture without `dom` → null → no skip (drops only on positive evidence). Not in the ablation (no React node to locate in the DOM). Counted in `findUrlCandidates`'s `chromeSkipped`, logged per site. A change here needs a `runAnalysisFromDb`/`recheckFindings` on a site crawled with the new extension.
- **Segment blacklist** (`config.analysis.segmentBlacklist`, default `['app']`): a path segment whose value is blacklisted is never mutated, in EITHER direction — not as the segment being swapped, and not as a candidate's replacement value. These are app-shell/section route roots (`/app`, `/speak`, …), not user-scoped ids; swapping one only switches app section (a different DOM that masquerades as a finding — the ejoy `/app` ↔ `/speak`,`/go`,`/website-directory` FPs). Query-param values are never blacklisted. Keep the default clear of any reference-site TP segment (none of busuu `objective_<uuid>` / pimsleur `?id` / lingualeo `wordTranslate` is `app`).
- **Identifier type-shape guard** (`sameIdShape`, candidateGenerator.ts; main AND ablation, NOT a config knob): a URL value is only swapped for a value of the same shape — numeric for numeric, non-numeric for non-numeric. A cross-type swap means the component's "sibling" is a different KIND of link (duolingo's lesson button `/lesson/unit/1/level/1` and the footer `/privacy` link share one Link component → `relative_domains=1 -> privacy`; promova `73 -> profile`). Compared on the STRING form, so a React number `1` and a string `'1'` are both numeric (candidateValue is `String(raw)`, the URL token is always a string). Digits only. Every stored reference TP is same-shape (pimsleur/lingualeo/promova numeric, busuu `objective_<uuid>`, clozemaster slugs).
- **Preindex lookups (and every shared-table read used during one site's analysis) MUST be site-scoped.** The DB holds many sites at once — `db.overwriteExistingDomain` wipes only the domain being re-crawled, never the others — so a read keyed by anything non-site-unique (a preindex `value`, a `url`, a `fingerprint`, a `node_id`) leaks another site's data into this site's analysis. `PreindexedValueStore.findByValue`/`countByValue` take `{ value, site }` and filter `state_id IN (SELECT id FROM react_states WHERE site = ?)` (`idx_react_states_site`); `candidateGenerator.findUrlCandidates` takes `site`. This was a real high-severity bug: celpipsimulator's `/blog` segment matched BABBEL's footer `blog` link (value `blog` was indexed by 4 sites) and forged a cross-site false positive. The clean reads are site-scoped by construction (`listMetaBySite`/`listBySite`/`listUrlsBySite`, `forEach{Response,GraphBySite}`, the `historyUrls` set); the deliberately UNscoped ones are safe — `getById`/`getResponseBody` key on a globally-unique PK, `authz_classifications` is a pure function of the diff (site-independent, never scope it), the ablation's JSON preindex is built in-memory from the site's own `http_events`, and all per-run dedup state resets per site. When adding any read, ask "could this return another site's row?".
- The ablation writes only to `ablation_*`. Never mix it with `vulnerabilities`/`analysis_stats`.
- Schema: tables are created in `db/openDatabase.ts`. `db.clearOnStart` wipes the tables listed in the README (`db.clearOnStart` in `## Configuration`). If you add a table, decide explicitly whether it gets wiped.

Full documentation: `docs/analysis.md` (keep it updated when behavior changes).

# Regression checks
For a change to the decision logic (guards, response comparison, capture), FIRST `npx tsx scripts/recheckFindings.ts <START_URL>`: re-examines only the stored `vulnerabilities`, writes nothing, minutes instead of a full pass. It verifies you did not LOSE a finding; it cannot find new ones, so also run the full pass when candidate generation changed: `npx tsx scripts/runAnalysisFromDb.ts <START_URL>` (uses captured data, no new crawl).

Expected (`recheckFindings`, authenticated profile, run one site at a time — they share the browser profile):
- **pimsleur 4/4** (`learn.pimsleur.com/MiniLearn`) — pure client-routed lessons by `?id`, fetch-gated. A drop below 4 means the network-idle wait or the not-found backoff regressed.
